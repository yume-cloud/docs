## Что делает этот шаг

После того как первое middleware попыталось определить компанию по адресу сайта (сабдомену) или по служебному заголовку, управление получает **Middleware разрешения тенанта по JWT**. Его задача — «до-определить» компанию для тех клиентов, у которых нет собственного сабдомена: мобильных приложений и внешних API-интеграций, которые обращаются к общему адресу и предъявляют только токен доступа.

Ключевая идея: если предыдущее middleware **не смогло** привязать запрос к конкретной схеме базы данных (соединение осталось на «псевдо-тенанте», то есть на общей public-схеме), то это middleware берёт компанию из самого пользователя, зашитого в его JWT-токене.

<Info>
Это middleware намеренно ничего не делает, если компания уже определена по адресу/заголовку. Оно вступает в игру только как запасной механизм для клиентов «без сабдомена».
</Info>

## Порядок работы

Обработка идёт строго по шагам.

### 1. Ленивое получение пользователя

Сначала middleware смотрит на пользователя запроса. Если он есть, но его идентификатор пустой (то есть пользователь ещё не догружен), middleware подменяет его на «ленивый» объект: настоящий пользователь будет извлечён из токена доступа только в момент первого обращения к нему.

Извлечение выполняет вспомогательный резолвер: он прогоняет запрос через **Кастомную JWT-аутентификацию** и возвращает найденного пользователя. Любая ошибка при этом **молча подавляется** — в таком случае возвращается анонимный пользователь.

<Note>
Подавление ошибок означает, что при недействительном или просроченном токене middleware не падает и не отдаёт ошибку сразу — оно просто получает анонимного пользователя и пропускает запрос дальше (см. шаг 2). Ответственность за отказ по причине неавторизованности лежит на самом эндпоинте.
</Note>

### 2. Проверка: нужно ли вообще разрешать тенант

Middleware выполняет основную логику только если компания ещё **не определена** — то есть соединение с базой находится на псевдо-тенанте (общая public-схема) либо тенант вообще не задан.

Если компания уже была определена ранее (по адресу или заголовку), middleware просто передаёт запрос дальше без изменений.

### 3. Умеет ли пользователь называть свою компанию

Если разрешать тенант всё-таки нужно, middleware проверяет, поддерживает ли объект пользователя операцию «определить свою компанию». У анонимного пользователя такой операции нет — в этом случае запрос просто пропускается дальше без установки компании.

<Tip>
Именно эта проверка — точка стыковки двух частей модуля: у объекта пользователя есть операция «определить свою компанию», а middleware её вызывает. Если у пользователя несколько членств в компаниях, логика выбора одного идентификатора инкапсулирована на стороне пользователя (описана в разделе про модель пользователя), а middleware работает с уже готовым числом.
</Tip>

### 4. Получение идентификатора компании

Middleware спрашивает у пользователя идентификатор его компании.

| Результат | Что происходит |
| --- | --- |
| Идентификатор не определён (пусто) | Запрос немедленно отклоняется с ответом **403** и сообщением «Пользователь не подключён к компании» |
| Идентификатор получен | Переход к поиску компании и переключению схемы |

<Warning>
Ответ 403 «Пользователь не подключён к компании» возвращается только на этой запасной ветке — то есть когда компания не была определена по адресу/заголовку И у аутентифицированного пользователя нет ни одного членства в компании. Для клиентов, заходящих по сабдомену компании, эта проверка не срабатывает вовсе.
</Warning>

### 5. Поиск компании с кэшированием

По полученному идентификатору middleware ищет компанию:

1. Сначала — в кэше под ключом вида `tenant_{идентификатор}`.
2. Если в кэше пусто, компания читается из базы по идентификатору и **результат кладётся в кэш на 60 секунд**.

После этого найденная компания устанавливается как активная: происходит переключение схемы базы данных на схему этой компании, и та же компания проставляется в объект запроса как «тенант запроса», чтобы последующий код мог на неё опираться.

<Info>
Короткий срок жизни кэша (60 секунд) — это компромисс: он снимает повторные обращения к базе за одной и той же компанией в пределах серии близких запросов, но при этом изменения в записи компании подхватываются почти сразу.
</Info>

## Как это используется

Этот механизм — то, что позволяет мобильному приложению и внешним API-клиентам работать без «фирменного» сабдомена компании. Клиент обращается к общему адресу, предъявляет токен доступа, и middleware само выбирает нужную схему базы данных по компании, к которой привязан пользователь.

Порядок в цепочке обработки важен: сначала работает middleware, определяющее компанию по адресу/заголовку, и только затем — данное middleware. Поэтому клиенты с сабдоменом идут по «быстрому» пути (компания уже известна), а клиенты без сабдомена — по «запасному» (компания берётся из токена).

## Итоговая таблица полей

| Поле | Тип | Назначение |
| --- | --- | --- |
| Следующий обработчик | Вызываемый объект | Ссылка на следующее middleware или представление в цепочке |
| Пользователь запроса | Связь | Аутентифицированный пользователь; при пустом идентификаторе догружается лениво из токена |
| Идентификатор компании | Число | Результат операции «определить свою компанию» у пользователя; при отсутствии — ответ 403 |
| Ключ кэша компании | Текст | Формат `tenant_{идентификатор}`, под ним компания кэшируется на 60 секунд |
| Тенант (компания) | Связь | Компания, найденная в кэше или базе; передаётся на переключение схемы и в объект запроса |
| Тенант запроса | Связь | Разрешённая компания, проставляемая в объект запроса для остального кода |
