## Что делает эта часть модуля

Когда клиент (мобильное приложение, веб-панель, интеграция) обращается к API, он предъявляет access-токен. Эта часть отвечает на три вопроса:

- **Кто это?** — по токену находится пользователь, проверяется его активность, объект кэшируется на 5 минут.
- **Как продлить сессию?** — по refresh-токену выпускается новый access-токен и, при включённой ротации, новый refresh-токен.
- **Тот ли это пользователь после переноса между схемами?** — старый идентификатор из токена при необходимости переводится в новый через таблицу соответствий.

<Info>
Кастомная JWT-аутентификация используется в проекте как способ проверки токена по умолчанию для всех защищённых эндпоинтов.
</Info>

## Разрешение пользователя по access-токену

При каждом запросе с access-токеном выполняется следующая последовательность.

### Шаг 1. Извлечение идентификатора

Из полезной нагрузки токена читается идентификатор пользователя. Если такого поля в токене нет, запрос отклоняется как невалидный токен.

### Шаг 2. Перевод старого идентификатора в новый (remap)

Этот шаг выполняется только если текущая схема не публичная **и** включён флаг перевода артефактов (по умолчанию включён).

Идея: некоторые пользователи были перенесены между схемами, и их прежний идентификатор в токене больше не совпадает с текущим. Система обращается к таблице соответствий и ищет запись, у которой:

- исходная схема совпадает с текущей схемой запроса;
- исходная таблица — таблица пользователей;
- старый идентификатор равен идентификатору из токена.

Если совпадение найдено, дальнейшая работа идёт уже с новым идентификатором. Если нет — идентификатор из токена остаётся как есть.

<Note>
Перевод идентификатора нужен только для непубличных схем. В публичной схеме идентификатор из токена используется напрямую.
</Note>

### Шаг 3. Кэш или база

По итоговому идентификатору формируется ключ кэша вида «пользователь + идентификатор». Ключ **автоматически изолирован по схеме**: одинаковый идентификатор в разных схемах попадает в разные ячейки кэша, поэтому пользователи разных компаний не перемешиваются.

- Если объект пользователя есть в кэше — он берётся оттуда.
- Если нет — пользователь читается из базы. Если такого пользователя нет, запрос отклоняется как «пользователь не найден».

### Шаг 4. Проверка активности и запись в кэш

Найденный пользователь проверяется на активность. Неактивный пользователь получает отказ «пользователь неактивен» — эта проверка выполняется на каждом запросе, в том числе для объекта, взятого из кэша. Важно понимать, что для объекта из кэша признак активности берётся из закэшированной копии, а не из свежего чтения базы.

Только пользователь, прочитанный из базы на этом запросе, записывается в кэш на 5 минут. Объект, уже взятый из кэша, повторно не перезаписывается.

<Warning>
Кэш живёт 5 минут. Если пользователя деактивировали или изменили, а инвалидация кэша не сработала, до истечения этих 5 минут запросы могут по-прежнему видеть старое состояние. Это касается и признака активности: проверка активности выполняется по уже закэшированному объекту, поэтому деактивированный пользователь может продолжать проходить проверку, пока кэш не истечёт или не будет сброшен.
</Warning>

## Обновление токена

Отдельный сериализатор обслуживает эндпоинт продления сессии по refresh-токену. Логика близка к разрешению пользователя, но со своими нюансами.

### Разбор refresh-токена и перевод идентификатора

Из refresh-токена извлекается идентификатор пользователя. Если схема непубличная, применяется тот же перевод старого идентификатора в новый по таблице соответствий, и полезная нагрузка refresh-токена обновляется новым идентификатором. В публичной схеме перевод не выполняется.

### Проверка пользователя

Если идентификатор известен и пользователь найден в базе, проверяется правило аутентификации (в частности — активность пользователя). Не прошедший проверку пользователь получает отказ «нет активной учётной записи».

### Выпуск токенов

- Всегда формируется новый access-токен.
- При включённой ротации refresh-токенов старый refresh при необходимости попадает в чёрный список, а затем выпускается новый refresh-токен (с новым идентификатором записи, временем создания и сроком действия).

<Info>
Настройки проекта: срок жизни access-токена — 1 день, refresh-токена — 30 дней, ротация refresh-токенов включена.
</Info>

## Инвалидация кэша по всем схемам пользователя

Так как пользователь глобален, а членство в компаниях хранится отдельно, один и тот же пользователь может быть закэширован в нескольких схемах одновременно. Поэтому сброс кэша выполняется сразу во всех релевантных схемах.

Набор схем собирается так:

1. Всегда включается публичная схема.
2. Добавляются схемы тех компаний, где пользователь числится администратором (по членствам пользователя в компаниях).

Затем во всех этих схемах удаляется ячейка кэша пользователя: для текущей схемы — напрямую, для остальных — с временным переключением на нужную схему. Сбой на отдельной схеме логируется, но не прерывает обработку остальных.

<Tip>
Именно поэтому недостаточно чистить кэш только в текущей схеме: копия объекта пользователя может жить и в публичной схеме, и в схемах его компаний.
</Tip>

### Сводка ключевых величин

| Параметр | Значение | Назначение |
| --- | --- | --- |
| Время жизни кэша пользователя | 5 минут | как долго объект пользователя хранится в кэше после чтения из базы |
| Изоляция ключа кэша | по схеме | одинаковый идентификатор в разных схемах не пересекается |
| Флаг перевода идентификаторов | включён | активирует поиск соответствия старого и нового идентификатора для непубличных схем |
| Срок access-токена / refresh-токена | 1 день / 30 дней | длительность сессии и окна продления |

## Как это связано с остальным модулем

- Перевод идентификаторов опирается на таблицу соответствий старых и новых идентификаторов, наполняемую при переносе пользователей между схемами.
- Инвалидация кэша вызывается из мест, где пользователь меняется (например, при обновлении профиля или смене групп/членств), чтобы следующий запрос перечитал актуальное состояние из базы.
- Разрешение тенанта по токену (в middleware) работает в паре с этим механизмом: сначала выбирается схема, затем по токену находится пользователь уже в контексте нужной схемы.
