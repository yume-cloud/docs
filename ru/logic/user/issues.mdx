Эта страница собирает в одном месте все известные **проблемы, баги и логические ошибки** модуля аутентификации и пользователей: как поведение расходится с ожидаемым, к чему это приводит и где искать причину в коде. Разделы упорядочены по серьёзности — от рисков безопасности до незначительных нюансов.

Ссылки на файлы и строки даны для разработчиков как ориентир и относятся к состоянию кода на момент составления страницы. Остальные страницы раздела намеренно описывают только штатное поведение — все отклонения вынесены сюда.

## Безопасность

Открытых рисков безопасности в самом модуле аутентификации сейчас нет — ранее описанные здесь закрыты. Смежные риски уровня платформы (разрешающий доступ по умолчанию, анонимные вебхуки) остались и перечислены в [«Риски и подводные камни: инфраструктура»](/ru/logic/infrastructure/issues).

<Note>
**Исправлено и снято с этой страницы:**

- **Активная компания проверяется на членство.** Компания по-прежнему определяется из клиентского заголовка, `Origin` или хоста, но для аутентифицированного запроса теперь требуется запись участия (пользователь ↔ компания), иначе `403 {"code": "tenant_forbidden"}`; явный, но неизвестный идентификатор компании даёт `403 {"code": "tenant_not_found"}` (`middlewares/tenant_access.py`). Раньше любой валидный вход плюс подставленный идентификатор компании читал и **переименовывал** чужую компанию.
- **Одноразовая ссылка перехода стала действительно одноразовой.** Пометка об использовании токена гасится в транзакции с блокировкой строки (`user/serializers/general.py:207-214`); повторное или неизвестное значение отдаёт `400` вместо `200` с учётными данными.
- **Веб-callback Google требует подтверждённой почты** (`user/views/google_oauth.py:163`) — раньше проверка была только на мобильном входе по ID-токену. Эффект небольшой: Google отдаёт только основную и уже подтверждённую почту, ценность правки — в снятии асимметрии между путями входа.
- **Вход через Google не создаёт компанию.** Раньше общее ядро входа заводило новую компанию и делало пользователя её суперпользователем. Теперь соцвход создаёт и обновляет только пользователя, а компанию заводит единственная точка — запрос на создание компании (`POST /v1/tenant/`). До этого пользователь остаётся без компании и получает `403 {"code": "tenant_required"}` (кроме адресов из списка исключений).
</Note>

## Логические ошибки

<Warning>
**Признак активности проверяется по закэшированной копии аккаунта.** Сведения об аккаунте хранятся в кэше около 5 минут, и проверка «аккаунт активен» на каждом запросе читает именно закэшированную копию, а не свежее состояние. Поэтому отключённый сотрудник продолжает проходить проверку до истечения кэша или его сброса.

- **Последствие:** отзыв доступа действует не мгновенно — окно до нескольких минут.
- **Как чинить:** проверять признак активности отдельным свежим чтением либо сбрасывать кэш аккаунта при отключении.
</Warning>

<Warning>
**Перевод старого идентификатора аккаунта в новый молча не срабатывает из-за несовпадения типов.** В таблице соответствий, наполняемой при переносе записей между компаниями, идентификаторы хранятся как текст (перенос затрагивал не только аккаунты, и не у всех записей ключи числовые), а сравнение выполняется с числовым идентификатором из сессии. Сравнение числа со строкой ничего не находит, и перевод тихо пропускается.

- **Последствие:** перенесённый между компаниями аккаунт может не опознаться по старой сессии — без ошибки, просто как «не найден».
- **Как чинить:** приводить идентификатор к строке перед поиском и обратно к числу после.
</Warning>

<Warning>
**Кэш ролей в компании живёт вечно и не сбрасывается при смене роли.** Признаки «суперпользователь / сотрудник / субаренда / группа в компании» кэшируются **без срока жизни**, а общая процедура сброса кэша пользователя очищает только ключ самого пользователя — ключи ролей она не трогает. Смена членства/роли (через редактор сотрудника или напрямую) не инвалидирует эти ключи.

- **Последствие:** после изменения роли старые права сохраняются в кэше неопределённо долго — пользователь может продолжать считаться сотрудником/суперпользователем (или наоборот) уже после изменения.
- **Где:** установка кэша без таймаута — `user/models.py:266-329`; сброс, не трогающий ролевые ключи, — `common/auth_cache.py:34-56`.
</Warning>

<Warning>
**Телефон, почта и имя пользователя не уникальны по отдельности.** В базе уникальна только **тройка** «имя пользователя + телефон + почта», причём все три поля допускают пустое значение (а в базе данных множество строк со всеми пустыми значениями считаются разными). Поэтому в системе могут существовать несколько пользователей с одинаковым телефоном; вход и поиск выбирают одного из совпавших по сортировке.

- **Последствие:** дубли по телефону/почте возможны; в какой аккаунт войдёт пользователь при дубле — определяется порядком (например, по убыванию идентификатора), а не бизнес-правилом. Проверка уникальности по отдельным полям выполняется только в коде и только на путях, которые её вызывают.
- **Где:** ограничение — `user/models.py:353` (`unique_together`); вход — `user/backends.py:18` (`order_by("-id")`); поиск/валидация — `user/services.py:19-29, 52-70`.
</Warning>

<Warning>
**Кэш прав группы живёт сутки и не сбрасывается при изменении прав.** Набор прав группы кэшируется на 24 часа по ключу группы; изменение прав группы не инвалидирует этот кэш.

- **Последствие:** после изменения прав роли новые/убранные права применяются с задержкой до суток.
- **Где:** `user/backends.py:47-57`.
</Warning>

Прочие логические нюансы:

- **Повторная привязка пользователя к компании не обновляет роли.** Привязка выполняется по принципу «создать при отсутствии»: у уже существующего членства переданные роли/группа **не** применяются — только при первом создании. (`user/services.py:38-49`)
- **Любое сохранение пользователя создаёт/привязывает клиента в текущей компании.** При каждом сохранении для не-сотрудника с телефоном автоматически ищется/создаётся карточка клиента для текущей компании — побочный эффект на любом сохранении, зависящий от того, какая компания активна в момент сохранения. (`user/models.py:388-425`)
- **Привилегированное создание/редактирование сотрудника не проверяет дубли.** Расширенный редактор пользователя не вызывает проверку уникальности телефона/почты (в отличие от ограниченного редактора профиля). (`user/serializers/general.py:80-149` против `:160-162`)
- **Новому пользователю назначается уровень лояльности из текущей компании.** Глобальному пользователю присваивается «привязанный к компании» уровень лояльности (самый дешёвый) — концептуальное смешение глобальной учётки и данных конкретной компании. (`user/models.py:197-202`)

## Прочее

- **Мёртвая ветка создания приложения соцвхода.** Проверка существующей записи приложения Google написана так, что исключение «не найдено» никогда не возникает (выборка возвращает пустой результат, а не бросает ошибку), поэтому ветка автосоздания недостижима. (`user/views/google_oauth.py:96-108`)
- **Адрес перенаправления Google по умолчанию указывает на localhost.** В обмене кода адрес перенаправления по умолчанию — локальный адрес разработки; генерация ссылки согласия собирает URL без кодирования параметров. (`user/views/google_oauth.py:153, 217-238`)
