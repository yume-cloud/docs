## Что делает эта часть

Google-вход — это отдельный способ попасть в систему без ввода пароля: пользователь подтверждает личность у Google, а система создаёт или находит его учётную запись и выдаёт токены доступа приложения. Реализованы три точки входа и одно общее ядро, которое превращает данные от Google в реального пользователя.

| Точка входа | Метод | Кто использует | Что делает |
| --- | --- | --- | --- |
| Генерация OAuth-ссылки | GET | веб-клиент | Собирает ссылку на страницу согласия Google |
| Callback веб-OAuth | POST | веб-клиент | Обменивает код авторизации на данные профиля и выдаёт токены |
| Вход по ID-token (мобильный) | POST | нативные приложения (iOS/Android) | Проверяет подпись ID-token от Google и выдаёт токены |

Все три открыты без предварительной авторизации (доступны анонимно) — это ожидаемо, потому что вход как раз и происходит здесь.

## Веб-сценарий: ссылка и обмен кода

### Шаг 1. Генерация ссылки

Клиент запрашивает ссылку авторизации. Система берёт публичный идентификатор OAuth-клиента из настроек, подставляет переданный клиентом адрес возврата и фиксированные параметры: запрашиваемые права «openid email profile», тип ответа «код авторизации» и офлайн-доступ (чтобы Google при необходимости выдал refresh-token). Готовая ссылка возвращается клиенту, который перенаправляет туда пользователя.

<Warning>
Адрес возврата в ссылке берётся из параметра запроса без проверки и подставляется в URL как есть. Значения по умолчанию нет — если клиент не передал адрес, в ссылку попадёт пустое значение, и Google откажет во входе.
</Warning>

### Шаг 2. Обмен кода на профиль

После согласия пользователя Google возвращает на клиент код авторизации. Клиент присылает этот код в callback. Дальнейшая логика:

1. Если кода нет — сразу ответ об ошибке (код обязателен).
2. Система отправляет код в Google на обмен: вместе с идентификатором и секретом OAuth-клиента, типом «код авторизации» и адресом возврата. Адрес возврата берётся из запроса, а если его нет — используется локальный адрес разработки по умолчанию.
3. Если в ответе Google нет access-token — ответ об ошибке обмена.
4. С полученным access-token система запрашивает у Google профиль пользователя (userinfo).
5. Если в профиле нет email — ответ об ошибке получения данных.
6. Профиль передаётся в общее ядро создания/обновления пользователя, после чего выдаются токены приложения.

<Warning>
Адрес возврата по умолчанию указывает на локальный адрес разработки. В боевой среде клиент обязан передавать собственный адрес возврата — иначе обмен кода не пройдёт.
</Warning>

## Мобильный сценарий: проверка ID-token

Нативные приложения получают ID-token непосредственно от Google и присылают его на отдельную точку входа. Здесь система не ходит в Google за обменом кода, а проверяет сам токен:

1. Если токена нет — ответ об ошибке (токен обязателен).
2. Собирается список допустимых «получателей» токена — это разрешённые идентификаторы OAuth-клиентов: веб, iOS и Android. Пустые значения отбрасываются. Если список пуст (ни один идентификатор не настроен) — ответ «Google-вход не настроен».
3. Токен проверяется на подлинность и целостность подписи средствами Google. Если проверка не прошла — ответ о недействительном токене.
4. Проверяется «получатель» токена: он должен совпасть с одним из разрешённых идентификаторов клиентов. Иначе — отказ.
5. Проверяется «издатель» токена: допускаются только адреса Google (`accounts.google.com` и его https-вариант). Иначе — отказ.
6. Проверяется, что почта в токене подтверждена. Если нет — отказ.
7. Только после всех проверок содержимое токена передаётся в общее ядро создания/обновления пользователя и выдаются токены приложения.

<Note>
Проверки «получателя», «издателя» и подтверждённости почты защищают от подмены: без них чужой валидный по подписи токен, выпущенный для другого приложения, мог бы использоваться для входа.
</Note>

## Ядро: создание или обновление пользователя

Обе точки входа сходятся в одной процедуре, которая принимает данные Google и возвращает готового пользователя. Форматы отличаются: веб-профиль хранит идентификатор Google в одном поле, ID-token — в другом; ядро понимает оба варианта.

### Извлечение данных

Из полученного набора берутся почта, имя, фамилия, ссылка на аватар и идентификатор пользователя у Google (из поля веб-профиля либо, если его нет, из поля ID-token). Если почты нет — процедура прерывается ошибкой (для мобильного входа она превращается в ответ об ошибке; в веб-сценарии наличие почты уже проверено ранее).

### Поиск и обновление пользователя

Пользователь ищется по почте.

- **Если найден** — данные дополняются, но не перезаписываются: имя, фамилия и аватар проставляются только если у пользователя соответствующее поле ещё пустое. Сохранение происходит только при реальном изменении.
- **Если не найден** — создаётся новый пользователь с почтой, именем, фамилией, аватаром и логином, равным почте.

<Info>
Существующий профиль никогда не затирается данными из Google: заполняются только пустые поля. Так ручные правки имени или фото не перетираются при повторном входе.
</Info>

### Загрузка аватара

Аватар подтягивается отдельным хелпером: он скачивает картинку по ссылке из профиля с таймаутом (примерно 3 секунды на соединение и 5 секунд на ответ). Если ссылки нет или ответ не успешный — возвращается пустое значение, и аватар просто не проставляется.

### Привязка социального аккаунта

Для пользователя обеспечивается наличие **Социального аккаунта** с провайдером «google» и идентификатором пользователя у Google. Если такой связки ещё нет — она создаётся, а сырые данные профиля сохраняются в неё. Если уже есть — сырые данные профиля перезаписываются свежими и сохраняются. Так связка Google-аккаунта с пользователем всегда актуальна.

### Автосоздание компании при первом входе

Ключевой побочный эффект: если у пользователя ещё нет ни одной компании (тенант не определяется), система автоматически создаёт для него компанию и оформляет членство с правами владельца — сотрудник со статусом администратора и суперпользователя, без привязки к группе и без пометки субаренды. Членство создаётся идемпотентно (повторно не дублируется).

<Warning>
Вход через Google для нового человека — это не только регистрация пользователя, но и автоматическое создание отдельной компании, где он сразу становится владельцем со всеми правами. Это осознанное поведение self-service регистрации, а не побочный дефект.
</Warning>

### Выдача токенов

После успешного создания/обновления обе точки входа выдают пару токенов приложения — доступа и обновления — которые дальше используются как при обычном входе.

## Allauth-адаптеры

Помимо ручного ядра, в проекте настроены два кастомных адаптера библиотеки allauth — они управляют её собственным конвейером входа.

**Адаптер локальных аккаунтов** (обычная, не социальная регистрация) всегда разрешает саморегистрацию. Его переопределённое сохранение по сути повторяет стандартное поведение: пользователь записывается в базу только при обычном (не отложенном) сохранении.

**Адаптер социального входа**:

- **Связывание по почте до входа**: если приходит Google-логин и в системе уже есть пользователь с такой почтой, социальный логин привязывается к этому существующему пользователю. Так один человек не получает второй дублирующий аккаунт из-за входа через Google.
- **Заполнение пользователя** из сырых данных Google: почта, имя, фамилия; логин при отсутствии подставляется равным почте.
- **Сохранение пользователя**: для Google-провайдера имя и фамилия проставляются только если пусты, логин при отсутствии — из почты, затем пользователь сохраняется.
- Саморегистрация через соцвход всегда открыта.

<Note>
Связывание по почте — важная гарантия: вход через Google для уже существующего по почте пользователя не плодит дубликаты, а подключается к его текущей учётной записи.
</Note>

## Как это используется

- Веб-клиент сначала получает ссылку авторизации, ведёт пользователя на страницу согласия Google, затем присылает полученный код в callback и получает токены приложения.
- Мобильные приложения получают ID-token нативно и обменивают его на токены приложения через мобильную точку входа.
- Для нового пользователя любой из путей создаёт учётную запись и его собственную компанию с правами владельца; для существующего — просто входит, обновляя недостающие поля профиля и связку с Google.
