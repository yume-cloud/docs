## Что делает эта часть модуля

Здесь живёт «ядро» уведомлений: как хранится само событие, как хранится персональное состояние каждого получателя и что происходит автоматически в момент создания уведомления — подбор подходящих сотрудников и рассылка сообщения по трём каналам (веб, мобильный push, Telegram).

Проще говоря: одно событие в системе (новый заказ, задача, документ) превращается в одно **Уведомление**, а система сама решает, кому из сотрудников и по каким каналам его показать.

## Модель данных

### Уведомление

Одна запись — одно событие компании. Уведомление принадлежит компании, знает, к какому объекту системы оно относится, и несёт текст сообщения плюс маршрутную информацию.

| Поле | Тип | Назначение |
| --- | --- | --- |
| Компания | связь | Компания-владелец уведомления. |
| Автор/источник | связь | Пользователь, породивший уведомление; при его удалении поле обнуляется, само уведомление остаётся. |
| Текст | текст | Основное содержимое сообщения (обязательно). |
| Тип | перечисление | Уровень важности: Информация, Предупреждение, Тревога. По умолчанию — Информация. |
| Доп. данные | JSON | Произвольная полезная нагрузка (например, идентификатор лида для задачи). |
| Тип объекта | текст | Строковый код связанной сущности (заказ, задача по лиду, обслуживание, документ и т.д.). |
| ID объекта | число | Идентификатор связанной сущности; используется, чтобы построить ссылку. |
| Целевые получатели | список чисел | Явный список ID пользователей. Если задан — доставка сужается только до них. |
| Тема | перечисление | Тема уведомления для фильтрации доступа. По умолчанию — тема по умолчанию. |
| Каналы доставки | список | Разрешённые каналы: Telegram, push, веб. По умолчанию включены все три. |
| Одноразовый захват | флаг | Уведомление, которое «забирает» только один сотрудник. |
| Кем захвачено | связь | Пользователь, забравший одноразовое уведомление; при удалении обнуляется. |
| Время захвата | дата/время | Момент захвата. |
| Создано | дата/время | Отметка создания. |
| Обновлено | дата/время | Отметка последнего изменения; ключевое поле для окна группировки уведомлений по времени. |

<Info>
Пара «Тип объекта» + «ID объекта» — это адрес связанной сущности. По ним строятся кликабельные ссылки в Telegram и переходы в приложениях. «Доп. данные» дополняют этот адрес нестандартными случаями (например, для задачи по лиду ссылка ведёт не на объект задачи, а на лид, чей идентификатор лежит именно в доп. данных).
</Info>

Записи всегда отдаются от новых к старым. Для быстрого доступа есть два индекса: по компании и времени обновления, а также по компании вместе с адресом объекта и временем обновления — второй нужен, чтобы находить уже существующее уведомление по тому же объекту (это опора для дозаписи и группировки, которые описаны в других разделах модуля).

### Уведомление пользователя

Одно **Уведомление** может касаться нескольких сотрудников, но состояние «прочитано / в архиве» у каждого своё. Для этого на каждого получателя заводится отдельная персональная запись, привязанная к родительскому уведомлению.

| Поле | Тип | Назначение |
| --- | --- | --- |
| Компания | связь | Компания-владелец записи. |
| Уведомление | связь | Родительское уведомление. |
| Получатель | связь | Сотрудник, для которого хранится состояние; при удалении обнуляется. |
| В архиве | флаг | Признак того, что получатель заархивировал уведомление. |
| Создано | дата/время | Отметка создания записи. |
| Обновлено | дата/время | Служебная отметка изменения. |

<Note>
Комбинация «компания + получатель + уведомление» уникальна — у одного сотрудника не может быть двух персональных состояний по одному и тому же уведомлению. В самой записи хранится только признак архивации: отдельного булева-флага «прочитано» здесь нет. Судя по устройству модели, признаком прочтения служит само наличие персональной записи (и её время создания).
</Note>

## Веер доставки: что происходит при создании

Как только уведомление сохранено **впервые**, автоматически запускается веер доставки. При последующих изменениях того же уведомления веер не срабатывает — только при создании.

Логика по шагам:

1. **Определяется компания.** Веер берёт текущую компанию из контекста запроса. Если компания не определена (например, вызов идёт вне контекста компании), доставка молча прекращается — ничего не рассылается.

2. **Собирается список штатных сотрудников этой компании.** Берётся перечень пользователей, у которых признак сотрудника выдан **именно в этой компании**. Участник другой компании в список не попадает, даже если сотрудником он числится где-то ещё. Список кэшируется отдельно на каждую компанию и переиспользуется между уведомлениями, чтобы не пересчитывать его каждый раз.

3. **Фильтрация по матрице доступа.** Из настроек доступа к уведомлениям отбираются строки, которые одновременно: относятся к этой компании, к теме данного уведомления, помечены как включённые и принадлежат сотрудникам из собранного списка. Если у уведомления задан явный список целевых получателей, фильтр дополнительно сужается только до них.

4. **Разделение по каналам.** Для каждого из трёх каналов из отобранных строк доступа берутся только те сотрудники, у кого этот конкретный канал включён. Так один и тот же человек может получать уведомление в вебе, но не в Telegram — всё зависит от его персональной матрицы доступа.

5. **Отправка.** По каждому каналу, который разрешён в самом уведомлении, вызывается свой помощник доставки — но только для «своего» списка сотрудников.

### Условия по каждому каналу

<Info>
Канал участвует в рассылке, только если он одновременно (а) входит в разрешённые каналы самого уведомления и (б) включён у конкретного сотрудника в его матрице доступа. Плюс к этому у веба и Telegram есть свои технические предусловия.
</Info>

| Канал | Дополнительное условие | Что уходит получателю |
| --- | --- | --- |
| Веб (Ably) | Должны быть настроены доступы к сервису Ably. | Событие с текстом, типом, адресом объекта и доп. данными публикуется в веб-канал компании. |
| Мобильный push (Expo) | — | Push с заголовком «Уведомление» и текстом сообщения; в полезной нагрузке — адрес объекта, тип и доп. данные. |
| Telegram | Должен быть настроен бот. | Готовый текст со ссылкой (см. ниже) рассылается в привязанные чаты сотрудников. |

### Как формируется сообщение в Telegram

Текст для Telegram собирается по-разному в зависимости от типа объекта, и в него подставляется ссылка на веб-кабинет компании. Адрес кабинета берётся из настроек компании (служебный префикс из адреса убирается); если адрес не задан, используется адрес по умолчанию.

- **Заказ** — текст выделяется жирным, ниже добавляется ссылка на страницу заказа.
- **Задача по лиду** — текст предваряется подписью «Новая задача», ссылка ведёт на лид, идентификатор которого берётся из доп. данных. Если для такой задачи в доп. данных нет идентификатора лида, уведомление в Telegram не отправляется вовсе.
- **Задача по обслуживанию** — подпись «Новая задача ТОО» и ссылка на страницу обслуживания.
- **Документ** — текст жирным и ссылка на страницу документа.

Готовое сообщение рассылается во все Telegram-чаты, привязанные к отобранным сотрудникам этой компании.

## Одноразовые уведомления («захват»)

Отдельный режим — уведомление с одноразовым захватом. Его смысл: событие показывается всем подходящим сотрудникам, но «забрать» (обработать) его должен только один. Когда кто-то его захватывает, фиксируется, кто именно и в какой момент это сделал.

Для веба есть отдельный механизм отзыва: после захвата всем остальным веб-клиентам отправляется команда убрать это уведомление из списка, а у того, кто захватил, оно остаётся помеченным. Отзыв работает только при настроенном доступе к сервису Ably.

<Tip>
Захват и его отзыв — про согласованность списков между открытыми вкладками сотрудников. Сам по себе первичный веер доставки одноразовое уведомление рассылает так же, как обычное; разница проявляется в момент, когда его кто-то забирает.
</Tip>

## Сломанная интеграция как уведомление

Отказ интеграции раньше оставался в логах: ключ протухал, сообщения переставали уходить, и компания узнавала об этом от клиентов. Теперь любой отказ интеграции превращается в **обычное уведомление** — никакого отдельного журнала отказов для этого нет, и он намеренно не заводился.

Отправитель передаёт код интеграции, вид события и текст. Из вида события выводится всё остальное:

| Вид события | Тема | Тип | Уровень |
| --- | --- | --- | --- |
| Истёк ключ доступа | Истёк ключ доступа интеграции | Алерт | Ошибка |
| Не удалось авторизоваться | Истёк ключ доступа интеграции | Алерт | Ошибка |
| Интеграция отключена | Истёк ключ доступа интеграции | Алерт | Ошибка |
| Ошибка при обращении к сервису | Ошибка интеграции | Предупреждение | Предупреждение |
| Не удалось синхронизировать данные | Ошибка интеграции | Предупреждение | Предупреждение |
| Не удалось провести оплату | Ошибка интеграции | Предупреждение | Предупреждение |
| Не удалось сформировать QR-код | Ошибка интеграции | Предупреждение | Предупреждение |

События про доступ (первые три) считаются «ключевыми»: они означают, что интеграция больше не работает и нужны действия человека, поэтому идут алертом. Остальные — предупреждения о единичном сбое.

Уведомление создаётся **сгруппированным**, с окном группировки в час: сервис, отвечающий ошибкой на каждый запрос, даст одну запись со счётчиком, а не поток одинаковых сообщений. Адресуется оно самой интеграции, рассылается по всем трём каналам и уходит по матрице доступа — явных получателей у него обычно нет.

В дополнительных данных уведомления лежит всё, что нужно интерфейсу, чтобы показать карточку и увести пользователя чинить: код, идентификатор и название интеграции, идентификатор подключения, вид события и уровень, код ответа сервиса, текст ошибки, полезная нагрузка, **адрес страницы интеграции** и **список доступных действий** (обновить ключ, переподключить, изменить, удалить) — набор действий тоже выводится из вида события.

<Note>
Когда интеграция снова заработала, её уведомления об отказе **удаляются** — по адресации на саму интеграцию. Отдельного «уведомления о восстановлении» нет: карточка отказа просто исчезает.
</Note>

### Протухший ключ отключает интеграцию

Для Wazzup отказ по ключу разбирается особо. Ответ сервиса распознаётся как «ключ недействителен», если пришёл код 401 либо тело ответа содержит одну из известных ошибок авторизации. В этом случае:

1. У всех подключений компании к Wazzup снимается признак «подключено», а **сам ключ вычищается** из данных подключения.
2. Отправляется уведомление вида «истёк ключ доступа» с подсказкой обновить ключ и подключить заново.
3. Вызывающему коду возвращается ошибка с кодом конфликта и машиночитаемым признаком отключения — чтобы интерфейс показал не абстрактный сбой, а понятную причину.

Подключение при этом **не удаляется** — удаляется только ключ. История, настройки и привязки сохраняются, и после обновления ключа интеграция включается на том же подключении. Раньше протухший ключ просто молчал: сообщения не уходили, а в интерфейсе интеграция выглядела рабочей.

## Как это используется

Эта часть — фундамент всего модуля уведомлений. Прикладной код не рассылает сообщения вручную: он просто создаёт **Уведомление** с нужными текстом, темой, адресом объекта и (при необходимости) явным списком получателей — а веер доставки сам подбирает сотрудников по матрице доступа и раскладывает сообщение по каналам. Фоновые задачи создания, дозаписи и группировки уведомлений, а также детали каждого канала доставки и настройка матрицы доступа описаны в соседних разделах модуля.

## Особенности поведения

- Для задачи по лиду обязателен идентификатор лида в доп. данных: без него уведомление в Telegram не отправляется совсем (ссылку построить не из чего).
- Веб-канал участвует в рассылке только при настроенных доступах к сервису Ably, а Telegram — только при настроенном боте; иначе соответствующий канал тихо пропускается.
- Отзыв одноразового уведомления из веба работает только при настроенном доступе к Ably; без него остальные вкладки не узнают о захвате и уведомление у них останется в списке.
- Явный список целевых получателей только сужает аудиторию поверх матрицы доступа, но не обходит её: указанный сотрудник всё равно должен иметь включённый доступ по теме и каналу, иначе сообщения не получит.
- Признак сотрудника учитывается по конкретной компании, а не «в целом по системе»: клиент вашей компании, который в другой компании работает сотрудником, внутренних уведомлений вашей компании не получит.

<Info>
- В персональной записи получателя нет отдельного флага «прочитано» — хранится только признак архивации; признаком прочтения, по-видимому, служит само наличие такой записи и её время создания.
- Разбивка по каналам идёт по индивидуальному признаку канала в строках матрицы доступа, поэтому один и тот же сотрудник может получать уведомление по одному каналу и не получать по другому.
</Info>
