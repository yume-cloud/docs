## Модель данных

В основе раздела лежит справочник персональных настроек — **Доступ к уведомлениям**. Одна запись этой модели отвечает на вопрос: «получает ли конкретный сотрудник конкретной компании уведомления по конкретной теме через конкретный канал».

| Поле | Тип | Назначение |
|---|---|---|
| Компания | связь | к какой компании относится настройка |
| Канал | список (Веб (Ably) / Push (мобильное приложение) / Telegram-бот) | канал доставки, к которому относится настройка |
| Пользователь | число (внутренний идентификатор сотрудника) | владелец настройки |
| Тема | список (см. справочник тем ниже) | категория события, к которой относится настройка |
| Включено | флаг | если включено — сотрудник получает уведомления по этой теме через этот канал; если выключено — не получает |

Для одной пары «компания + сотрудник» не может быть двух записей с одинаковым сочетанием канала и темы — это сочетание уникально. Иными словами, полный набор персональных настроек одного сотрудника — это матрица «канал × тема», где в каждой ячейке лежит ровно один флаг включено/выключено.

<Info>
Этот справочник хранится в общей области данных, единой для всех компаний системы (а не в изолированном пространстве данных компании), поэтому разделение по компаниям обеспечивается исключительно полем «Компания» в каждой записи, а не физическим разделением хранения. Любая выборка по этой модели обязана явно фильтроваться по текущей компании.
</Info>

## Справочник каналов уведомлений

Канал — это способ доставки уведомления сотруднику. В системе их три:

| Канал | Что это |
|---|---|
| Веб (Ably) | доставка в реальном времени в веб-версию/личный кабинет через сервис Ably |
| Push (мобильное приложение) | push-уведомление в мобильное приложение на телефоне сотрудника |
| Telegram-бот | сообщение через единый Telegram-бот всей системы (один общий бот на всю платформу, а не отдельный бот у каждой компании) — работает только если сотрудник сам привязал свой Telegram-аккаунт к этому боту |

Фактическая доставка по каналу дополнительно зависит от того, включён ли этот канал в списке разрешённых каналов самого события. Для веб-канала и для Telegram-канала есть ещё одно условие: канал должен быть технически настроен на уровне всей системы в целом — одинаково для всех компаний (единые для всей платформы ключи сервиса Ably для веб-канала и единый токен Telegram-бота для Telegram-канала); если такая общесистемная настройка отсутствует, канал не работает вообще ни для одной компании. Для push-канала подобной общесистемной технической проверки в логике рассылки нет. Персональная настройка из этого раздела — последний фильтр в цепочке: даже если канал технически доступен и разрешён событием, конкретный сотрудник не получит уведомление, если сам отключил для себя эту тему по этому каналу.

## Справочник тем уведомлений

Тема — это категория события, по которой сотрудник включает или выключает уведомления независимо от канала. Всего в справочнике 27 тем, сгруппированных по бизнес-областям.

### Общая тема

| Тема | Когда используется |
|---|---|
| По умолчанию | служебная «тема-заглушка»: применяется к событиям, для которых не задана более узкая тема (например, к части общих уведомлений по автопарку) |

### Заявки

| Тема | Когда используется |
|---|---|
| Заявка забронирована | заявка на аренду переведена в статус бронирования |
| Заявка завершена | заявка на аренду завершена |
| Просрочка по заявке | заявка превысила согласованное время использования |
| Изменение статуса оплаты заявки | у заявки изменился статус оплаты |

### Транзакции

| Тема | Когда используется |
|---|---|
| Создана транзакция | создана денежная транзакция (в том числе при поступлении онлайн-оплаты) |
| Возврат по транзакции | по транзакции оформлен возврат |
| Удаление транзакции | транзакция удалена |

### Клиенты

| Тема | Когда используется |
|---|---|
| Превышен лимит задолженности клиента | долг клиента превысил установленный лимит |
| Клиент добавлен в чёрный список | клиента внесли в чёрный список |

### Документы

| Тема | Когда используется |
|---|---|
| Документ создан | создан новый документ |
| Документ подписан | документ подписан |

### Инвентаризация

| Тема | Когда используется |
|---|---|
| Инвентаризация создана | создана инвентаризация |
| Чек-лист инвентаризации | событие по чек-листу инвентаризации |

### Доставка

| Тема | Когда используется |
|---|---|
| Доставка назначена | на доставку назначен исполнитель |
| Изменение статуса доставки | у доставки изменился статус |
| Доставка завершена | доставка завершена |
| Доставка отменена | доставка отменена |

### Техническое обслуживание

| Тема | Когда используется |
|---|---|
| Наступил срок ТО | наступил плановый срок технического обслуживания |
| ТО назначено | техническое обслуживание назначено исполнителю |
| ТО завершено | техническое обслуживание завершено |

### Инвентарь

| Тема | Когда используется |
|---|---|
| Единица инвентаря сломана | единица инвентаря помечена как сломанная |

### SMS

| Тема | Когда используется |
|---|---|
| Низкий баланс SMS | баланс SMS-рассылок компании опустился ниже порога |
| Ошибка отправки SMS | SMS не удалось отправить |
| Возврат средств за SMS | средства за недоставленное SMS возвращены |

### Внешние интеграции

| Тема | Когда используется |
|---|---|
| Создан штраф OkAuto | из интеграции с OkAuto поступил штраф |
| Получено сообщение Wazzup | через интеграцию Wazzup получено новое сообщение от клиента |

<Note>
Часть тем из справочника зарезервирована на будущее: переключатель для них уже присутствует в персональных настройках, но ни одно событие в системе пока их не порождает, поэтому включение/выключение таких тем на данный момент ни на что не влияет.
</Note>

## Матрица «канал × тема» и значения по умолчанию

Полный набор персональных настроек одного сотрудника — это все сочетания трёх каналов и двадцати семи тем, то есть 81 запись. По умолчанию для нового сотрудника (и для новой пары «канал/тема», появившейся в системе) значение флага «Включено» — **включено**: сотрудники подписаны на все темы по всем каналам, если не отключили что-то вручную.

Матрица не создаётся заранее одним действием — она **доукомплектовывается лениво**, при первом обращении сотрудника к списку своих настроек: система сравнивает количество уже сохранённых у сотрудника записей с полным размером матрицы (81), и если оно не совпадает с этим числом (в любую сторону — как при нехватке, так и при избытке), недостающие сочетания «канал/тема» создаются автоматически со значением «включено». Уже существующие записи при этом не трогаются — их значения (в том числе выключенные вручную) сохраняются.

## Чтение настроек

Эндпоинт: `GET /v1/notifications/access/`. Доступен любому авторизованному пользователю, работает только с его собственными настройками в рамках текущей компании. Ответ не постраничный — всегда возвращается плоский список (в норме — все 81 запись).

Каждый элемент ответа содержит:

| Поле | Тип | Назначение |
|---|---|---|
| Идентификатор записи | число | используется для последующих операций и сверки |
| Канал уведомления | список | один из трёх каналов |
| Тема уведомления | список | одна из тем справочника |
| Включено | флаг | текущее значение персональной настройки |

Компания и идентификатор сотрудника в ответе не показываются — они и так однозначно определяются текущим авторизованным пользователем и текущей компанией.

Именно при обращении к этому эндпоинту происходит доукомплектование матрицы, описанное выше: если у сотрудника ещё не было ни одной записи (например, это его первый визит в раздел настроек уведомлений) или количество его записей просто не совпадает с полным набором из 81 сочетания, недостающие сочетания «канал/тема» создаются со значением «включено» непосредственно перед формированием ответа.

## Массовое сохранение настроек

Тот же адрес, метод записи: `POST /v1/notifications/access/`. Тело запроса — объект с одним вложенным списком настроек; каждый элемент этого списка описывает пару «канал/тема» и желаемое значение флага «Включено».

| Поле элемента | Тип | Назначение |
|---|---|---|
| Канал уведомления | список | канал, для которого меняется настройка |
| Тема уведомления | список | тема, для которой меняется настройка |
| Включено | флаг | новое значение флага для этой пары |

Логика сохранения:

1. Для каждой присланной пары «канал/тема» система проверяет, есть ли у сотрудника уже сохранённая запись с таким сочетанием (в рамках текущей компании).
2. Если запись уже существует — обновляется только флаг «Включено», остальные поля не трогаются.
3. Если записи ещё нет — создаётся новая запись сразу с присланным значением флага.
4. Все изменения в рамках одного запроса выполняются как единая атомарная операция: либо применяются целиком, либо не применяются вовсе.

<Tip>
Присылать нужно только те пары «канал/тема», которые сотрудник действительно изменил — отправлять полный набор из 81 записи на каждое сохранение не обязательно.
</Tip>

Эндпоинт всегда работает только с настройками текущего авторизованного пользователя — возможности одним запросом изменить настройки уведомлений другого сотрудника (например, руководителем — за подчинённого) в этом API нет.

## Как это используется в рассылке уведомлений

Когда в компании происходит событие с определённой темой, система формирует список получателей для рассылки. Кандидатами становятся штатные сотрудники компании; из них для каждого канала (веб, push, Telegram) отбираются те, у кого по данной теме и данному каналу в персональных настройках стоит значение «включено». Если у события дополнительно указан ограниченный список получателей, итоговый список пересекается ещё и с ним.

Уведомление по веб-каналу и по Telegram-каналу уходит только при одновременном выполнении трёх условий:

- канал входит в список каналов, разрешённых для конкретного события;
- канал технически настроен на уровне всей системы в целом, одинаково для всех компаний (для веб-канала подключён сервис Ably, для Telegram-канала работает единый Telegram-бот системы);
- у конкретного сотрудника этот канал и эта тема включены в персональных настройках.

Для push-канала действуют только первое и третье условия — отдельной общесистемной технической проверки для push в текущей логике рассылки нет.

Таким образом, справочники каналов и тем из этого раздела и персональные настройки «Доступ к уведомлениям» — это последний, персональный уровень фильтрации получателей: система сама решает, кому в принципе может прийти уведомление, а этот раздел решает, хочет ли конкретный сотрудник получать именно эту тему именно этим способом.

## Подводные камни

<Warning>
- **Общая область данных для всех компаний.** Справочник персональных настроек уведомлений хранится в общей, единой для всех компаний области данных — разделение обеспечивается только полем «Компания» в каждой записи. Любая выборка по этому справочнику обязана явно фильтроваться по текущей компании, иначе возможна утечка данных между компаниями.
- **Новая тема не работает «из коробки».** Если новая тема уведомлений появляется в справочнике уже после того, как сотрудник открывал раздел настроек, запись для неё не создаётся автоматически — она появляется лениво только при следующем обращении сотрудника к списку своих настроек. До этого момента сотрудник не попадёт в получатели рассылки по этой теме, даже если по замыслу она должна быть включена по умолчанию.
- **Список получателей рассылки может выходить за пределы компании.** Запрос, который формирует список кандидатов на рассылку среди штатных сотрудников, сам не гарантированно ограничен текущей компанией. В получатели теоретически может попасть пользователь, чей штатный доступ оформлен в другой компании, — если у него при этом есть личная запись настроек уведомлений в текущей компании (например, он раньше был её сотрудником или работает в нескольких компаниях сразу).
</Warning>

- Проверка «количество сохранённых настроек не совпадает с полным набором» реагирует и на нехватку, и на избыток записей. Если тема или канал когда-нибудь будут убраны из справочника, у пользователей с уже сохранёнными «устаревшими» записями это условие будет срабатывать при каждом обращении к настройкам, вызывая лишнюю попытку доукомплектования, хотя добавлять там уже нечего.
- Ответ на массовое сохранение настроек возвращает клиенту ровно те данные, что он отправил, а не фактическое состояние записей в базе — например, у только что созданных пар «канал/тема» в ответе не будет их идентификатора. Чтобы получить актуальные данные, нужно заново запросить список настроек.
- При одновременной отправке двух запросов на сохранение одной и той же новой пары «канал/тема» возможна гонка: оба запроса могут не увидеть эту пару как существующую и попытаться создать её параллельно, из-за чего один из запросов завершится технической ошибкой базы данных вместо аккуратного сообщения валидации.

<Info>
Из 27 тем справочника события системы на данный момент реально порождают только 14. Остальные 13 (например, «Заявка забронирована», «Заявка завершена», «Изменение статуса оплаты заявки», обе темы по клиентам, «Документ создан», обе темы по инвентаризации, «Изменение статуса доставки», «Доставка завершена», «Наступил срок ТО», «ТО завершено», «Единица инвентаря сломана») доступны для переключения в настройках, но пока ни на что не влияют.
</Info>
