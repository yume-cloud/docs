Полный перечень полей — в [глоссарии Telegram-уведомлений](/ru/logic/notifications/telegram-glossary).

## Обзор

Эта страница описывает часть модуля «Уведомления», отвечающую за личный Telegram-канал сотрудника: как сотрудник привязывает свой личный чат с Telegram-ботом Yume к своему аккаунту, как он может отвязать его обратно, и как система технически отправляет текстовые сообщения через Telegram Bot API — как персональные, так и общие.

<Info>
Привязка выполняется в два этапа и в двух разных интерфейсах: сотрудник получает код подтверждения **внутри Telegram**, а вводит его **на сайте/в приложении Yume**. Это единственный способ связать конкретный Telegram-чат с конкретным сотрудником конкретной компании.
</Info>

## Модель данных

Каждая привязка Telegram-чата к сотруднику хранится как отдельная запись Telegram-пользователя. Таблица общая для всех компаний: одна и та же запись со временем может «путешествовать» между состояниями — от только что открытого чата с ботом до подтверждённой привязки к конкретному сотруднику.

| Поле | Тип | Назначение |
| --- | --- | --- |
| Компания | связь | Компания, к которой привязан чат. Пустая, пока привязка не подтверждена. |
| ID пользователя | число | Сотрудник, к которому привязан чат. Пустой, пока привязка не подтверждена. |
| ID чата Telegram | число | Уникальный идентификатор личного чата пользователя с ботом. Уникален во всей системе. |
| Имя пользователя в Telegram | текст | Ник (`@username`) из профиля Telegram на момент последнего обращения к боту. |
| Имя | текст | Имя из профиля Telegram. |
| Фамилия | текст | Фамилия из профиля Telegram. |
| Подтверждена | флаг | `Да`, если привязка подтверждена вводом верного кода; `Нет` — временная, ещё не подтверждённая запись. |
| Код подтверждения | текст | Одноразовый код, который нужно ввести на сайте. Обнуляется сразу после успешного подтверждения. |

<Note>
Идентификатор чата Telegram уникален для всей системы, а не в рамках одной компании. Это значит, что один и тот же Telegram-аккаунт человека может быть подтверждённо привязан только к одной паре «компания + сотрудник» одновременно — привязать его сразу ко второй компании нельзя, не отвязав от первой.
</Note>

Кроме того, для пары «компания + сотрудник» может существовать только одна подтверждённая привязка — то есть у одного сотрудника в одной компании не может быть двух одновременно привязанных Telegram-чатов.

## Как сотрудник получает код подтверждения

Код подтверждения выдаётся не на сайте, а внутри Telegram, при обращении к боту:

1. Сотрудник открывает бота Yume в Telegram и отправляет стартовую команду.
2. Система ищет запись Telegram-пользователя по идентификатору чата; если её ещё нет — создаёт новую, пустую (без компании и без сотрудника).
3. Если эта запись уже подтверждена (чат уже привязан к какому-то сотруднику), бот сообщает, что аккаунт уже привязан, и предлагает воспользоваться отдельной командой отключения, если нужно перепривязать чат.
4. Если запись ещё не подтверждена, бот генерирует случайный шестизначный код подтверждения, сохраняет его в записи и показывает сотруднику текстом прямо в чате с инструкцией ввести этот код в настройках профиля на сайте.

<Warning>
Код подтверждения не имеет срока действия — он не привязан ко времени выдачи и не сбрасывается автоматически. Он остаётся действительным до тех пор, пока не будет использован для привязки или пока сотрудник заново не запросит код той же командой (тогда старый код в этой записи перезаписывается новым).
</Warning>

## Привязка аккаунта

Привязка выполняется на стороне сайта/приложения через отдельный запрос, в который сотрудник передаёт полученный в Telegram код.

Логика обработки запроса привязки на сервере:

1. Код подтверждения обязателен и должен состоять ровно из шести символов — иное значение отклоняется ещё до основной обработки.
2. Система ищет **среди всех компаний** (без ограничения текущей компанией) неподтверждённую запись Telegram-пользователя с введённым кодом. Если совпадение не найдено — запрос завершается ошибкой «не найдено».
3. Если совпадение найдено, из найденной записи забираются идентификатор чата, ник, имя и фамилия, после чего сама временная (неподтверждённая) запись удаляется.
4. По идентификатору чата создаётся (или обновляется, если запись с таким чатом почему-то уже существует) итоговая запись Telegram-пользователя: в неё проставляются текущая компания и текущий авторизованный сотрудник, копируются ник/имя/фамилия, привязка помечается подтверждённой, а код подтверждения обнуляется.
5. Сотруднику в тот же Telegram-чат отправляется сообщение об успешной привязке профиля — асинхронно, фоновой задачей.

<Warning>
Поиск кода подтверждения не ограничен текущей компанией сотрудника — проверяется совпадение только по самому коду и по статусу «не подтверждено». Формально это означает, что привязать конкретный Telegram-чат к своему аккаунту может любой авторизованный сотрудник любой компании, если он узнал шестизначный код, — вне зависимости от того, для какой компании этот код изначально предназначался.
</Warning>

Тот же адрес, что используется для привязки, поддерживает и запрос текущего статуса: система ищет привязку текущего сотрудника в текущей компании и возвращает его ник в Telegram. Если привязки нет — возвращается ошибка «не найдено», а не пустой/отрицательный ответ.

## Отвязка аккаунта

Отвязать личный Telegram-канал можно двумя независимыми путями:

- **С сайта/из приложения**: отдельный запрос отвязки ищет привязку текущего авторизованного сотрудника в текущей компании и удаляет её целиком. Если привязки нет — запрос завершается ошибкой «не найдено».
- **Из самого Telegram**: сотрудник может отправить боту команду отключения прямо в чате; бот находит запись по идентификатору чата (без какой-либо дополнительной проверки, что запрос идёт именно от владельца аккаунта в приложении Yume — фактически доверие строится на том, что доступ к самому Telegram-чату уже есть только у его владельца) и удаляет её, если она существует.

После отвязки любым из способов запись Telegram-пользователя исчезает полностью: чтобы снова получать уведомления, нужно заново пройти привязку с новым кодом.

## Отправка уведомлений через Telegram Bot API

Отправка Telegram-уведомления — это фоновая задача, единая точка отправки любого текстового сообщения в Telegram для всей системы (не только для сценария привязки/отвязки, но и для прочих модулей, которым нужно уведомить компанию или конкретного сотрудника).

| Параметр | Назначение |
| --- | --- |
| Текст сообщения | Отправляемый текст. Поддерживает HTML-разметку Telegram (например, жирный текст, ссылки) — режим разбора текста жёстко зафиксирован как HTML. |
| Токен бота | Какой бот отправляет сообщение. Если не указан явно — используется основной бот Yume. |
| ID получателя | Личный чат сотрудника или канал компании. Если не указан явно — используется общий канал уведомлений компании. |

Механика отправки простая: задача формирует запрос к методу отправки сообщений Telegram Bot API и передаёт в нём получателя, текст и режим разметки, после чего возвращает код ответа Telegram. Задача выполняется в отдельной очереди сообщений с большим предельным временем выполнения (до одного часа) — на практике сам вызов занимает доли секунды, большой лимит — это запас на случай задержек соединения.

<Warning>
Задача не проверяет код ответа Telegram Bot API на ошибку и не логирует неуспешные попытки — она просто возвращает код ответа вызвавшему коду. Если сообщение не доставлено (например, сотрудник заблокировал бота, чат был удалён, или текст содержит некорректную HTML-разметку), это никак не отражается на записи привязки: она остаётся помеченной как подтверждённая, хотя фактически перестала получать сообщения.
</Warning>

## Как это используется в модуле «Уведомления»

Персональный Telegram-канал — один из трёх каналов доставки события (наряду с push-уведомлением на телефон и лентой в веб-интерфейсе). Когда в компании происходит событие, для которого у сотрудника включён канал доставки в Telegram (в его персональных настройках уведомлений), система ищет подтверждённую привязку Telegram-пользователя именно для пары «эта компания + этот сотрудник» и, если она есть, отправляет сотруднику текст события в его личный чат с ботом — с уточнённым текстом и прямой ссылкой на соответствующий объект (заявку, задачу по лиду, документ, задачу техобслуживания) в веб-версии Yume.

<Note>
Если у сотрудника нет подтверждённой привязки, событие в Telegram ему просто не отправляется — без ошибки и без запасного канала доставки. Другие каналы (push, веб-лента), если они включены, продолжают работать независимо.
</Note>

Отправка Telegram-уведомления как фоновая задача переиспользуется и другими модулями системы (например, для оповещений по счетам, оплатам, окончанию смен) — все они используют тот же механизм отправки сообщений в Telegram, отличаясь лишь текстом, ботом и получателем.

## Подводные камни

<Warning>
- **Поиск кода подтверждения не ограничен компанией** — совпадение по коду и статусу «не подтверждено» ищется среди всех компаний, поэтому теоретически привязать чужой Telegram-чат к своему аккаунту может сотрудник любой компании, узнавший код.
- **Код подтверждения бессрочный** — он не хранит момент выдачи и остаётся рабочим, пока не будет использован или перегенерирован повторной командой в боте.
- **Отправка сообщений не проверяется на успешность** — фоновая задача не смотрит на ответ Telegram и не логирует неудачи; при недоставке (блокировка бота, удалённый чат, некорректная разметка текста) привязка остаётся помеченной как подтверждённая, хотя сообщения фактически не доходят.
</Warning>

- Поиск неподтверждённой записи по коду не сортируется явно по времени выдачи: при случайном совпадении кодов у двух записей выбирается более поздняя по порядку создания, а не первая по времени.
- Идентификатор чата Telegram уникален во всей системе, а не в рамках отдельной компании — один и тот же Telegram-аккаунт нельзя подтверждённо привязать сразу к двум компаниям, сначала нужно отвязать текущую привязку.
- Команда отключения бота удаляет привязку по идентификатору чата без проверки, что запрос исходит именно от владельца аккаунта в Yume — это отдельный путь отвязки, минующий авторизацию и проверку компании, характерные для веб-запроса.
- У задачи отправки нет автоматической повторной попытки при сбое, несмотря на большой запас времени на выполнение — временный сетевой сбой не приводит к повторной отправке.
- Режим разметки текста жёстко зафиксирован как HTML, но сама задача не экранирует спецсимволы — за корректность разметки отвечает вызывающий код, иначе сообщение может быть отклонено или отображено неверно.
- Запрос текущего статуса привязки при её отсутствии возвращает ошибку «не найдено», а не пустой или отрицательный ответ — это нужно учитывать в клиентских приложениях.
