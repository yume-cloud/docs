## Модель данных

### Уведомление — общая запись события

Каждое событие в компании (новая заявка, изменение статуса, новая задача по сделке, новый документ, обслуживание техники и т. п.) превращается в одну запись «Уведомление». Эта запись — единственный источник правды и для общей ленты, и для рассылки по каналам: как только запись сохраняется, автоматически запускается логика рассылки (описана ниже).

| Поле | Тип | Назначение |
|---|---|---|
| **Идентификация** | | |
| ID | число | Первичный идентификатор записи; используется в ссылках и передаётся в пуш- и веб-уведомлении как идентификатор события. |
| Компания | связь | Компания (тенант), к которой относится уведомление. Лента и рассылка всегда работают в рамках одной компании. |
| **Источник события** | | |
| Тип объекта-источника | текст | Внутренний код модели-источника события (например, «это заявка», «это задача по сделке», «это документ»). Управляет текстом ссылки при отправке в Telegram и служит ключом для поиска/обновления уведомления при повторных событиях по тому же объекту. |
| ID объекта-источника | число | Идентификатор конкретной записи-источника (например, ID заявки). Вместе с типом объекта-источника образует пару, по которой система ищет уже существующее уведомление для обновления. |
| **Содержание** | | |
| Текст | текст | Основной текст уведомления. Отображается в ленте и рассылается во все выбранные каналы. |
| Тип | список (Информация / Предупреждение / Тревога) | Отметка важности. <Info>Тип не отображается в самой ленте — ответ API списка уведомлений его не содержит. Он передаётся внутрь пуш-уведомления и веб-уведомления (для интеграции реального времени), чтобы клиентское приложение могло визуально выделить более важные события.</Info> |
| Тема | категория события | Категория, к которой относится событие (заявки, оплаты и транзакции, работа с клиентами, документы, обслуживание техники, SMS-рассылки и т. д.). По умолчанию используется общая тема. Тема сверяется с персональными настройками уведомлений сотрудника — именно она решает, хочет ли конкретный человек получать события такого рода. |
| Каналы рассылки | список каналов (Telegram-бот / push / веб) | Через какие каналы вообще разрешено рассылать это конкретное уведомление. Реальная отправка дополнительно сужается персональными настройками получателя — то есть канал должен быть и разрешён на уровне события, и включён у конкретного сотрудника. |
| Явные получатели | список сотрудников | Необязательное поле. Если заполнено — рассылка по каналам сужается только до перечисленных людей (при условии, что они всё ещё входят в круг штатных сотрудников, см. шаг 2 ниже). Если пусто — по каналам адресуется любой штатный сотрудник компании, у кого включена соответствующая тема. |
| Доп. данные | произвольные данные | Дополнительные данные события: используются для построения диплинка (например, ссылка на сделку для задачи) и передаются целиком в пуш- и веб-уведомление. |
| **Даты** | | |
| Создано | дата/время | Момент создания записи. |
| Обновлено | дата/время | Момент последнего изменения. По этому полю фактически сортируется лента (см. ниже), а не по дате создания — но см. предупреждение ниже о том, что при обновлении уведомления по дедупликации это поле фактически не пересчитывается. |

<Info>У модели также исторически сохранилось одно поле-«владелец» (сотрудник, на которого якобы оформлено уведомление). Ни один из текущих способов создания уведомлений его не заполняет, поэтому на практике оно всегда пустое — однако оно всё равно присутствует в ответе API ленты отдельным полем. Логика рассылки по каналам это поле не использует и ориентируется на компанию, тип/ID объекта-источника и явных получателей, описанных выше.</Info>

### Отметка пользователя об уведомлении — персональный статус

Общая лента одна на компанию, но у каждого сотрудника — свой персональный статус прочтения по каждому уведомлению. Этот статус хранится не как поле самого уведомления, а как отдельная запись «Отметка пользователя об уведомлении», привязанная к паре компания + сотрудник + уведомление.

| Состояние | Что видит сотрудник | Как это устроено |
|---|---|---|
| Непрочитано | Уведомление выделено как новое | Персональной отметки для этого сотрудника по этому уведомлению вообще не существует |
| Прочитано | Уведомление открыто/подтверждено, но остаётся в активном списке | Отметка существует, поле «в архиве» = нет |
| В архиве | Уведомление скрыто из активного списка | Отметка существует, поле «в архиве» = да |

На одного сотрудника и одно уведомление может существовать только одна такая отметка — повторно создать вторую отметку того же сотрудника по тому же уведомлению система не позволит.

## Как уведомление создаётся и обновляется

Новые записи в общей ленте создают фоновые задачи, которые запускаются из бизнес-логики других модулей (заявки, сделки, документы, обслуживание техники и т. д.), а не сам пользователь напрямую. Есть два сценария создания.

### Простое создание

Каждый вызов создаёт новую отдельную запись уведомления — даже если по тому же объекту-источнику уже есть более ранние записи. Такой вариант используется, когда каждое событие по объекту действительно должно быть отдельной строкой в ленте.

### Создание или обновление с дедупликацией

Этот сценарий сначала ищет уже существующее уведомление с тем же типом и ID объекта-источника в рамках компании:

- **Если такое уведомление уже есть** — у него обновляются только текст, дополнительные данные и явные получатели. При этом **удаляются все персональные отметки прочтения/архива** всех сотрудников по этому уведомлению — то есть ранее прочитавшие или заархивировавшие его сотрудники увидят его как новое непрочитанное событие снова.
- **Если такого уведомления ещё нет** — создаётся новая запись, как при простом создании.

<Warning>При обновлении существующей записи тема и разрешённые каналы рассылки, переданные в этот вызов, **не применяются** — сохраняются тема и каналы, заданные при первоначальном создании записи. Кроме того, это обновление выполняется прямой массовой записью полей в базу, а не через обычное сохранение записи. Из-за этого: во-первых, повторной рассылки по каналам (push/Telegram/веб) на этом шаге **не происходит** — новые уведомления по каналам уходят только один раз, в момент первого создания записи; во-вторых, дата изменения записи **не сдвигается на текущий момент** — вопреки интуитивному ожиданию, повторное событие по тому же объекту-источнику не поднимает более старую запись наверх ленты.</Warning>

## Кто получает рассылку и по каким каналам

Сразу после того, как в базе появляется **новая** запись уведомления (то есть именно вставка, а не последующее обновление того же объекта-источника), автоматически запускается логика рассылки. Она выполняется синхронно в момент сохранения и определяет получателей и каналы по следующим шагам.

### Шаг 1. Проверка контекста

Если на момент сохранения не удаётся определить компанию в текущем контексте выполнения (например, фоновая операция выполняется вне контекста конкретной компании, хотя сама запись сохраняется с явно указанной компанией), рассылка просто не выполняется — запись в ленте всё равно создаётся, но никому ничего не отправляется.

### Шаг 2. Круг потенциальных получателей

Сначала собирается список сотрудников компании — точнее, тех из них, у кого в компании включена роль штатного персонала, а не буквально всех, кто когда-либо был привязан к компании (подробнее см. примечание ниже об особенностях этой выборки). Этот список на короткое время — на несколько секунд — кэшируется, чтобы не пересчитывать его при каждом событии, если события идут пачкой. Если у уведомления заполнено поле «Явные получатели», список дополнительно сужается только до этих людей — остальные сотрудники, даже с включённой темой, в этом случае рассылку не получат.

### Шаг 3. Персональные настройки решают доступность каждого канала

Для оставшегося круга людей система смотрит их персональные настройки уведомлений компании: включена ли у человека именно эта тема события и именно этот канал (push, веб, Telegram). Только пересечение «канал разрешён у события» + «канал и тема включены у человека» даёт реального получателя по каждому конкретному каналу — то есть один и тот же человек может, например, получить событие в push, но не получить его в Telegram, если так настроено у него лично.

### Шаг 4. Отправка по каждому разрешённому каналу

- **Веб (реального времени)** — отправляется только если для проекта в принципе настроена интеграция веб-уведомлений; если она не настроена, отправка по этому каналу тихо пропускается (в ленте уведомление всё равно появится при следующем обращении к списку).
- **Push** — отправляется на все активные мобильные устройства получателей; если у человека нет ни одного активного устройства, push просто не доставляется, без ошибки.
- **Telegram-бот** — отправляется только тем получателям, кто лично привязал Telegram-чат к своему аккаунту в этой компании, и только если для проекта в принципе настроен Telegram-бот. Текст и ссылка в сообщении формируются в зависимости от типа события: для заявки — ссылка на страницу заявки, для задачи по сделке — ссылка на саму сделку (сообщение начинается с пометки «Новая задача»), для заявки на техобслуживание — ссылка на карточку обслуживания (с пометкой «Новая задача ТОО»), для документа — ссылка на документ. <Warning>Для события «задача по сделке» сообщение в Telegram отправляется, только если в дополнительных данных события указана сама сделка; если такой привязки нет — Telegram-сообщение не формируется вовсе, при этом push и веб-уведомление по этому же событию всё равно уходят как обычно.</Warning>

## Лента уведомлений (список)

<Warning>Лента показывает **все** уведомления компании любому авторизованному сотруднику — независимо от того, был ли он в списке явных получателей события и включена ли у него соответствующая тема/канал. Поле «Явные получатели» и персональные настройки уведомлений влияют только на то, кому реально придёт push/Telegram/веб-сообщение, но не на то, что появится в списке ленты при её открытии.</Warning>

Список ленты для текущего сотрудника всегда ограничен его компанией и дополнительно помечает каждую запись двумя признаками, которых нет в самой модели уведомления, а которые вычисляются на лету при каждом запросе: прочитано ли уведомление этим сотрудником и находится ли оно у него в архиве.

### Сортировка

Лента сортируется по дате **обновления**, от новых к старым, а не по дате создания. На практике для подавляющего большинства уведомлений эти две даты совпадают: единственный сценарий, который в теории мог бы сдвигать дату изменения уже существующей записи, — «создание или обновление с дедупликацией», — на деле выполняет прямую массовую запись полей в базу и **не** пересчитывает дату изменения (см. предупреждение выше). Поэтому повторное событие по тому же объекту-источнику не поднимает более старую запись наверх ленты — она остаётся на том месте, которое соответствует моменту её первоначального создания.

### Фильтрация ленты

По ленте можно фильтровать:

| Поле | Тип | Назначение |
|---|---|---|
| Тип объекта-источника | список значений через запятую | Оставить только уведомления по определённым типам событий (например, только по заявкам). |
| В архиве | да/нет | Показать только заархивированные либо только незаархивированные уведомления текущего сотрудника. |
| Прочитано | да/нет | Показать только прочитанные либо только непрочитанные уведомления текущего сотрудника. |

Дополнительно ленту можно искать по тексту уведомления.

### Счётчик непрочитанных

Показывает количество уведомлений компании, которые для текущего сотрудника одновременно непрочитаны **и** не находятся в архиве. Заархивированные уведомления в счётчик не попадают, даже если формально они ни разу не были отмечены прочитанными до архивации.

## Отметить прочитанным

Действие принимает либо список конкретных ID уведомлений, либо признак «прочитать всё».

- **По списку ID** — для каждого указанного уведомления (в рамках своей компании) создаётся персональная отметка «прочитано» для текущего сотрудника, но только если у него ещё вообще нет никакой отметки по этому уведомлению. Если уведомление уже отмечено прочитанным или уже заархивировано этим же сотрудником — повторный вызов ничего не меняет (заархивированное уведомление не «распечатывается» обратно).
- **«Прочитать всё»** — то же самое, но применяется сразу ко всем уведомлениям компании, у которых у текущего сотрудника ещё нет персональной отметки, независимо от того, какие фильтры сейчас применены в интерфейсе ленты.

В обоих случаях действие затрагивает только личные отметки вызвавшего его сотрудника и не влияет на статус прочтения этого же уведомления у других сотрудников.

## Архивировать

Действие тоже принимает либо список конкретных ID, либо признак «архивировать всё», но устроено иначе, чем отметка прочитанным.

- **«Архивировать всё»** — сначала для текущего сотрудника создаются недостающие персональные отметки по всем уведомлениям компании (то есть все непрочитанные становятся прочитанными), а затем **все** его личные, ещё не заархивированные отметки переводятся в архив. Действие полностью ограничено вызвавшим его сотрудником.
- **По списку ID** — переводятся в архив уже существующие персональные отметки «прочитано, не в архиве» с указанными ID уведомлений. Если по конкретному ID у сотрудника ещё вообще нет отметки (уведомление всё ещё непрочитано) — точечное архивирование для него не создаёт отметку и не переводит уведомление в архив, оно просто остаётся непрочитанным.

<Warning>В отличие от «Архивировать всё» и от отметки прочитанным, точечное архивирование по списку ID **не ограничено вызвавшим его сотрудником**: оно переводит в архив персональные отметки «прочитано, не в архиве» у всех сотрудников компании, у кого такая отметка уже была по перечисленным уведомлениям, а не только у того, кто вызвал действие.</Warning>

<Tip>Из-за этой особенности точечное архивирование конкретных уведомлений предсказуемо работает только для собственных, уже прочитанных уведомлений сотрудника; для «архивировать разом всё, что вижу» предназначено именно действие «Архивировать всё».</Tip>

## Подводные камни

<Warning>
- Лента показывает все уведомления компании абсолютно каждому сотруднику — вне зависимости от того, назван ли он получателем события и включена ли у него нужная тема или канал. Явные получатели и персональные настройки влияют только на реальную рассылку по push, Telegram и веб-каналу, а не на то, что видно в списке.
- Точечное архивирование по конкретным уведомлениям не ограничено вызвавшим его сотрудником: оно переводит в архив уже прочитанные отметки любых сотрудников компании, у кого они есть по указанным уведомлениям, а не только у того, кто выполнил действие.
- При повторном событии по тому же объекту-источнику система обновляет только текст, дополнительные данные и получателей — тема и разрешённые каналы, заданные при первом создании, повторным вызовом не меняются.
- Обновление существующего уведомления по тому же объекту-источнику не вызывает повторную рассылку по каналам и не поднимает запись наверх ленты: дата изменения при этом не пересчитывается, а по каналам событие рассылается только один раз, в момент первого создания записи.
</Warning>

- Точечное архивирование работает только с уже прочитанными и не заархивированными отметками: если сотрудник ещё не открывал уведомление, оно остаётся непрочитанным, и точечное архивирование его не тронет.
- При обновлении уведомления по тому же объекту-источнику удаляются личные отметки о прочтении и архивации всех сотрудников по этой записи — ранее прочитавшие или заархивировавшие её сотрудники увидят уведомление снова как новое непрочитанное.
- Сообщение в Telegram по задаче сделки формируется, только когда в данных события есть ссылка на саму сделку; push- и веб-уведомление по этому же событию уходят в любом случае.
- Круг получателей рассылки — это сотрудники с включённой ролью штатного персонала, а не любой, кто когда-либо был связан с компанией; список ненадолго кэшируется, из-за чего сразу после найма или увольнения сотрудника рассылка может на несколько секунд отставать от актуального состава.
- Если сотрудник явно назван получателем уведомления, но не входит в круг штатного персонала компании, рассылка по каналам ему всё равно не придёт.
- Поле-«владелец» уведомления сейчас никогда не заполняется при создании, но всё равно присутствует в ответе ленты отдельным полем.
- Отметка важности уведомления не отображается в самой ленте — она передаётся только внутрь push- и веб-уведомления, чтобы визуально выделить более важные события.
- Пара «тип события + идентификатор объекта-источника», по которой ищутся уведомления для обновления, не защищена ограничением уникальности в базе данных — при одновременных вызовах теоретически возможно появление дублирующих записей и двойная рассылка.
- Массовые действия «Прочитать всё» и «Архивировать всё» обрабатывают все уведомления компании независимо от того, какие фильтры сейчас применены в интерфейсе ленты.
