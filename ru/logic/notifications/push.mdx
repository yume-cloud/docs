Полный перечень полей — в [глоссарии push-уведомлений](/ru/logic/notifications/push-glossary).

## Обзор

Push-уведомления — один из трёх каналов доставки событий единого шлюза уведомлений Yume (наряду с Telegram-ботом и веб-каналом). Страница описывает, как мобильное или веб-приложение регистрирует и снимает с регистрации push-токен устройства, как система решает, кому и что отправлять, и как сервер разговаривает с сервисом push-доставки Expo, на котором построена мобильная доставка Yume.

Хранилище push-токенов — общее для всех компаний: запись ссылается на компанию через отдельное поле, но это поле не обязано быть заполнено. Это важно держать в голове: некоторые операции ниже по умолчанию работают в масштабе всей системы, а не только внутри одной компании — это отмечено отдельно там, где это существенно.

## Модель данных: Push-токен устройства

Каждая строка — это один push-токен одного устройства одного сотрудника в одной компании.

| Поле | Тип | Назначение |
|---|---|---|
| Компания | связь | Компания, которой принадлежит регистрация устройства. Может быть не заполнена. |
| ID пользователя | число | Сотрудник — владелец токена. |
| Push-токен | текст | Сам токен устройства, выданный сервисом push-доставки. |
| ID устройства | текст | Отличает одно физическое устройство от другого. На уровне базы данных может быть пустым, но при регистрации через API это поле должно присутствовать в теле запроса (см. предупреждение ниже). |
| Тип устройства | список (iOS / Android / Web) | Платформа устройства. На уровне базы данных по умолчанию — iOS, но при регистрации через API это поле обязательно должно присутствовать в теле запроса (см. предупреждение ниже). |
| Активен | флаг | Определяет, получит ли устройство push-уведомления. |
| Последнее использование | дата/время | Обновляется автоматически при каждом полном сохранении записи (регистрация нового устройства или повторная регистрация существующего). |
| Дата создания | дата/время | Момент первой регистрации именно этой комбинации компания + сотрудник + токен + устройство + платформа. |
| Дата обновления | дата/время | Также обновляется автоматически при полном сохранении записи. |

### Уникальность записи и поиск

Одна и та же комбинация «компания + сотрудник + токен + ID устройства + тип устройства» существует только в одном экземпляре — повторная регистрация с теми же параметрами обновляет существующую запись, а не создаёт дубликат.

Для быстрого поиска предусмотрено два индекса: по паре «сотрудник + активность» (в первую очередь используется при рассылке push конкретным сотрудникам, где фильтруются сразу оба поля; частично помогает и при получении списка своих устройств, где фильтр идёт только по сотруднику) и по самому значению токена (используется при автоматической деактивации токена после ошибки отправки).

## Регистрация устройства

Мобильное или веб-приложение отправляет push-токен, полученный от системы устройства, вместе с идентификатором устройства и типом платформы.

<Warning>
Поля «ID устройства» и «Тип устройства» формально допускают отсутствие значения при валидации запроса, но при фактической обработке оба поля читаются из тела запроса без запасного варианта. Если одно из них полностью отсутствует в запросе (ключ не передан вовсе), регистрация не выполняется — запрос завершается ошибкой сервера, а не тихой подстановкой значения по умолчанию (в частности, платформы iOS). Клиентским приложениям следует всегда явно передавать оба поля, даже если значение ID устройства пустое.
</Warning>

Логика регистрации:

1. Система ищет среди **всех активных** push-токенов (не только текущего сотрудника и не только текущей компании) записи, у которых совпадает значение токена **или** совпадает ID устройства (если он передан и не пуст), и которые принадлежат **другому** сотруднику. Все такие записи помечаются неактивными.
2. Затем для комбинации «компания + текущий сотрудник + токен + ID устройства + тип устройства» выполняется поиск-или-создание: если такая запись уже есть — она обновляется и помечается активной; если нет — создаётся новая, сразу активная.

Смысл шага 1 — автоматически «отобрать» устройство у прежнего владельца, если то же физическое устройство (или тот же токен) теперь используется другим сотрудником, например при смене пользователя корпоративного планшета или переустановке приложения другим человеком на том же телефоне.

<Warning>
Проверка на шаге 1 не ограничена текущей компанией — она сравнивает токен и ID устройства по всей системе. Если один и тот же токен или один и тот же ID устройства случайно совпадёт у сотрудников из разных компаний, регистрация в одной компании деактивирует чужую активную запись в другой компании.
</Warning>

## Просмотр своих устройств

Сотрудник может получить список всех push-токенов, когда-либо зарегистрированных им в текущей компании — как активных, так и уже отключённых, отсортированных от последних зарегистрированных к более ранним. Это позволяет приложению показать пользователю список его устройств и их текущий статус.

## Отписка устройства от push

Отдельное действие «отписать устройство» принимает только ID устройства и деактивирует **все** push-токены с этим ID устройства в рамках текущей компании — независимо от того, какому сотруднику они принадлежат. Это рассчитано на сценарий «это устройство больше никогда не должно получать push», например при выходе из аккаунта на общем/сдаваемом устройстве, а не только «отписать лично себя».

## Отправка push-уведомлений

### Место push в общей ленте событий

Push — один из источников доставки, наравне с Telegram-ботом и веб-каналом. Когда в компании создаётся новая запись в единой ленте событий, система определяет получателей push для темы этого события: берутся сотрудники, у которых в персональных настройках включён именно push-канал для темы этого события (а если событие адресовано конкретным получателям — список дополнительно сужается до них). Если push как канал не включён в источники этого конкретного события или ни у одного сотрудника push не разрешён по настройкам для этой темы — отправка не выполняется вовсе.

### Что отправляется

Для отобранных сотрудников система забирает **все активные** push-токены их устройств в этой компании и одним пакетным вызовом отправляет каждому из них push-сообщение через сервис отправки push-уведомлений (обёртку над Expo). Сообщение состоит из:

- заголовка — фиксированный текст «Уведомление»;
- текста — сам текст события из ленты;
- звука — стандартный звук уведомления;
- Android-канала — стандартный канал приложения;
- количества на значке — не устанавливается;
- служебных данных — идентификатор события в ленте, тип и идентификатор связанного объекта, категория важности события (информация / предупреждение / тревога) и дополнительные структурированные данные события. Эти данные приложение использует, чтобы при нажатии на push открыть нужный экран.

<Note>
Если у выбранных сотрудников не нашлось ни одного активного токена устройства, отправка считается успешно завершённой без единой попытки доставки — это штатный исход, а не ошибка.
</Note>

Отправка выполняется в фоне (асинхронной задачей) и не блокирует создание самого события в ленте: событие в ленте появляется независимо от того, дойдёт ли push до устройств.

### Обработка ошибок отправки

Ответ сервиса отправки разбирается на успешные и ошибочные попытки по каждому токену отдельно.

Если ошибка по конкретному токену означает «токен недействителен» или «устройство снято с регистрации» — этот токен немедленно помечается неактивным по значению самого токена (не по сотруднику и не по компании). Любые другие виды ошибок отправки (временная недоступность сервиса push-доставки, ошибка формирования сообщения и т. п.) не приводят к деактивации токена — он будет использован при следующей отправке снова. В общий лог при этом попадает только сводное количество успехов и ошибок по всей рассылке; сведения о каждой конкретной ошибке остаются только в результате самой фоновой задачи, а не в отдельной журнальной записи.

<Warning>
Отправка требует явно переданный идентификатор компании и список получателей: если хотя бы один из них отсутствует, задача отправки завершается с ошибкой сразу, ничего не отправив и не выбросив исключение — это стоит учитывать при диагностике «push не пришёл», проверяя именно результат задачи, а не журнал ошибок.
</Warning>

## Периодическая очистка неактивных токенов

Отдельная фоновая задача периодически находит push-токены, которые одновременно неактивны и не обновлялись дольше 30 дней, и удаляет их из базы безвозвратно. Смысл — не копить в базе токены отключённых или переустановленных устройств бесконечно.

<Tip>
Отсчёт «30 дней» ведётся от момента последнего полного сохранения записи, а не от момента, когда токен фактически стал неактивным: деактивация токена (при ошибке отправки, при отписке устройства или при вытеснении другим сотрудником) не обновляет дату последнего сохранения записи, поэтому фактический отсчёт обычно идёт от момента последней полной регистрации этого токена.
</Tip>

## Как это используется

| Действие | Метод и путь | Что происходит |
|---|---|---|
| Зарегистрировать/обновить токен устройства | `POST /v1/notifications/mobile/` | Регистрирует push-токен текущего сотрудника, автоматически деактивируя конфликтующие токены (см. выше) |
| Получить список своих устройств | `GET /v1/notifications/mobile/` | Список токенов текущего сотрудника в текущей компании, активных и неактивных |
| Отписать устройство от push | `POST /v1/notifications/mobile/unsubscribe/` | Деактивирует все токены с указанным ID устройства в текущей компании |

Оба маршрута требуют авторизации пользователя; отдельной проверки роли или принадлежности к персоналу компании на уровне доступа не выполняется.

## Подводные камни

<Warning>
- При регистрации нового токена деактивация «чужих» токенов по совпадению значения токена или ID устройства выполняется без фильтра по компании — то есть теоретически может затронуть запись из любой компании в системе, а не только текущей.
- При ошибке отправки push (недействительный токен или устройство снято с регистрации) токен деактивируется по одному только значению токена, без фильтра по компании или по сотруднику — при случайном совпадении значения токена это может задеть запись из другой компании.
- Деактивация токена во всех трёх сценариях (при регистрации нового устройства, при ручной отписке устройства, при ошибке отправки) не обновляет дату последнего использования и дату последнего сохранения записи. Из-за этого 30-дневный отсчёт для последующей очистки неактивных токенов фактически идёт от момента последней полной регистрации токена, а не от момента, когда он реально стал неактивным.
- Периодическая очистка неактивных токенов не включена по умолчанию в общее расписание фоновых задач — чтобы она действительно выполнялась, её нужно добавить отдельно (например, через панель администратора); без этого неактивные токены не будут удаляться автоматически.
- Если клиентское приложение при регистрации устройства вовсе не передаёт поле «ID устройства» или «Тип устройства» (даже с пустым значением), регистрация не завершается платформой по умолчанию, а обрывается ошибкой сервера — оба поля нужно передавать всегда явно.
</Warning>

<Info>
- Регистрация push-токенов и уведомлений в панели администратора оформлена с ошибкой, из-за чего эти сущности фактически не видны в административной панели, хотя по замыслу должны там отображаться.
- В системе заложена возможность точечно включать или выключать конкретный токен, но ни один маршрут ей не пользуется: вручную активировать один отключённый токен или деактивировать ровно один токен (кроме отписки по ID устройства) через API нельзя.
- Отправка push требует обязательно указанный идентификатор компании и непустой список получателей; при их отсутствии задача завершается с пометкой об ошибке в результате, не прерываясь исключением — это стоит проверять при разборе причин недоставки.
- Автоматическая деактивация токена при ошибке отправки срабатывает только для двух типов ошибок (недействительный токен и «устройство снято с регистрации»); любые другие ошибки отправки лишь попадают в сводный подсчёт, а токен остаётся активным и будет использован при следующей рассылке.
</Info>
