## Что делает этот слой

Все загружаемые пользователями файлы (фото инвентаря, вложения, документы) и вся статика интерфейса хранятся не на диске сервера приложения, а во внешнем S3-совместимом объектном хранилище. Этот раздел описывает, как платформа решает три задачи:

- изолирует файлы каждой компании друг от друга, даже когда они лежат в одном общем бакете;
- защищается от попыток «вырваться» из выделенного компании каталога через хитрое имя файла;
- отдаёт статические файлы интерфейса (стили, скрипты, шрифты) быстро и с версионированием, без обращения к S3.

<Info>
Файловое хранилище — часть платформенного слоя, а не отдельный раздел приложения. Оно опирается на уже выбранную для запроса компанию: какой компании принадлежит текущий запрос, в тот «каталог» и попадёт файл. Как именно определяется компания запроса, описано в разделе «Пользователи и доступ».
</Info>

## Три хранилища

Платформа использует три разных механизма хранения, у каждого своя роль.

| Хранилище | Бакет | Роль |
| --- | --- | --- |
| S3-хранилище компании | media | Хранилище по умолчанию для всех загружаемых медиафайлов; изолирует файлы по компании |
| Общее публичное хранилище | public | Файлы, общие для всех компаний; используется только явно, не по умолчанию |
| Хранилище статики | локальная сборка + раздача веб-сервером | Стили, скрипты, шрифты интерфейса — сжатие и версионирование |

### S3-хранилище компании (по умолчанию)

Это основной бэкенд: когда любой код проекта сохраняет загруженный файл без явного указания хранилища, файл идёт именно сюда, в бакет media.

Ключевая особенность — **имя файла всегда начинается с префикса идентификатора текущей компании**. Перед сохранением к пути файла спереди добавляется идентификатор той компании, к которой привязан текущий запрос. В результате файлы разных компаний физически лежат в разных «папках» одного бакета и никогда не пересекаются, даже если две компании загрузили файлы с одинаковыми именами.

<Warning>
Префикс идентификатора компании подставляется из контекста текущего запроса. Значит, компания должна быть уже определена к моменту сохранения файла. Если сохранить файл вне контекста запроса (например, в фоновой обработке, где компания не установлена), префикс окажется не тем — файл уйдёт «не в ту папку». В tenant-aware фоновых задачах контекст компании восстанавливается автоматически, но при ручных операциях об этом нужно помнить.
</Warning>

### Общее публичное хранилище

Отдельный бэкенд для файлов, которые не принадлежат конкретной компании и должны быть общими: он пишет в бакет public и **не добавляет префикс компании**. Это хранилище не является хранилищем по умолчанию — его подключают явно там, где файл действительно общий для всех. Логика защиты имени файла у него такая же, как у основного, но без изоляции по компании.

### Хранилище статики

Статика (файлы интерфейса) обслуживается отдельно от медиафайлов. При сборке проекта все статические файлы собираются в локальный каталог, сжимаются и получают версионные имена (в имя добавляется отпечаток содержимого). Раздаёт их сам веб-сервер приложения через встроенное промежуточное звено, а не S3. Благодаря версионным именам браузер может кэшировать файлы сколь угодно долго: при любом изменении содержимого меняется имя, и старый кэш не мешает.

## Как формируется имя файла

Формирование имени — самая ответственная часть, потому что именно здесь обеспечиваются и изоляция, и безопасность. Для основного хранилища шаги такие:

1. **Префикс компании.** К исходному пути файла спереди приписывается идентификатор текущей компании.
2. **Нормализация разделителей.** Все обратные слэши заменяются на прямые — путь приводится к единому виду.
3. **Разделение на каталог и имя.** Путь делится на «папку» и собственно имя файла.
4. **Защита от выхода за каталог.** Если в частях каталога встречается переход на уровень выше (элемент «..»), сохранение отклоняется с ошибкой подозрительной файловой операции. Так блокируется попытка через хитрое имя файла «вырваться» из папки своей компании в чужую.
5. **Очистка имени.** Собственно имя файла прогоняется через стандартную очистку допустимых символов, после чего путь и имя собираются обратно в нормализованный путь.

Общее публичное хранилище проходит те же шаги, кроме первого: префикс компании не добавляется.

<Note>
Проверка на «выход за каталог» смотрит именно на части каталога. Само имя файла дополнительно очищается стандартным механизмом допустимых символов. Вместе это не даёт подставить путь вида «подняться на уровень выше и записать в соседнюю папку».
</Note>

### Перезапись файлов

Оба S3-хранилища работают в режиме **перезаписи**: если файл с точно таким же итоговым именем уже существует, он перезаписывается новым, а не сохраняется рядом с добавлением суффикса-уникализатора. Это упрощает предсказуемость ссылок, но означает, что загрузка файла с совпадающим путём затирает предыдущий.

<Warning>
Из-за режима перезаписи не стоит рассчитывать, что загрузка двух файлов с одинаковым именем в одном каталоге компании сохранит оба. Второй перезапишет первый. Уникальность имён, где она нужна, должна обеспечиваться вызывающим кодом.
</Warning>

## Ссылки на файлы

Чтобы получить публичный адрес сохранённого файла, используется хелпер URL медиафайла: ему передают ключ (путь объекта в хранилище), и он возвращает адрес через хранилище по умолчанию. Для пустого ключа возвращается «ничего» (пустой результат) — удобно, когда файл может быть не задан.

Ссылки на файлы формируются **с временной подписью доступа**: в адресе присутствует подписанный параметр. Это значит, что прямая ссылка на объект действительна ограниченное время и её нельзя произвольно долго переиспользовать или раздавать как постоянную.

<Note>
Так как хелпер работает через хранилище по умолчанию, он тоже опирается на контекст текущей компании — ключ разрешается в рамках той компании, от имени которой выполняется запрос.
</Note>

## Настройки подключения и путей

Параметры доступа к S3 берутся из переменных окружения и не хранятся в коде.

| Параметр | Назначение |
| --- | --- |
| Адрес S3-эндпоинта | URL S3-совместимого сервиса |
| Ключ доступа | Идентификатор доступа к хранилищу |
| Секретный ключ | Секрет доступа к хранилищу |
| Регион | Регион хранилища |
| Подпись в query-строке | Включена — ссылки на файлы содержат временную подпись доступа |

<Note>
В окружении также определена переменная с именем бакета, но фактически используемые бакеты («media» и «public») жёстко заданы в коде хранилищ — эта переменная не влияет на то, в какой бакет попадёт файл.
</Note>

Базовые URL и локальные пути статики и медиа заданы отдельно:

| Настройка | Значение / смысл |
| --- | --- |
| URL статики | Базовый путь раздачи статики интерфейса |
| URL медиа | Базовый путь для медиа |
| Каталог статики | Куда собираются статические файлы при сборке |
| Каталог медиа | Локальный каталог медиа |
| Префикс раздачи статики | Префикс, под которым веб-сервер отдаёт статику |

<Info>
Имена конкретных бакетов для медиа и для общего хранилища зафиксированы в коде («media» и «public»), тогда как учётные данные, адрес сервиса и регион приходят из окружения. Это позволяет менять окружение (тест, продакшн) без правок кода.
</Info>

## Как это связано с остальной платформой

Файловое хранилище — низовой слой: им пользуются практически все разделы приложения, где есть загрузки (инвентарь, вложения, документы). Изоляция по компании здесь — прямое продолжение общей модели изоляции: как база данных разграничивает данные компаний через RLS, так хранилище разводит их файлы по префиксам в бакете. Никакой отдельной настройки на стороне прикладного кода для этого не требуется — достаточно, чтобы к моменту сохранения был установлен контекст компании.

## Подводные камни

<Warning>
- Префикс каталога компании подставляется из контекста текущего запроса в момент сохранения файла — если сохранять файл там, где компания ещё или уже не установлена, файл уйдёт под неверный префикс (в чужую или в системную папку).
- Оба S3-хранилища работают в режиме перезаписи: файл с тем же итоговым именем затирает предыдущий, суффикс-уникализатор не добавляется — уникальность имён должен обеспечивать вызывающий код.
</Warning>

- Проверка на выход за каталог («..») смотрит только на части каталога, а не на само имя файла; защиту имени обеспечивает отдельная очистка допустимых символов — обе части работают только вместе.
- Общее публичное хранилище не добавляет префикс компании и потому не изолирует файлы по компании — его нельзя использовать как замену основному там, где нужна изоляция.
- Имя бакета определено в окружении, но фактические бакеты для медиа и общего хранилища жёстко заданы в коде, поэтому переменная окружения не влияет на выбор бакета.

<Info>
- Ссылки на файлы подписаны и действуют ограниченное время (подпись включена в адрес) — их нельзя раздавать как постоянные публичные адреса.
- Хелпер получения адреса возвращает пустой результат для пустого ключа, поэтому его безопасно вызывать для необязательных файлов.
- Имена бакетов для медиа и общего хранилища зашиты в коде, а учётные данные, адрес сервиса и регион берутся из переменных окружения.
</Info>
