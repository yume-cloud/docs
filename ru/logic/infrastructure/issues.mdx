Эта страница собирает **инфраструктурные риски и подводные камни** платформы: места, где изоляция компаний, фоновые задачи, кэш, хранилище и права доступа ведут себя не так, как ожидается «по умолчанию». Разделы упорядочены по серьёзности.

<Note>
Ссылки на файлы и строки даны для разработчиков как ориентир и относятся к состоянию кода на момент составления страницы. Остальные страницы раздела описывают штатное поведение — отклонения и риски вынесены сюда.
</Note>

<Note>
**Фактическая правка, важная для чтения всей страницы: политик row-level security (RLS) в проекте нет ни одной.** Проверено на живой базе: `pg_policies` пуст, ни одной таблицы с `relrowsecurity`; в репозитории нет ни `CREATE POLICY`, ни `set_config`. Изоляция компаний держится **в коде приложения, а не в базе**: каждая строка компанийной модели несёт ссылку на компанию (`tenant`), а менеджер модели добавляет к запросу фильтр по активной компании соединения (`connection.tenant`). Прежние формулировки на этой странице про «политику изоляции данных, которая при пустом контексте что-то блокирует» были неверны: блокировать нечему — при пустом контексте менеджер просто не добавляет фильтр, и запрос видит строки всех компаний.
</Note>

## Изоляция компаний (критично)

<Warning>
**Доступ по умолчанию — «разрешено всем».** Глобально задан разрешающий доступ, поэтому каждый раздел обязан сам подключить проверку прав. Любой забытый permission-класс делает раздел публичным для **анонимных** запросов.

- **Последствие:** один пропущенный permission-класс = публичный доступ; адреса OpenAPI-описания (справочник API) отдаются без ограничений. Для аутентифицированных запросов межкомпанийный доступ закрыт отдельной проверкой членства (`middlewares/tenant_access.py`), но анонимного доступа она не касается — сверять членство не с кем.
- **Где:** `rental_tenant_back/settings.py:345-347` (разрешающий доступ по умолчанию); открытые адреса документации — `rental_tenant_back/urls.py:86,149-154`.
- **Как чинить:** «запрещено по умолчанию» и ограничение адресов документации.
</Warning>

<Warning>
**Анонимные вебхуки создают данные в любой компании.** Обработчики вебхуков Wazzup и Ringostat объявлены без аутентификации и без прав, а компанию берут из активного контекста соединения — то есть из хоста, `Origin` или заголовка с идентификатором компании, которые задаёт вызывающая сторона. Проверка членства сюда не достаёт: она применяется только к аутентифицированным запросам.

- **Последствие:** неаутентифицированный POST заводит клиента и лид в произвольной компании.
- **Где:** обработчики вебхуков Wazzup и Ringostat (`integrations/`), компания — из `connection.tenant`.
- **Как чинить:** адрес вебхука с токеном на подключение (потребуется перерегистрировать callback в кабинете каждой компании).
</Warning>

## Логика и неочевидное поведение

<Note>
**Исправлено и снято с этой страницы:**

- **Кэш резолвинга компании инвалидируется, а не ждёт истечения суток.** Ключи компании — по идентификатору, по служебному имени компании (`schema_name`) и по каждому её домену — гасятся при любом изменении компании или домена, включая массовое обновление в обход сохранения. Смена домена гасит и прежнее имя хоста: раньше старый хост продолжал резолвиться в компанию до конца суток. Отрицательный ответ («домен не найден») живёт 60 с вместо суток, а добавление домена гасит его явно, поэтому новый домен виден сразу. Срок жизни ключа стал одинаковым во всех трёх местах, где он писался с разным (резолвинг по хосту, добор компании по токену, фоновые задачи). Ручная команда очистки кэша компаний теперь чистит и доменные ключи.
- **Добор компании по токену не выставляет контекст на «пустую» компанию.** Если идентификатор компании получен, а сама компания уже удалена, запрос получает `403 {"code": "tenant_required"}` вместо внутренней ошибки при первом же обращении к данным; пустое значение больше не кэшируется как валидное.
- **Вебхук Kaspi Pay при незаданном секрете отклоняет запрос.** Раньше подпись сравнивалась даже с пустым ключом; теперь `verify_signature` пишет ошибку в журнал и возвращает отказ, а обработчик отвечает `401` (`integrations/kaspi_pay/webhook.py:44-56,66-68`).
</Note>

<Warning>
**Второго рубежа поверх фильтра менеджера нет: код без контекста компании видит строки всех компаний, а не падает.** Ограничение по компании — это только фильтр `tenant=connection.tenant`, который добавляет менеджер модели. Добавляют его три менеджера: `TenantScopeManager` с подклассами (менеджер `objects` у наследников `TenantScopeModel` — около ста моделей: аренды, клиенты, инвентарь, членство и т. д.), `CompanyManager` (задачи, их типы и связи; связи документов и сессий ассистента) и `TenantScopedAttachmentManager` (вложения). Если активной компании в соединении нет — `connection.tenant` пуст или это заглушка без `id`, как после сброса контекста или внутри `schema_context(get_public_schema_name())`, — менеджеры фильтр не добавляют, и запрос возвращает строки всех компаний. Ошибки при этом не возникает, а политик, которые остановили бы такой запрос, в базе нет. Десятки моделей со ссылкой на компанию, объявленной вручную, и штатным менеджером (`DocumentV2`, `Settings`, `Notification`, `KaspiTransaction`, `AuditEvent` и др.) не ограничены даже так: фильтр по компании для них пишется в каждом запросе вручную.

- **Последствие:** обращение к компанийной модели в обход обычного конвейера запроса или фоновой задачи читает, меняет и удаляет строки всех компаний. Отсутствие сбоя ничего не доказывает: сбоя не будет никогда.
- **Где:** `common/tenant_scope.py:8-33` (`TenantScopeManager`, `CompanyManager`), `attachments/managers.py:5-13`; контекст компании выставляют `middlewares/tenant.py:61-80`, `middlewares/auth.py:47-63` и `rental_tenant_back/celery.py:147-171`.
- **Как чинить:** явно устанавливать контекст компании (или падать) в любом коде, который выполняется вне запроса и вне фоновой задачи, — управляющие команды, разовые скрипты, обработчики сигналов внешних систем. Нефильтрованный менеджер `.admin`, объявленный рядом с каждым из этих менеджеров, оставлять для кода, которому строки всех компаний нужны намеренно: админка, проверка членства, приглашения, кросс-компанийные задачи. Для фоновых задач механизм проверки контекста есть, но пока не срабатывает (см. ниже).
</Warning>

<Warning>
**Требование компании у фоновых задач по умолчанию не объявлено, общий строгий режим выключен, а сама проверка задачу не останавливает.** Воркер определяет компанию по заголовкам задачи: по `_tenant_id`, а если его нет — по служебному имени компании `_schema_name`. Задача, поставленная вне контекста компании (управляющая команда, запись beat без привязки к компании, код внутри `schema_context(get_public_schema_name())`), несёт только служебное имя, а оно у большинства компаний одинаковое, — и воркер выполняет её в контексте **первой по `id` компании** с этим именем: менеджеры ограничивают задачу строками этой компании, новые строки получают ссылку на неё, а в журнал пишется разве что предупреждение.

Механизм защиты есть, но не срабатывает. Задача может объявить, что компания ей обязательна (`tenant_required=True`), а строгий режим `CELERY_TENANT_STRICT` распространяет требование на все задачи модулей из `TENANT_APPS` (`crm`, `shared`, `workshop`, `sales`, `fleet`). Но режим по умолчанию **выключен**, и ни одна задача требования не объявляет: явно размечены только шесть задач, которые сами выставляют контекст компании, и все — как **не** требующие компании (`refresh_accrued_debt`, `request_autopenalty`, `autowithdraw`, `sync_order_alerts`, `purge_finished_penalties`, `sweep_task_reminders`). Записи beat проходят проверку молча и без разметки.

Объявленное требование задачу тоже не остановит. Проверка выполняется в обработчике сигнала `task_prerun`, а Celery перехватывает исключения обработчиков сигналов (`Signal.send`) и только пишет их в журнал. `MissingTenantContext` — как и `Ignore`, когда компанию определить не удалось, — задачу не прерывает, но пропускает идущую следом установку контекста: задача выполняется вовсе без контекста компании, и менеджеры её не ограничивают.

- **Последствие:** задача, поставленная без контекста компании, сегодня работает с данными первой по `id` компании; с включённым требованием она работала бы со строками всех компаний.
- **Где:** `rental_tenant_back/celery.py:44-93` (`has_company_context`, `is_tenant_required`, `check_company_context`), `:96-144` (`get_tenant_from_task`), `:147-160` и `:179` (`set_connection` на `task_prerun`), `:195-207` (заголовки при постановке); `rental_tenant_back/task.py:8` (`tenant_required`); переключатель `CELERY_TENANT_STRICT` — `rental_tenant_back/settings.py:557`.
- **Как чинить:** сначала перенести проверку и установку контекста туда, где исключение действительно прерывает задачу (например, в `before_start` у `TenantTask`), и не подставлять первую попавшуюся компанию по общему служебному имени; затем разметить задачи компанийных модулей требованием компании и включить строгий режим на стейдже, потом в проде. Задачи обслуживания компаний и биллинга остаются без требования — работа вне контекста конкретной компании для них штатна.
</Warning>

<Warning>
**Разбор имени хоста через замену подстроки портит домены.** Префиксы вроде `api.`/`stage.`/`dev.`/`manager.` и слово `localhost` вырезаются заменой подстроки в любом месте строки, а не только в начале. Домен, содержащий такую подстроку в середине, будет искажён и зарезолвится не в ту компанию либо не зарезолвится вовсе.

- **Последствие:** неверный резолвинг компании по домену для доменов с «опасными» подстроками.
- **Где:** `middlewares/tenant.py:26-31`; та же ошибка продублирована в `rental_tenant_back/views.py:1074-1078`.
- **Как чинить:** убирать только настоящие префиксы (по меткам домена), а не заменой подстроки.
</Warning>

<Warning>
**Пользователь нескольких компаний без контекста молча попадает в компанию с наибольшим идентификатором.** Когда компания не определена (например, мобильный клиент без субдомена и без заголовка), выбирается компания пользователя с максимальным идентификатором.

- **Последствие:** пользователь незаметно работает не в той организации.
- **Где:** `user/models.py:349-366`; используется в `middlewares/auth.py:47-63`.
</Warning>

## Хранилище, права и прочее

<Warning>
**Адреса доставки закрыты только аутентификацией — ролевых прав там нет.** Ранее в списке прав этих адресов стоял класс, который выглядел проверкой принадлежности к точке проката, но пропускал любой запрос; класс удалён (он стоял в 43 местах в 18 модулях, фактического доступа его удаление не изменило). На доставке он был единственной проверкой помимо аутентификации — значит после удаления там остался только вход в систему.

- **Последствие:** любой сотрудник компании, независимо от роли и прав, может подтверждать и закрывать доставки.
- **Где:** `crm/views/delivery/action.py` — `permission_classes = [IsAuthenticated]`.
- **Как чинить:** добавить настоящие права раздела доставки (по аналогии с остальными разделами), а не возвращать заглушку.
</Warning>

- **Префикс хранилища не разделяет файлы компаний.** Ключ файла начинается со служебного имени компании из подключения (`connection.schema_name`), а оно у большинства компаний одинаковое. В основном хранилище перезапись одноимённых файлов включена, а файлы-вложения из обычной загрузки сохраняются под исходным именем (`media/files/<имя>`): файл другой компании с тем же именем перезапишет объект, на который уже ссылается вложение первой, а удаление любого из этих вложений удалит общий объект. Изображения и прямая загрузка получают имя `uuid4`, но при завершении прямой загрузки ключ берётся из запроса без проверки, чей это файл. (`common/s3_storage.py:9-19`, `attachments/serializers/file.py:17-25,46-59`, `attachments/views/file.py:44-47`, `attachments/views/direct_upload.py:53-94`)
- **Права на чтение можно обойти общим флагом.** На части адресов чтение (GET) разрешено любому сотруднику компании в обход конкретного права «просмотр», поэтому гранулярные права на чтение там не действуют. (`common/model_permisson.py:38-41,78-79`; требует подтверждения — возможно, намеренно)
- **Сопоставление «метод → право»: создание для операций через POST.** Массовые изменения/удаления, реализованные как POST, требуют лишь право «добавление», а не «изменение»/«удаление» — сотрудник с правом добавления сможет выполнять такие операции. (`common/model_permisson.py:12,32`)
- **Риск утечки секретов в мониторинг.** Включена передача пользовательских данных в систему мониторинга, а декоратор захвата локальных переменных дополнительно прикладывает их к исключению — пароли/токены из локальных переменных могут уехать в мониторинг. (`rental_tenant_back/settings.py:156`, `common/logging.py:191-216`; требует подтверждения)
- **Косметика маршрутов.** Раздача статики подключена безусловно (в проде статику отдаёт веб-сервер — маршрут вводит в заблуждение), а админка смонтирована дважды — напрямую и через локализованные маршруты. (`rental_tenant_back/urls.py:89,146,147`)
- **Цена индексов поиска.** Миграция `crm/0416` добавляет семь триграммных GIN-индексов — по имени и телефону клиента, по названию и `unique_id` инвентаря и групп инвентаря, по названию комплекта. Индексы строятся по таблицам со строками всех компаний и замедляют запись в них. Кроме того, триграммный индекс не работает на терминах короче 3 символов: поиск по одной-двум буквам по-прежнему сканирует таблицу, поэтому минимальную длину запроса имеет смысл ограничивать на стороне интерфейса.

## Что реализовано корректно

- **Поиск больше не выходит за пределы компании и использует индексы.** Поиск по полям связанных сущностей выполняется через подзапрос компанийного менеджера (раньше это был джойн по таблице целиком — в плане запроса видны были строки всех компаний), а принудительная коллация, из-за которой планировщик не мог применить индекс (разница до 1000 раз), снята. Побочный эффект, о котором стоит знать: подбор по «неправильной раскладке» клавиатуры удалён — запрос латиницей больше не находит кириллические совпадения.
- **Проверка членства в активной компании** для аутентифицированных запросов: нет записи участия — `403 {"code": "tenant_forbidden"}`; явный, но неизвестный идентификатор компании — `403 {"code": "tenant_not_found"}` вместо молчаливого выполнения в собственной компании; глобальные `is_staff`/`is_superuser` проходят. Запрещено по умолчанию — новый адрес закрыт без участия автора, список исключений задан явно (`middlewares/tenant_access.py`, `MEMBERSHIP_OPTIONAL_*`). Кэшируется только положительный результат, на 60 с.
- Защита от выхода за пределы каталога в **обоих** хранилищах — основном и публичном (префикс из служебного имени компании `connection.schema_name` + проверка `..` + нормализация пути); в публичном перезапись одноимённых файлов отключена. Файлы разных компаний этот префикс не разделяет — см. выше.
- Сброс контекста компании соединения после каждой фоновой задачи, в том числе при ошибке.
- Установка контекста компании в фоновой задаче только на нужных базах: список задаёт `tenant_databases` задачи, по умолчанию — только основная база. База GPS контекста компании не получает: её строки ссылки на компанию не содержат, принадлежность трекеров выводится из инвентаря компании.
- Ограничение размера и полей в JSON-логах; сброс контекста корреляции запроса в `finally`.
- Инвалидация кэша аутентифицированного пользователя по всем компаниям пользователя.
- лог создаётся только в режиме отладки и ротируется; секреты — вне репозитория.
