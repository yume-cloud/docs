Эта страница собирает **инфраструктурные риски и подводные камни** платформы: места, где изоляция компаний, фоновые задачи, кэш, хранилище и права доступа ведут себя не так, как ожидается «по умолчанию». Разделы упорядочены по серьёзности. Самое важное — раздел про изоляцию компаний: она держится на нескольких соглашениях, нарушение любого из которых снимает защиту.

<Note>
Ссылки на файлы и строки даны для разработчиков как ориентир и относятся к состоянию кода на момент составления страницы. Остальные страницы раздела описывают штатное поведение — отклонения и риски вынесены сюда.
</Note>

## Изоляция компаний (критично)

<Warning>
**Активная компания выбирается по клиентскому заголовку без проверки принадлежности пользователя к компании.** Компания (а значит, RLS-контекст соединения) определяется из заголовка `X-Tenant-Id` или из `Origin`/хоста — всё это управляется клиентом. Middleware устанавливает выбранную компанию как активную для соединения **без проверки**, что аутентифицированный пользователь действительно состоит в этой компании.

- **Последствие:** изоляция данных держится не на middleware, а на том, что **каждый** view подключит permission-класс, перепроверяющий членство (через связь пользователь↔компания). На эндпоинте без такого класса выбор чужой компании заголовком ведёт к чтению/записи её данных.
- **Где:** `middlewares/tenant.py:82-98` (установка активной компании по `X-Tenant-Id`/хосту без проверки пользователя), `:24-27` (`Origin` берётся в приоритете над хостом и тоже задаётся клиентом). Смягчение — только в permission-классе `common/model_permisson.py` (перепроверка членства), и только там, где он подключён.
- **Как чинить:** после резолвинга компании по клиентскому заголовку проверять членство аутентифицированного пользователя; перейти на «запрещено по умолчанию».
</Warning>

<Warning>
**Доступ по умолчанию — «разрешено всем».** Глобально задан разрешающий доступ, поэтому каждый эндпоинт обязан сам подключить проверку прав. Любой забытый permission-класс делает эндпоинт публичным, а в сочетании с выбором компании по заголовку (выше) — открывает данные произвольной компании.

- **Последствие:** один пропущенный permission-класс = публичный доступ; эндпоинты схемы API (Swagger/OpenAPI) отдаются без ограничений.
- **Где:** `rental_tenant_back/settings.py:263-265` (разрешающий доступ по умолчанию); открытые docs-эндпоинты — `rental_tenant_back/urls.py:139-144`.
- **Как чинить:** «запрещено по умолчанию» и ограничение docs-эндпоинтов.
</Warning>

## Логика и неочевидное поведение

<Warning>
**Автофильтр по компании отсутствует на уровне ORM — защита держится только на RLS-политике.** Базовый менеджер компанийных моделей не добавляет собственный фильтр по компании: изоляция полностью полагается на RLS-политику самой таблицы. Если RLS-контекст на соединении не выставлен (например, код обратился к модели в обход обычного request/task-конвейера), результат зависит от того, как политика конкретной таблицы обрабатывает отсутствующий контекст.

- **Последствие:** второго рубежа (фильтра по компании поверх RLS) в обычном потоке запроса нет; если политика какой-то таблицы при пустом RLS-контексте пропускает строки вместо того, чтобы их блокировать, запрос к такой модели может вернуть чужие строки.
- **Требует подтверждения:** для каждой компанийной таблицы политика должна по умолчанию **запрещать** доступ при отсутствующем RLS-контексте (deny-by-default); отдельного фильтра на уровне ORM для этого случая нет.
</Warning>

<Warning>
**Фоновая задача без контекста компании молча выполняется без RLS-контекста, а не падает.** При постановке задачи идентификатор компании берётся из текущего соединения безусловно, в том числе когда компания не определена. Если задача ставится вне запроса и контекст компании потерян, в заголовок попадает пустое значение вместо реального идентификатора, и воркер выполняет тело задачи без активного RLS-контекста — это тихо неверный контекст, а не ошибка.

- **Последствие:** фоновая обработка может незаметно работать без изоляции по компании; ошибку видно только там, где RLS-политика при пустом контексте не блокирует доступ.
- **Где:** `rental_tenant_back/celery.py:108-116` (проставление идентификатора компании), `:15-62` (определение компании задачи), `rental_tenant_back/task.py:18-27`.
- **Как чинить:** для задач, требующих компании, явно проверять наличие реального идентификатора компании и падать, а не выполняться без RLS-контекста.
</Warning>

<Warning>
**Разбор имени хоста через замену подстроки портит домены.** Префиксы вроде `api.`/`stage.`/`dev.`/`manager.` и слово `localhost` вырезаются заменой подстроки в любом месте строки, а не только в начале. Домен, содержащий такую подстроку в середине, будет искажён и зарезолвится не в ту компанию либо не зарезолвится вовсе.

- **Последствие:** неверный резолвинг компании по домену для доменов с «опасными» подстроками.
- **Где:** `middlewares/tenant.py:29-34`; та же ошибка продублирована в `rental_tenant_back/views.py:294-298`.
- **Как чинить:** убирать только настоящие префиксы (по меткам домена), а не заменой подстроки.
</Warning>

<Warning>
**Кэш резолвинга компании живёт 24 часа и кэширует «не найдено».** Результат резолвинга компании (по идентификатору и по домену), включая отрицательный ответ, кэшируется на сутки, и ручной инвалидации нет. Тот же ключ переиспользуется с разным сроком жизни в других местах.

- **Последствие:** после смены домена, деактивации компании или добавления нового домена система до 24 часов отдаёт устаревший результат; несогласованный срок жизни одного ключа в разных местах.
- **Где:** `middlewares/tenant.py:9,53,71,78`; тот же ключ с TTL 60 c — `middlewares/auth.py:47`, с дефолтным TTL — `rental_tenant_back/celery.py:43,59`.
- **Как чинить:** снизить срок жизни и/или инвалидировать ключи при изменении компании и доменов.
</Warning>

<Warning>
**Пользователь нескольких компаний без контекста молча попадает в компанию с наибольшим идентификатором.** Когда компания не определена (например, мобильный клиент без субдомена и без заголовка), выбирается компания пользователя с максимальным идентификатором.

- **Последствие:** пользователь незаметно работает не в той организации.
- **Где:** `user/models.py:331-347`; используется в `middlewares/auth.py:32-49`.
</Warning>

<Warning>
**Добор компании по токену может выставить RLS-контекст на «пустую» компанию.** Если идентификатор компании получен, а сама компания уже удалена, пустое значение кэшируется и передаётся в установку RLS-контекста, что приводит к внутренней ошибке при последующем обращении к данным.

- **Последствие:** 500 вместо понятного отказа; «пустая» компания кэшируется как валидная.
- **Где:** `middlewares/auth.py:45-49`.
- **Как чинить:** проверять наличие компании до установки RLS-контекста и возвращать отказ.
</Warning>

## Хранилище, права и прочее

<Warning>
**Публичное хранилище не разделяет файлы по компаниям и перезаписывает одноимённые.** В отличие от основного хранилища (ключ с префиксом идентификатора компании), публичное хранилище кладёт файлы без префикса компании и с включённой перезаписью.

- **Последствие:** файлы разных компаний с одинаковым именем перетирают друг друга в общем бакете.
- **Где:** `common/s3_storage.py:22-31` (нет префикса компании), `:24` (перезапись включена); ср. основное хранилище `:14`.
</Warning>

- **Проверка «есть точки проката» ничего не проверяет.** Permission-класс, который должен ограничивать доступ наличием точек проката, всегда возвращает «разрешено» (реальная логика закомментирована); места, полагающиеся на него как на защиту, фактически открыты. (`common/has_rental_permission.py:4-6`)
- **Права на чтение можно обойти общим флагом.** На части эндпоинтов чтение (GET) разрешено любому сотруднику компании в обход конкретного права «просмотр», поэтому гранулярные права на чтение там не действуют. (`common/model_permisson.py:38-41,78-79`; требует подтверждения — возможно, намеренно)
- **Сопоставление «метод → право»: создание для операций через POST.** Массовые изменения/удаления, реализованные как POST, требуют лишь право «добавление», а не «изменение»/«удаление» — сотрудник с правом добавления сможет выполнять такие операции. (`common/model_permisson.py:12,32`)
- **Риск утечки секретов в мониторинг.** Включена передача пользовательских данных в систему мониторинга, а декоратор захвата локальных переменных дополнительно прикладывает их к исключению — пароли/токены из локальных переменных могут уехать в мониторинг. (`rental_tenant_back/settings.py:97`, `common/logging.py:191-216`; требует подтверждения)
- **Косметика маршрутов.** Раздача статики подключена безусловно (в проде статику отдаёт whitenoise — маршрут вводит в заблуждение), а админка смонтирована дважды — напрямую и через локализованные маршруты. (`rental_tenant_back/urls.py:82,136,137`)

## Что реализовано корректно

- Защита от выхода за пределы каталога в основном хранилище (префикс идентификатора компании + проверка `..` + нормализация пути).
- Сброс RLS-контекста соединения после каждой фоновой задачи, в том числе при ошибке.
- Установка RLS-контекста на всех нужных базах (включая GPS-базу), по умолчанию — только основная.
- Ограничение размера и полей в JSON-логах; сброс контекста корреляции запроса в `finally`.
- Инвалидация кэша аутентифицированного пользователя по всем компаниям пользователя.
- SQL-лог создаётся только в режиме отладки и ротируется; секреты — вне репозитория.
