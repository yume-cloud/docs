Эта страница собирает **инфраструктурные риски и подводные камни** платформы: места, где изоляция компаний, фоновые задачи, кэш, хранилище и права доступа ведут себя не так, как ожидается «по умолчанию». Разделы упорядочены по серьёзности.

<Note>
Ссылки на файлы и строки даны для разработчиков как ориентир и относятся к состоянию кода на момент составления страницы. Остальные страницы раздела описывают штатное поведение — отклонения и риски вынесены сюда.
</Note>

<Note>
**Фактическая правка, важная для чтения всей страницы: политик row-level security (RLS) в проекте нет ни одной.** Проверено на живой базе: `pg_policies` пуст, ни одной таблицы с `relrowsecurity`, `CREATE POLICY` в репозитории не встречается. Изоляция компаний держится **на отдельной схеме PostgreSQL для каждой компании и на `search_path`**. Прежние формулировки на этой странице про «политику изоляции данных, которая при пустом контексте что-то блокирует» были неверны: блокировать нечему — при пустом контексте запрос просто попадает в публичную схему, где лежат таблицы с теми же именами.
</Note>

## Изоляция компаний (критично)

<Warning>
**Доступ по умолчанию — «разрешено всем».** Глобально задан разрешающий доступ, поэтому каждый раздел обязан сам подключить проверку прав. Любой забытый permission-класс делает раздел публичным для **анонимных** запросов.

- **Последствие:** один пропущенный permission-класс = публичный доступ; адреса схемы API (справочник API) отдаются без ограничений. Для аутентифицированных запросов межкомпанийный доступ закрыт отдельной проверкой членства (`middlewares/tenant_access.py`), но анонимного доступа она не касается — сверять членство не с кем.
- **Где:** `rental_tenant_back/settings.py:263-265` (разрешающий доступ по умолчанию); открытые адреса документации — `rental_tenant_back/urls.py:139-144`.
- **Как чинить:** «запрещено по умолчанию» и ограничение адресов документации.
</Warning>

<Warning>
**Анонимные вебхуки создают данные в любой компании.** Обработчики вебхуков Wazzup и Ringostat объявлены без аутентификации и без прав, а компанию берут из активного контекста соединения — то есть из хоста, `Origin` или заголовка с идентификатором компании, которые задаёт вызывающая сторона. Проверка членства сюда не достаёт: она применяется только к аутентифицированным запросам.

- **Последствие:** неаутентифицированный POST заводит клиента и лид в произвольной компании.
- **Где:** обработчики вебхуков Wazzup и Ringostat (`integrations/`), компания — из `connection.tenant`.
- **Как чинить:** адрес вебхука с токеном на подключение (потребуется перерегистрировать callback в кабинете каждой компании).
</Warning>

<Warning>
**Подпись вебхука Kaspi Pay сравнивается даже при пустом секрете.** При незаданном секрете в журнал пишется отметка «подпись не проверяется», но сравнение всё равно выполняется — с пустым ключом подпись подделывается.

- **Последствие:** платёжный вебхук принимает поддельные запросы, если секрет не сконфигурирован.
- **Где:** `integrations/kaspi_pay/webhook.py:44`.
- **Как чинить:** при пустом секрете отклонять запрос, а не «проверять» его пустым ключом.
</Warning>

## Логика и неочевидное поведение

<Note>
**Исправлено и снято с этой страницы:**

- **Кэш резолвинга компании инвалидируется, а не ждёт истечения суток.** Ключи компании — по идентификатору, по имени схемы и по каждому её домену — гасятся при любом изменении компании или домена, включая массовое обновление в обход сохранения. Смена домена гасит и прежнее имя хоста: раньше старый хост продолжал резолвиться в компанию до конца суток. Отрицательный ответ («домен не найден») живёт 60 с вместо суток, а добавление домена гасит его явно, поэтому новый домен виден сразу. Срок жизни ключа стал одинаковым во всех трёх местах, где он писался с разным (резолвинг по хосту, добор компании по токену, фоновые задачи). Ручная команда очистки кэша компаний теперь чистит и доменные ключи.
- **Добор компании по токену не выставляет контекст на «пустую» компанию.** Если идентификатор компании получен, а сама компания уже удалена, запрос получает `403 {"code": "tenant_required"}` вместо внутренней ошибки при первом же обращении к данным; пустое значение больше не кэшируется как валидное.
</Note>

<Warning>
**Второго рубежа поверх схемы компании нет: код в обход обычного конвейера запроса попадает в публичную схему, а не падает.** Базовый менеджер компанийных моделей не добавляет собственного фильтра по компании — изоляция целиком опирается на то, что соединение переключено на схему нужной компании. Если контекст компании не выставлен, запрос уходит в публичную схему, где существуют таблицы с теми же именами (проверено: таблицы аренд, инвентаря и клиентов там есть). Ошибки при этом не возникает.

- **Последствие:** обращение к компанийной модели в обход обычного конвейера запроса или фоновой задачи читает и пишет публичные копии настоящих таблиц. Отсутствие сбоя ничего не доказывает: сбоя не будет никогда.
- **Где:** базовый менеджер компанийных моделей; переключение схемы — `middlewares/tenant.py`, `rental_tenant_back/celery.py`.
- **Как чинить:** явно устанавливать контекст компании (или падать) в любом коде, который выполняется вне запроса и вне фоновой задачи — управляющие команды, разовые скрипты, обработчики сигналов внешних систем. Для фоновых задач такой механизм уже есть (см. ниже).
</Warning>

<Warning>
**Требование компании у фоновых задач по умолчанию не объявлено, а общий строгий режим выключен.** Механизм есть: задача может объявить, что компания ей обязательна, — тогда при потере контекста она падает с понятной ошибкой вместо тихого выполнения в публичной схеме. Есть и общий строгий режим, распространяющий требование на все задачи компанийных модулей. Но по умолчанию режим **выключен**, а поимённая классификация задач не выполнена: явно помечены только два кросс-компанийных обхода (начисление автоштрафов и автосписание) — как **не** требующие компании.

- **Последствие:** задача, которой компания на самом деле нужна, при потере контекста по-прежнему выполняется в публичной схеме и оставляет лишь предупреждение в журнале.
- **Где:** `rental_tenant_back/celery.py` (`check_company_context`, `is_tenant_required`), `rental_tenant_back/task.py` (`tenant_required`), переключатель `CELERY_TENANT_STRICT` — `rental_tenant_back/settings.py:443`.
- **Как чинить:** разметить задачи компанийных модулей требованием компании, включить строгий режим на стейдже, затем в проде. Задачи обслуживания компаний и биллинга остаются без требования — публичная схема для них штатна.
</Warning>

<Warning>
**Разбор имени хоста через замену подстроки портит домены.** Префиксы вроде `api.`/`stage.`/`dev.`/`manager.` и слово `localhost` вырезаются заменой подстроки в любом месте строки, а не только в начале. Домен, содержащий такую подстроку в середине, будет искажён и зарезолвится не в ту компанию либо не зарезолвится вовсе.

- **Последствие:** неверный резолвинг компании по домену для доменов с «опасными» подстроками.
- **Где:** `middlewares/tenant.py:29-34`; та же ошибка продублирована в `rental_tenant_back/views.py:294-298`.
- **Как чинить:** убирать только настоящие префиксы (по меткам домена), а не заменой подстроки.
</Warning>

<Warning>
**Пользователь нескольких компаний без контекста молча попадает в компанию с наибольшим идентификатором.** Когда компания не определена (например, мобильный клиент без субдомена и без заголовка), выбирается компания пользователя с максимальным идентификатором.

- **Последствие:** пользователь незаметно работает не в той организации.
- **Где:** `user/models.py:331-347`; используется в `middlewares/auth.py:32-49`.
</Warning>

## Хранилище, права и прочее

<Warning>
**Адреса доставки закрыты только аутентификацией — ролевых прав там нет.** Ранее в списке прав этих адресов стоял класс, который выглядел проверкой принадлежности к точке проката, но пропускал любой запрос; класс удалён (он стоял в 43 местах в 18 модулях, фактического доступа его удаление не изменило). На доставке он был единственной проверкой помимо аутентификации — значит после удаления там остался только вход в систему.

- **Последствие:** любой сотрудник компании, независимо от роли и прав, может подтверждать и закрывать доставки.
- **Где:** `crm/views/delivery/action.py` — `permission_classes = [IsAuthenticated]`.
- **Как чинить:** добавить настоящие права раздела доставки (по аналогии с остальными разделами), а не возвращать заглушку.
</Warning>

- **Права на чтение можно обойти общим флагом.** На части адресов чтение (GET) разрешено любому сотруднику компании в обход конкретного права «просмотр», поэтому гранулярные права на чтение там не действуют. (`common/model_permisson.py:38-41,78-79`; требует подтверждения — возможно, намеренно)
- **Сопоставление «метод → право»: создание для операций через POST.** Массовые изменения/удаления, реализованные как POST, требуют лишь право «добавление», а не «изменение»/«удаление» — сотрудник с правом добавления сможет выполнять такие операции. (`common/model_permisson.py:12,32`)
- **Риск утечки секретов в мониторинг.** Включена передача пользовательских данных в систему мониторинга, а декоратор захвата локальных переменных дополнительно прикладывает их к исключению — пароли/токены из локальных переменных могут уехать в мониторинг. (`rental_tenant_back/settings.py:97`, `common/logging.py:191-216`; требует подтверждения)
- **Косметика маршрутов.** Раздача статики подключена безусловно (в проде статику отдаёт веб-сервер — маршрут вводит в заблуждение), а админка смонтирована дважды — напрямую и через локализованные маршруты. (`rental_tenant_back/urls.py:82,136,137`)
- **Цена индексов поиска.** Триграммные индексы поиска (миграция `crm/0416`) создаются в каждой схеме компании — около 3,6% размера таблицы, и запись по таблице клиентов, которая идёт постоянно, они замедляют. Кроме того, триграммный индекс не работает на терминах короче 3 символов: поиск по одной-двум буквам по-прежнему сканирует таблицу, поэтому минимальную длину запроса имеет смысл ограничивать на стороне интерфейса.

## Что реализовано корректно

- **Поиск больше не выходит за пределы компании и использует индексы.** Поиск по полям связанных сущностей выполняется через подзапрос компанийного менеджера (раньше это был джойн по таблице целиком — в плане запроса видны были строки всех компаний), а принудительная коллация, из-за которой планировщик не мог применить индекс (разница до 1000 раз), снята. Побочный эффект, о котором стоит знать: подбор по «неправильной раскладке» клавиатуры удалён — запрос латиницей больше не находит кириллические совпадения.
- **Проверка членства в активной компании** для аутентифицированных запросов: нет записи участия — `403 {"code": "tenant_forbidden"}`; явный, но неизвестный идентификатор компании — `403 {"code": "tenant_not_found"}` вместо молчаливого выполнения в собственной компании; глобальные `is_staff`/`is_superuser` проходят. Запрещено по умолчанию — новый адрес закрыт без участия автора, список исключений задан явно (`middlewares/tenant_access.py`, `MEMBERSHIP_OPTIONAL_*`). Кэшируется только положительный результат, на 60 с.
- Защита от выхода за пределы каталога в **обоих** хранилищах — основном и публичном (префикс схемы компании + проверка `..` + нормализация пути); в публичном перезапись одноимённых файлов отключена.
- Сброс контекста компании соединения после каждой фоновой задачи, в том числе при ошибке.
- Установка контекста компании на всех нужных базах (включая GPS-базу), по умолчанию — только основная.
- Ограничение размера и полей в JSON-логах; сброс контекста корреляции запроса в `finally`.
- Инвалидация кэша аутентифицированного пользователя по всем компаниям пользователя.
- лог создаётся только в режиме отладки и ротируется; секреты — вне репозитория.
