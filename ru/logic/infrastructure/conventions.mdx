## Что это за раздел

В коде Yume есть несколько «сквозных» соглашений, которые применяются почти в каждом приложении, но не относятся ни к одной конкретной бизнес-функции. Эта страница описывает две такие договорённости платформенного слоя:

1. **Базовая модель с метками времени** — единый способ фиксировать, когда запись была создана и когда изменена в последний раз.
2. **Проверка прав доступа по модели** — то, как система решает, имеет ли сотрудник компании право выполнить конкретный запрос (посмотреть, создать, изменить или удалить данные), и почему каждый защищённый раздел API обязан подключать эту проверку явно.

<Info>
Разрешение компании по адресу/заголовку и вход по JWT описаны в разделе «Пользователи и доступ» — здесь мы на них только опираемся. Привязка данных к конкретной компании (базовая модель с привязкой к компании) описана в разделе про изоляцию компаний; настоящая страница дополняет её соглашениями более общего уровня.
</Info>

## Базовая модель с метками времени

Подавляющее большинство таблиц в системе наследуют один общий абстрактный базовый класс. Он не создаёт собственной таблицы в базе — он лишь добавляет к любой унаследовавшей его модели две служебные колонки времени.

| Поле | Тип | Назначение |
| --- | --- | --- |
| Дата создания | дата/время | Проставляется автоматически один раз, в момент создания записи, и больше не меняется. Колонка проиндексирована, поэтому по ней быстро строятся выборки и сортировки «свежие сверху». |
| Дата изменения | дата/время | Обновляется автоматически при каждом сохранении записи — отражает момент последнего изменения. |

### Почему это важно для бизнеса

- **Единообразие.** Не нужно в каждой модели заново заводить поля «когда создано» и «когда изменено» — они появляются автоматически у всех, кто наследует базовый класс.
- **Надёжность дат.** Обе метки заполняет сама система, а не прикладной код и не пользователь. Дату создания невозможно «подделать» через обычное сохранение — она фиксируется единожды.
- **Скорость отчётов.** Индекс по дате создания — причина, по которой списки, ленты событий и аналитика «за период» работают быстро: база не пересматривает всю таблицу, а идёт по индексу.

<Note>
Метка времени изменения обновляется при любом сохранении записи, даже если фактически поменялось всего одно поле. Это ожидаемое поведение: она отвечает на вопрос «когда запись трогали в последний раз», а не «когда изменилось конкретное поле».
</Note>

## Проверка прав доступа по модели

По умолчанию во всём проекте действует принцип «доступ разрешён всем» — базовая настройка прав не ограничивает никого. Это сделано сознательно: платформа не навязывает единую защиту всем эндпоинтам, а требует, чтобы **каждый защищённый раздел API подключал проверку прав явно**. Основной инструмент такой проверки — класс прав «по модели», предназначенный для наборов представлений (ViewSet), работающих с данными.

<Warning>
Из-за политики «по умолчанию разрешено всем» эндпоинт без явно подключённой проверки прав будет открыт для всех. Защита — это не то, что включено «само собой»; её нужно осознанно добавить к каждому разделу, где есть закрытые данные.
</Warning>

### Как метод запроса превращается в право

Проверка отталкивается от того, **что именно** клиент пытается сделать, и переводит HTTP-метод запроса в конкретное право на модель:

| Действие клиента | Требуемое право |
| --- | --- |
| Просмотр (чтение списка/записи) | право на просмотр модели |
| Создание | право на добавление в модель |
| Изменение (полное или частичное) | право на изменение модели |
| Удаление | право на удаление модели |
| Служебные запросы (проверка возможностей, «пустой» запрос) | право не требуется |

Каждое представление, использующее эту проверку, обязано указать, **с какими моделями** оно работает. Если такой список моделей не задан, проверка намеренно завершается ошибкой — это защита от случайно незащищённого эндпоинта. Требуемые права вычисляются сразу по всем моделям представления: чтобы запрос прошёл, у пользователя должны быть права на каждую из них.

### Порядок проверки

Когда приходит запрос, проверка идёт по шагам и на первом же несоответствии отказывает в доступе:

1. **Технический обход.** Если у представления явно выставлен признак «игнорировать проверку прав по модели», доступ разрешается без дальнейших проверок (используется для служебных случаев).
2. **Аутентификация.** Пользователь должен быть распознан системой. Анонимный запрос к защищённому разделу отклоняется.
3. **Принадлежность к персоналу компании.** Доступ получают только пользователи, отмеченные как сотрудники компании. Клиент компании или посторонний пользователь через этот класс прав не пройдёт, даже если он аутентифицирован.
4. **Послабление для чтения.** Если у представления включён режим «разрешить просмотр без отдельного права», то запросы на чтение пропускаются сразу после проверки, что перед нами сотрудник, — не требуя именно права на просмотр. Этот режим удобен, когда видеть данные должен любой сотрудник, а ограничивать нужно лишь изменения.
5. **Собственно право.** Во всех остальных случаях система собирает нужные права по всем моделям представления и проверяет, что у пользователя есть каждое из них.

<Tip>
Режим «разрешить просмотр без отдельного права» ослабляет только чтение. Создание, изменение и удаление всё равно проходят полную проверку прав — этот режим не открывает запись.
</Tip>

### Особый случай — права на аналитику

Есть модель-заглушка, существующая **только ради набора прав** к разделам аналитики. У неё нет собственной таблицы в базе — это чисто «вешалка» для прав. Права к ней описаны прямо в самой модели, а не выводятся из стандартной карты «метод → право».

Для таких «особых» моделей проверка работает иначе: вместо того чтобы по методу запроса подобрать одно право (просмотр/добавление/изменение/удаление), система собирает **весь набор объявленных для модели прав** и требует их. Так закрытые разделы аналитики защищаются собственными, специально заведёнными правами (например, отдельными правами на продажи, клиентов, финансы, зарплаты и прочие срезы аналитики), а не общими правами на просмотр.

### Вспомогательный справочник прав

Рядом с основной проверкой есть отдельный, «модульный» справочник соответствия «метод → право», дублирующий карту внутри класса проверки. Он используется небольшой вспомогательной функцией, которая по модели возвращает код права **на создание** записи. Это утилита для тех мест кода, где нужно программно получить именно «право на добавление», не запуская всю процедуру проверки запроса.

<Note>
Тот факт, что карта соответствия «метод → право» присутствует в системе в двух местах — внутри класса проверки и в отдельном модульном справочнике — стоит держать в голове: это две копии одного и того же соглашения.
</Note>

## Заглушка проверки «точек аренды»

В коде есть ещё один класс прав, задуманный для того, чтобы пускать к некоторым разделам только пользователей, у которых есть точки аренды (или которые являются администраторами компании). **Сейчас это заглушка: она всегда разрешает доступ.** Настоящая логика в коде присутствует, но отключена (закомментирована).

<Warning>
Класс проверки «точек аренды» в текущем виде **никого не ограничивает** — он пропускает любой запрос. Если раздел рассчитывает именно на эту проверку как на реальную защиту, фактически защиты там нет. Опираться на неё как на работающее ограничение нельзя; в проектной документации она упоминается как задел на будущее.
</Warning>

## Как это используется на практике

- Новая модель данных почти всегда наследует базовый класс с метками времени — так у неё сразу появляются корректные даты создания и изменения без дополнительного кода.
- Новый защищённый раздел API (набор представлений) подключает проверку прав по модели **явно** и указывает список моделей, с которыми работает; при необходимости включает послабление для чтения.
- Разделы аналитики защищаются собственными правами через модель-заглушку прав на аналитику.
- Проверку «точек аренды» на сегодня следует воспринимать как незадействованную — реальным барьером доступа она не является.

## Подводные камни

<Warning>
- **Доступ по умолчанию открыт всем.** Эндпоинт без явно подключённой проверки прав остаётся полностью открытым — защиту нужно осознанно добавлять к каждому разделу с закрытыми данными.
- **Проверка «точек аренды» — заглушка.** Сейчас она всегда разрешает доступ (настоящая логика отключена), поэтому как реальное ограничение не работает; полагаться на неё нельзя.
- **Проверка прав по модели требует списка моделей.** Если у представления он не задан, проверка намеренно падает с ошибкой, а не «пропускает» запрос.
- **Не сотрудник не пройдёт.** Даже аутентифицированный пользователь получает отказ, если он не отмечен как сотрудник компании — клиенты и посторонние отсекаются ещё до проверки конкретного права.
</Warning>

Что ещё полезно держать в голове:

- Дата изменения обновляется при любом сохранении записи, даже если реально поменялось лишь одно поле — это отметка «когда запись трогали», а не «когда изменилось конкретное значение».
- Дата создания проиндексирована, а дата изменения — нет; сортировки и фильтры «за период» стоит строить по дате создания, иначе выборка окажется медленной.
- Послабление для чтения ослабляет только просмотр; создание, изменение и удаление по-прежнему требуют соответствующих прав.
- Для модели-заглушки прав на аналитику нужен весь набор объявленных для неё прав, а не одно право по методу запроса — обычная карта «метод → право» к ней не применяется.
- Когда представление работает с несколькими моделями, для доступа нужны права по каждой из них одновременно — недостаточно права только на одну.
- Карта соответствия «метод → право» существует в двух копиях (внутри класса проверки и в отдельном модульном справочнике) — при изменениях их легко рассинхронизировать.
- Служебный признак «игнорировать проверку прав по модели» полностью открывает эндпоинт до всех остальных проверок — его наличие на представлении отключает защиту целиком.
