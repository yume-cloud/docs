Полный перечень полей — в [глоссарии](/ru/logic/infrastructure/routing-docs-glossary).

Маршрутизация URL — это «диспетчерская» всего бэкенда Yume. Весь проект имеет **одну-единственную корневую таблицу маршрутов**: она принимает каждый входящий запрос, по началу адреса решает, какому разделу системы его отдать, и заодно собирает служебные адреса — проверки доступности, страницы документации, админ-панель, метрики. Здесь же, в конце, автоматически достраиваются адреса интерактивной документации API для каждого логического раздела.

Важно: сам выбор компании (по домену или заголовку) и проверка входа по токену выполняются раньше, в слое разрешения компании и добора компании по токену. Маршрутизация уже работает внутри выбранной компании — она отвечает только на вопрос «куда направить запрос», а не «от чьего имени он идёт».

## Версионирование и структура адресов

Почти все рабочие адреса начинаются с версии **/v1/**. Единственное исключение среди разделов приложений — **Документы**, они живут под отдельной версией **/v2/**. Это сделано намеренно: новая версия документов разрабатывалась как самостоятельная замена и вынесена в свой префикс, чтобы не ломать старые интеграции.

Часть адресов вообще не имеет версии в начале: это служебные адреса (проверки, метрики, редактор, админка) и раздел **Wallet (пасскарты)**, который отвечает на короткий адрес без версии, потому что ссылки на пасскарты Apple и Google должны быть максимально стабильными и компактными.

<Info>
Одна и та же версия /v1/ используется для всех разделов. Номер версии здесь — это соглашение о совместимости адресов, а не отдельная «версия кода»; повышают его точечно (как с Документами), а не для всего проекта сразу.
</Info>

## Как разделы подключаются к таблице маршрутов

Каждый раздел системы отвечает за свой набор адресов и подключается под своим префиксом. Ниже — карта основных префиксов.

| Раздел | Префикс адреса |
| --- | --- |
| Аутентификация | /v1/auth/ |
| CRM (несколько наборов) | /v1/crm/ |
| Настройки CRM | /v1/crm/settings/ |
| Интеграции CRM | /v1/crm/integrations/ |
| Финансы | /v1/finances/ |
| Каталог и общие сущности | /v1/shared/ |
| Управление сайтом | /v1/website/ |
| Компании | /v1/tenant/ |
| Биллинг | /v1/billing/ |
| Новости | /v1/news/ |
| Вложения | /v1/attachments/ |
| Уведомления | /v1/notifications/ |
| Документы (v2) | /v2/documents/ |
| Продажи | /v1/sales/ |
| Мастерская | /v1/workshop/ |
| Магазин | /v1/shop/ |
| Plus-продукты | /v1/plus/ |
| Kaspi | /v1/kaspi/ |
| Автопарк | /v1/fleet/ |
| Сервис автомобильных штрафов (авто) | /v1/cars/ |
| SMS | /v1/sms/ |
| Чёрный список | /v1/blacklist/ |
| Wallet (пасскарты) | /wallet/ |
| Публичные аренды | /v1/rents/ |
| AI-ассистент | /v1/assistant/ |

### CRM собирается из нескольких наборов под одним префиксом

Раздел CRM — самый крупный, поэтому его адреса физически разбиты на несколько независимых наборов (Конфигурация, Основное, Права доступа, Аренда, Аналитика, Дашборд), и все они подключены к **одному и тому же** префиксу /v1/crm/. Для пользователя это выглядит как единый раздел CRM; внутри же каждый набор развивается отдельно. Финансы, хотя и относятся к CRM по смыслу, вынесены под собственный префикс /v1/finances/.

### Геолокация подключена «внутри интеграций»

Раздел GPS/геолокация подключён внутри интеграций — по адресу вида /v1/crm/integrations/geolocation/. Это отражает бизнес-логику: отслеживание техники — часть подсистемы интеграций.

<Warning>
Адрес, под которым геолокация показана в документации, и адрес, по которому она реально отвечает, различаются. В карте разделов документации геолокация описана как самостоятельный короткий адрес (/v1/geolocation/), а фактически запросы обслуживаются по адресу внутри интеграций (/v1/crm/integrations/geolocation/) — короткого самостоятельного адреса в рабочей таблице маршрутов нет вовсе. При интеграции ориентируйтесь на реальный рабочий адрес, а не только на страницу документации.
</Warning>

### Локализованная админка и служебные адреса

Помимо разделов приложений, таблица маршрутов подключает служебные адреса: проверку доступности, проверку существования компании, индекс документации, админ-панель, метрики мониторинга, редактор текста и переключение языка. Админ-панель подключена дважды — обычным адресом и в локализованном варианте (под языковыми префиксами), чтобы интерфейс администратора открывался на нужном языке.

## Документация API: группы и их страницы

Документация API организована вокруг **реестра групп**: это перечень логических разделов (Аутентификация, CRM-наборы, Финансы, Компании, Интеграции и т. д.), где каждой группе сопоставлен свой набор адресов. По этому реестру система в цикле, автоматически, создаёт для **каждой** группы три служебных адреса:

| Что генерируется | Назначение |
| --- | --- |
| OpenAPI-описание группы в формате JSON | Машиночитаемое описание только адресов этой группы; путь вида `/v1/docs/openapi/<ключ>.json` |
| Схема группы | Технический источник схемы для интерактивной страницы |
| Swagger UI группы | Интерактивная страница «поиграть с API» по адресу `/crm/<ключ>/docs/swagger/` |

Ключевой смысл здесь — **изоляция**: описание каждой группы строится только по её собственному набору адресов, а не по всему проекту. Поэтому вместо одной гигантской и неудобной страницы получается набор компактных страниц по разделам.

<Note>
Интерактивные страницы документации (схема и Swagger UI) открываются по адресам, начинающимся с /crm/, **без** префикса версии /v1/. Только машиночитаемое OpenAPI-описание живёт под /v1/docs/. Это стоит учитывать, когда ищете ссылку на документацию конкретного раздела.
</Note>

### Метаданные разделов и индекс документации

Отдельно ведётся **справочник метаданных разделов**: для каждого раздела там задано человекочитаемое название, описание и иконка. Ключи этого справочника должны соответствовать ключам реестра групп — у каждого раздела из справочника обязан существовать сгенерированный адрес OpenAPI.

Вью **индекса документации** (адрес /v1/docs/) отдаёт единый JSON-список всех разделов. По каждому разделу возвращаются ключ, название, описание, иконка и, что важно, **абсолютная ссылка** на его OpenAPI-описание. Эта ссылка строится динамически от текущего адреса запроса — то есть на стенде и на проде она автоматически указывает на правильный домен, её не нужно прописывать вручную.

<Warning>
Справочник метаданных разделов не должен «убегать вперёд» реестра групп: у каждого раздела из справочника обязан существовать сгенерированный адрес OpenAPI. Если добавить раздел в справочник, но забыть про реестр групп, индекс документации перестанет собираться, потому что ссылку на несуществующий адрес построить нельзя. В обратную сторону мягче: раздел, который есть в реестре, но отсутствует в справочнике, просто не попадёт в список разделов — без ошибки.
</Warning>

### Небольшие расхождения между названиями и содержимым

- Группа документации **Wallet** по смыслу описывает пасскарты, но технически показывает адреса раздела **Kaspi** — именно Kaspi отвечает за пасскарты Apple и Google.
- Раздел **Публичные аренды** есть в рабочей таблице маршрутов, но **не входит** ни в реестр групп, ни в справочник разделов — то есть отдельной страницы документации у него нет.

## Служебные вью

### Проверка доступности

Простейшая проверка «жив ли сервис»: по адресу /health/ всегда возвращается короткий ответ со статусом «ok». Она не обращается к базе данных и не проверяет компанию — это лёгкая проба живости для балансировщика и мониторинга, которая отвечает мгновенно.

### Проверка существования компании

Вью по адресу /exists/ отвечает на вопрос «обслуживает ли платформа компанию на этом домене». Логика такая:

1. Берётся домен запроса — сначала из заголовка источника (Origin), а если его нет, то из хоста запроса; порт и приставка «www.» отбрасываются.
2. Домен нормализуется: служебные приставки «manager.», «stage.», «dev.», «api.» убираются, а локальный адрес разработки заменяется на основной рабочий домен. Так и локальная разработка, и стенд, и разные поддомены сводятся к одному «каноническому» имени компании.
3. Для одного зарезервированного домена (такси-поддомен основного сайта) ответ всегда «не существует» — этот домен намеренно исключён.
4. Во всех остальных случаях ответ — «существует».

<Info>
Проверка существования сейчас работает как «список исключений»: она отвечает «да» практически для любого домена, кроме одного зарезервированного, и не сверяется с фактическим списком заведённых компаний. Это осознанно лёгкая проверка на уровне маршрутизации.
</Info>

## Дашборд админ-панели

Главная страница админ-панели (на движке Unfold) наполняется отдельным колбэком дашборда. Он собирает сводную картину по всей платформе за выбранный период и кладёт её в контекст страницы.

### Выбор периода

Наверху дашборда — форма фильтра дат с двумя полями («Дата с» и «Дата по») и календарными виджетами. Логика периода:

- Если даты не заданы, берётся **последние 30 дней** (диапазон по умолчанию), включая сегодняшний день.
- Если пользователь по ошибке указал начало позже конца, даты автоматически меняются местами.
- Выбранный диапазон запоминается в служебной строке параметров, чтобы он сохранялся при перелистывании таблиц.

### Что показывает дашборд

| Блок | Что содержит |
| --- | --- |
| KPI-карточки | Подтверждённая выручка за период (со счётчиком «сколько счетов подтверждено из общего числа» и сколько ожидают), число активных интеграций (в т. ч. демо), число компаний (и сколько появилось новых за период), число сотрудников компаний (и сколько среди них супер-пользователей) |
| График выручки по неделям | Подтверждённая выручка, сгруппированная по неделям выбранного периода |
| График счетов по статусам | Количество счетов в разбивке по статусам оплаты |
| Таблица последних счетов | Свежие счета с датой, компанией, статусом и суммой; постранично, по 10 на страницу |
| Таблица топ-интеграций | Интеграции по числу подключений, с разбивкой на демо и платные; постранично, по 10 на страницу |

Выручка в KPI и на графике по неделям считается **только по подтверждённым** счетам — по фактически захваченной сумме, а не по выставленной. (В таблице последних счетов сумма каждой строки, наоборот, показывается по выставленному итогу счёта.) Для графика по неделям период выравнивается по началу недели, и недели без выручки показываются с нулём (сплошная линия без «дыр»).

<Note>
Обе таблицы дашборда листаются независимо: у счетов и у интеграций свои параметры страницы. Номер страницы всегда «зажимается» в допустимый диапазон — если запросить несуществующую страницу, откроется ближайшая корректная, ошибки не будет.
</Note>

## Как это используется на практике

- **Фронтенд и мобильные клиенты** обращаются к рабочим адресам разделов под /v1/ (и /v2/ для документов).
- **Проверка доступности** используется инфраструктурой (балансировщик, мониторинг) как быстрая проба живости.
- **Проверка существования компании** помогает клиентскому приложению понять, «есть ли здесь компания», ещё до входа.
- **Индекс документации и Swagger-страницы** используют разработчики интеграций: сначала берут список разделов из индекса, затем открывают интерактивную страницу нужного раздела.
- **Дашборд админки** — рабочий инструмент внутренней команды: обзор выручки, компаний, сотрудников и интеграций за период, прямо на главной странице админ-панели.

## Подводные камни

<Warning>
- **Рабочий и документируемый адреса геолокации расходятся.** В документации раздел показан под коротким самостоятельным адресом, но в рабочей таблице маршрутов такого короткого адреса нет вовсе — запросы обслуживаются только по адресу внутри интеграций. При интеграции ориентируйтесь на реальный рабочий адрес, а не на страницу документации.
- **Справочник разделов не должен опережать реестр групп.** Индекс документации по каждому разделу из справочника строит ссылку на его сгенерированный адрес документации. Если добавить раздел в справочник, но забыть про реестр групп, индекс перестанет собираться — ссылку на несуществующий адрес построить нельзя. В обратную сторону мягче: раздел, который есть в реестре, но отсутствует в справочнике, просто не попадёт в список, без ошибки.
</Warning>

- Раздел CRM подключён к своему префиксу сразу несколькими независимыми наборами адресов (конфигурация, основное, права, аренда, аналитика, дашборд) — для пользователя это один раздел, но внутри несколько источников маршрутов.
- Группа документации «Wallet» технически показывает адреса раздела Kaspi — именно он отвечает за пасскарты.
- Раздел «Публичные аренды» есть в рабочей таблице маршрутов, но отсутствует и в реестре групп, и в справочнике разделов — отдельной страницы документации у него нет.
- Интерактивные страницы документации (схема и Swagger UI) открываются по адресам без префикса версии; только машиночитаемое OpenAPI-описание живёт под адресом с версией.
- Проверка существования компании работает как список исключений: отвечает «да» почти для любого домена и «нет» только для одного зарезервированного такси-поддомена, не сверяясь с реальным перечнем заведённых компаний.
- Нормализация домена в этой проверке выполняется простой заменой подстрок, поэтому служебные приставки вырезаются в любом месте имени, а не только в его начале.
- Проверка доступности всегда возвращает статус «ok» и не обращается к базе данных — это проба живости, а не проверка работоспособности базы.
- Таблицы дашборда листаются независимо (по 10 записей у каждой), а номер запрошенной страницы всегда зажимается в допустимый диапазон, поэтому несуществующая страница не даёт ошибки.
- Выручка в KPI и на графике по неделям считается только по подтверждённым счетам и по фактически захваченной сумме, тогда как в таблице последних счетов сумма строки берётся по выставленному итогу — это важно при сверке.
