Полный перечень полей — в [глоссарии](/ru/logic/binotel-glossary). Подключение и работа с разделом глазами пользователя — на странице [«Binotel»](/binotel).

## Что делает интеграция

Интеграция забирает у Binotel звонки компании, хранит их у себя и показывает поверх них дашборд, историю с фильтрами и записи разговоров. Звонки сопоставляются с клиентами по номеру телефона, поэтому в истории виден клиент, а в карточке клиента — его звонки. Отдельно остаётся давняя возможность **позвонить клиенту** из карточки: Yume просит Binotel соединить внутренний номер сотрудника с номером клиента.

Binotel ограничивает частоту тяжёлых запросов статистики (пять в минуту) и отдаёт не больше двух тысяч звонков за ответ, поэтому вся синхронизация построена вокруг этих двух пределов: регулярная работа идёт дешёвыми «с момента» запросами, а история подтягивается порциями, по одной фоновой задаче на порцию.

## Модель данных

### Подключение Binotel

Состояние интеграции у одной компании: персональный ключ вебхука, курсоры синхронизации, ход импорта истории и кэш списка сотрудников. Оно хранится отдельно от самого подключения интеграции, потому что данные подключения переписываются целиком при каждом переподключении.

| Поле | Назначение |
| --- | --- |
| Ключ вебхука | Случайная строка в адресе вебхука; по ней Binotel «узнаётся» компанией. Можно перевыпустить из админки |
| Курсор синхронизации | Момент самого свежего известного звонка; от него (с нахлёстом) идёт следующая синхронизация |
| Последняя удачная синхронизация, последняя ошибка | Для диагностики и статуса на странице интеграции |
| Ключ отклонён | Момент, когда Binotel отверг ключ или секрет; пока подключение не отредактировано, синхронизация не запускается |
| Последний вебхук | Когда последний раз приходил звонок по вебхуку |
| Импорт истории: статус, начало, прогресс, окончание | Ход загрузки истории за 90 дней: ожидает, идёт, завершён, сбой |
| Сотрудники | Кэш списка сотрудников Binotel (имя, отдел, внутренний номер) по адресу почты и момент его обновления |

### Звонок Binotel

Один звонок, уникальный внутри компании по идентификатору звонка в Binotel. Звонки всех компаний лежат в общей таблице с признаком компании.

| Группа полей | Что хранится |
| --- | --- |
| Идентификация | Идентификатор звонка и идентификатор компании в Binotel |
| Время и направление | Момент начала; входящий или исходящий |
| Номера | Внутренний номер и номер группы сотрудника; номер клиента как пришёл, только его цифры и последние девять цифр — для сопоставления |
| Длительности | Ожидание и разговор в секундах |
| Состояние | Статус звонка кодом Binotel; признак первого звонка с этого номера |
| Клиент и сотрудник по данным Binotel | Идентификатор и имя клиента в Binotel; имя и почта сотрудника |
| Номер АТС | Номер и его название |
| Есть запись | Выводится из статуса: запись существует только у состоявшихся разговоров |
| Источник | Откуда пришёл звонок: периодическая синхронизация, импорт истории или вебхук |
| Исходные данные | Ответ Binotel целиком |

## Откуда берутся звонки

### Периодическая синхронизация

Каждые пять минут общая задача раскладывается на одну задачу на каждую подключённую компанию. Задача компании:

1. Берёт **блокировку** на десять минут — параллельный запуск по той же компании завершится сразу.
2. Пропускает компанию, у которой Binotel отклонил ключ после последнего редактирования подключения.
3. Запрашивает входящие и исходящие звонки **с момента курсора минус 15 минут** нахлёста (или за последние сутки, если курсора ещё нет).
4. Если ответ упёрся в предел в две тысячи звонков, сдвигает курсор на самый свежий полученный звонок и повторяет — не больше десяти страниц за запуск.
5. Звонки, которые больше пяти минут висят в состоянии «в разговоре», перепроверяет отдельным запросом деталей (до ста за раз).
6. Записывает новый курсор, момент удачной синхронизации, снимает ошибку и гасит плашки сбоя интеграции.

### Импорт истории

При подключении запускается импорт истории за **90 дней**. Он идёт порциями по **семь дней**, каждая порция — отдельная фоновая задача, между ними пауза около тринадцати секунд под предел «пять тяжёлых запросов в минуту». Если ответ по порции упёрся в две тысячи звонков, окно **делится пополам** и обе половины ставятся в очередь заново — так ни один звонок не теряется за пределом ответа; делить окно короче часа задача не станет. По завершении курсор синхронизации выставляется на конец импорта, если он был старее.

Импорт запускается и при повторном подключении: если истории ещё не было — целиком, если с последней синхронизации прошло больше суток — от курсора, иначе достаточно обычной синхронизации.

### Вебхук

Binotel умеет присылать завершённый звонок сразу (метод API CALL COMPLETED), но не подписывает свои запросы. Поэтому компания определяется по **ключу в адресе** вебхука, а отправитель проверяется по **опубликованным адресам серверов Binotel**; запрос с другого адреса отклоняется. Адрес вебхука показан на странице интеграции — его передают в поддержку Binotel.

Вебхук всегда отвечает «успех», как только звонок сохранён, иначе Binotel будет повторять доставку семь раз в течение 38 часов. Компании с истёкшим подключением он тоже отвечает «успех», но ничего не сохраняет. Запросы другого типа и без деталей звонка подтверждаются и пропускаются.

### Правило слияния

Три источника пишут в одну таблицу, поэтому действует одно правило: **звонок «в разговоре» никогда не перезаписывает уже сохранённый окончательный статус**. Так запоздавший ответ синхронизации не откатит то, что вебхук уже завершил. Внутри одной пачки при повторе идентификатора побеждает последнее вхождение; у известного звонка обновляются все поля, кроме идентификатора и компании.

## Сопоставление с клиентами

Клиенты лежат в данных компании, а звонки — в общей таблице, поэтому объединить их запросом нельзя. Сопоставление делается **при чтении**, одним запросом на страницу результатов:

- точное совпадение — по номеру с плюсом и всеми цифрами;
- совпадение по **последним девяти цифрам** — на случай разного формата кода страны;
- если под ключ подходят несколько клиентов, побеждает **самый новый**.

Поиск в истории по тексту работает так же наоборот: цифры ищутся в номере, буквы — в имени сотрудника и имени клиента по данным Binotel, а также по клиентам Yume с таким именем (берутся первые двести совпадений, и их номера подставляются в фильтр).

## Что считается отвеченным и пропущенным

| Понятие | Статусы Binotel |
| --- | --- |
| Отвеченный | «Отвечен», «Переведён», «Голосовое сообщение» |
| Пропущенный | Входящий, не отвеченный, не SMS/факс и не «в разговоре» |
| Не разговор | SMS (отправляется, доставлено, не доставлено) и факс (принят, не принят): входят в общее число, но не считаются ни отвеченными, ни пропущенными |
| С записью | «Отвечен», «Голосовое сообщение», «Факс принят» |

Среднее ожидание считается только по входящим, средний разговор — только по отвеченным.

## Дашборд и история

Все отчёты читают только сохранённые звонки — к Binotel при открытии страницы система не обращается. Период без явных границ — текущий месяц; границы приводятся к часовому поясу компании.

| Отчёт | Что отдаёт |
| --- | --- |
| Сводка | Всего, входящие, исходящие, отвечено, пропущено, среднее ожидание, средний и суммарный разговор, уникальных номеров |
| По дням | Входящие, исходящие, отвечено и пропущено на каждый день периода; дни без звонков отдаются нулями, чтобы на графике был столбик на каждый день |
| По сотрудникам | Всего, отвечено, пропущено, средний и суммарный разговор — по почте сотрудника |
| История | Постраничный список с фильтрами: направление, статусы, сотрудник, только пропущенные, номер, поиск; сортировка по времени, ожиданию и разговору |
| Сотрудники для фильтра | Кэш Binotel плюс все, кто встречается в сохранённых звонках |

На дашборде интерфейс по умолчанию показывает последние семь дней и десять свежих пропущенных; в истории — текущий месяц. В карточке клиента история встроена с фильтром по номеру клиента.

## Записи разговоров

Binotel хранит запись только для состоявшихся разговоров, а выданная ссылка действует **пятнадцать минут**, поэтому ссылка запрашивается по нажатию и не сохраняется. У звонка, о котором известно, что записи нет, ответ «записи нет» приходит без обращения к Binotel. Ошибки различаются: неверный ключ или отключённая компания — сбой шлюза; запись не найдена — «недоступна»; нет связи с Binotel — шлюз недоступен. Плеер при ошибке воспроизведения запрашивает свежую ссылку сам.

## Подключение и проверка ключей

При подключении пара «ключ + секрет» **проверяется у Binotel** дешёвым запросом списка сотрудников. Неверные ключи, отключённая компания, временное ограничение или недоступность API возвращаются как ошибка формы — подключение не сохраняется. После удачного подключения в фоне запускаются обновление сотрудников и импорт истории.

Список сотрудников также обновляется по всем компаниям **ежедневно в 04:20**. Ручная синхронизация с кнопки «Обновить» ставит задачу компании в очередь, но не чаще одного раза в минуту — повторное нажатие получает отказ с указанием, сколько ждать.

## Поведение при сбоях

| Что случилось | Что делает система |
| --- | --- |
| Binotel отклонил ключ или секрет | Плашка сбоя «ключ отклонён»; момент отказа записывается, синхронизация не запускается, пока подключение не отредактировано |
| Компания отключена на стороне Binotel | Плашка «отключено»; дальнейшие попытки прекращаются так же |
| Binotel ограничил частоту | Клиент один раз ждёт десять секунд и повторяет; задача синхронизации повторяется через пятнадцать секунд |
| Другая ошибка API или нет связи | Задача повторяется до трёх раз с минутной паузой; после исчерпания повторов — плашка «не удалось синхронизировать» |
| Удачная синхронизация | Снимает все плашки сбоя интеграции Binotel |

Плашки сбоя — общий механизм интеграций; их появление считается и в метриках наблюдаемости платформы.

## Настройки окружения

| Настройка | Назначение | По умолчанию |
| --- | --- | --- |
| Адрес API Binotel | База адресов REST API | версия 4.0 |
| Внешний адрес для вебхука | С него собирается адрес, который показывается компании | адрес API Yume |
| Разрешённые адреса вебхука | Адреса серверов Binotel: одиночные, диапазоны или сети; пустой список отключает проверку (локальная разработка) | три опубликованных диапазона Binotel |
| Нахлёст синхронизации | На сколько минут назад от курсора запрашивать звонки | 15 минут |
| Глубина истории | За сколько дней импортировать историю при подключении | 90 дней |
| Порция истории | Длина одного окна импорта | 7 дней |
| Пауза между тяжёлыми запросами | Под предел «пять запросов в минуту» | 13 секунд |
| Пауза при ограничении частоты | Сколько ждать перед единственным повтором | 10 секунд |
| Окно ручной синхронизации | Как часто можно нажимать «Обновить» | 60 секунд |

## Особенности поведения

- Звонки хранятся в общей таблице с признаком компании и уникальны по паре «компания + идентификатор звонка».
- Статус «в разговоре» не перезаписывает окончательный статус ни из какого источника.
- Ответ Binotel, упёршийся в две тысячи звонков, при синхронизации сдвигает курсор и читается дальше, при импорте истории — делит окно пополам.
- Клиент подставляется при чтении по номеру целиком или по последним девяти цифрам; при нескольких совпадениях берётся самый новый клиент.
- Вебхук проверяет адрес отправителя по списку адресов Binotel и ключ компании в адресе; подписи у запросов Binotel нет.
- Неактивное подключение подтверждает вебхук, но не сохраняет звонок.
- Ссылка на запись живёт пятнадцать минут и не хранится; звонки без записи не ходят в Binotel.
- Ключи проверяются при подключении; отклонённый позже ключ останавливает синхронизацию до редактирования подключения.
- Ручная синхронизация ограничена одним запуском в минуту на компанию.
