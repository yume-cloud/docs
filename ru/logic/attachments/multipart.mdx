Когда нужно прикрепить к объекту большой файл, передавать его одним запросом неэффективно и ненадёжно. Для таких случаев
предусмотрена прямая загрузка в S3-совместимое хранилище по частям: сам файл минует сервер приложения и уходит напрямую в
хранилище, а сервер лишь координирует процесс, выдавая временные ссылки. Сервер вмешивается только в начале (подготовка) и
в конце (закрепление файла и создание записи-вложения). Результатом успешной загрузки становится обычный
[прикреплённый файл](/ru/logic/attachments/files).

<Info>
Файл не проходит через сервер приложения. Каждая часть отправляется браузером или мобильным приложением напрямую в
хранилище по временной ссылке. Это снимает нагрузку с сервера и позволяет загружать файлы, размер которых значительно
превышает обычные лимиты запроса.
</Info>

## Логика

Весь процесс доступен только авторизованным пользователям и состоит из четырёх независимых шагов.

**Шаг 1. Инициализация.** Клиент передаёт имя файла и, по желанию, тип содержимого; если тип не указан, применяется
универсальное значение для двоичных данных. Система извлекает расширение из имени файла (в нижнем регистре), формирует
уникальный ключ хранения в папке для файлов, где имя заменяется на случайный идентификатор с сохранением расширения (так
исходное имя в хранилище не фигурирует и коллизии имён исключены), и открывает в хранилище сессию многочастной загрузки. В
ответ клиент получает идентификатор загрузки и ключ хранения.

<Note>
Ключ хранения и идентификатор загрузки формируются один раз на этом шаге. Все дальнейшие запросы (получение ссылок на
части, завершение, отмена) должны использовать именно эту пару — сервер их между запросами не запоминает.
</Note>

**Шаг 2. Получение ссылки на часть.** Клиент разбивает файл на части и для каждой части запрашивает временную ссылку,
передавая идентификатор загрузки, ключ хранения и порядковый номер части. По полученной ссылке клиент напрямую отправляет
данные части в хранилище. Части можно загружать параллельно — важен лишь корректный порядковый номер каждой части.

<Warning>
Временная ссылка на загрузку части действует **1 час**. Если загрузка занимает дольше или клиент запросил ссылку заранее
и не успел ею воспользоваться, ссылку нужно запросить заново.
</Warning>

**Шаг 3. Завершение и создание вложения.** После отправки всех частей клиент вызывает завершение и передаёт:

| Поле | Тип | Назначение |
|------|-----|------------|
| Идентификатор загрузки | строка | Сессия загрузки, открытая на шаге 1 |
| Ключ хранения | строка | Путь файла в хранилище |
| Список частей | список | Части с их порядковыми номерами и идентификаторами (для «сборки» файла) |
| Тип объекта | текст | Имя вида родительского объекта |
| Идентификатор объекта | число | Идентификатор конкретного родительского объекта |
| Категория | текст | Необязательная метка-категория файла |
| Имя файла | текст | Необязательное название |

Список частей принудительно сортируется сервером по порядковому номеру (поэтому клиент может передавать части в
произвольном порядке), хранилищу отправляется команда собрать части в единый файл, по имени типа объекта определяется вид
родительского объекта, а расширение вычисляется из ключа хранения (если определить не удалось — применяется значение по
умолчанию для двоичных данных). Затем создаётся запись-вложение: компания и автор берутся из контекста запроса, категория
и название — из запроса (если указаны), полиморфная привязка — из переданных типа и идентификатора объекта. Ссылка на сам
файл устанавливается на уже загруженный объект хранилища по его ключу — файл повторно не загружается.

<Info>
На шаге завершения новый файл не передаётся — запись-вложение лишь «закрепляется» за уже собранным в хранилище файлом.
Вложение в системе появляется только после успешного завершения; до этого момента в хранилище есть незавершённая
загрузка, но записи в системе нет.
</Info>

**Шаг 4. Отмена.** Если загрузку нужно прервать, клиент вызывает отмену с идентификатором загрузки и ключом хранения.
Хранилищу отправляется команда прервать многочастную загрузку — уже отправленные части удаляются, файл не собирается,
система отвечает пустым успешным ответом.

## Подводные камни

<Warning>
**«Повисшие» и осиротевшие файлы.** Отмена незавершённой загрузки полностью на стороне клиента: сервер не отслеживает и не
удаляет незавершённые многочастные загрузки. Кроме того, запись-вложение создаётся только на шаге завершения, тогда как
файл физически собирается в хранилище раньше — если завершение не вызвано, в хранилище остаётся файл без записи в системе.
</Warning>

Прочие особенности:

- **Определение вида родительского объекта идёт только по имени вида** без учёта приложения — при совпадении имён в разных приложениях поиск завершится ошибкой из-за неоднозначности.
- **Обязательные поля берутся напрямую, без предварительной проверки** — отсутствие имени файла, идентификатора загрузки, ключа хранения, номера части или списка частей приведёт к внутренней ошибке вместо аккуратного ответа о некорректном запросе.
- **Расширение вычисляется из ключа хранения** (то есть из исходного имени файла на шаге инициализации), а не из типа содержимого; при отсутствии расширения подставляется значение по умолчанию для двоичных данных.
