## Логика

Компания оплачивает право на подписание определённого числа документов через покупку пакета подписей. Пакет привязывается к тарифу и к позиции счёта, а по мере подписания документов из пакета списываются единицы. Отдельно в системе предусмотрена сущность «баланс документов» на период — но она не подключена ни к одному бизнес-процессу (см. предупреждение ниже). Есть и специальная проверка доступа, которая по замыслу должна блокировать подписание при исчерпании квоты, но в текущей версии полностью отключена.

<Warning>
Проверка исчерпания квоты подписей фактически отключена во всём модуле: и в проверке доступа перед подписанием, и в валидации части сценариев подписания. Счётчики пакета (использовано/остаток) продолжают вестись и отображаться в API, но ни один запрос на подписание сейчас не блокируется из-за нехватки квоты.
</Warning>

### Пакет подписей документов

Пакет — разовая порция лимита подписей, выданная компании в привязке к тарифу и/или к позиции счёта. Остаток и признак «Активен» — вычисляемые свойства (не хранятся в базе): остаток — это «Всего» минус «Использовано», но не меньше нуля; активен — когда остаток больше нуля.

**Как появляется пакет.** Создаётся автоматически при подтверждении оплаты счёта компании — для каждой позиции подтверждённого счёта, которая относится к тарифу с типом «количество» и принадлежит продукту подписания документов, создаётся один новый пакет с лимитом из количества, указанного в тарифе. Старые пакеты не продлеваются и не суммируются — они накапливаются как отдельные записи.

**Общий остаток компании** — это сумма остатков всех её пакетов с ненулевым остатком; если у компании нет ни одного пакета, общий остаток равен нулю.

**Списание подписи из пакета** происходит автоматически при переходе конкретной подписи документа в статус «Подписан» (то есть на каждую подпись каждого подписанта):

1. Среди пакетов компании выбирается самый старый по дате создания пакет с ненулевым остатком.
2. Если такого пакета нет — квота не списывается, документ подписывается как обычно.
3. Если пакет найден, но документ уже был списан именно из него ранее — повторного списания не происходит.
4. Иначе — «Использовано» увеличивается на единицу, создаётся запись расхода, отправляется веб-уведомление о новом значении.

<Tip>
Пакеты расходуются по принципу «сначала старый»: пока у самого раннего пакета остаётся хотя бы одна свободная подпись, списание идёт именно из него.
</Tip>

<Warning>
Поскольку списание привязано к каждой отдельной подписи, а проверка «уже списано» — к конкретной паре пакет+документ, возможен пограничный случай: если у документа несколько подписантов и ровно между их подписаниями самый старый пакет исчерпывается, подпись второго подписанта спишется уже из следующего пакета — один документ может списать не одну, а две (или больше) единицы квоты. Для документов с одним подписантом такого эффекта нет.
</Warning>

### Баланс документов

Отдельная сущность — счётчик суммы для компании на определённый период (даты начала и окончания). Не является частью процесса пакетов подписей выше.

<Warning>
На данный момент баланс документов нигде не создаётся, не обновляется и не проверяется — ни при оплате счетов, ни при подписании документов. Модель существует в базе данных (у неё даже нет регистрации в административной панели, в отличие от пакетов), но не подключена ни к одному бизнес-процессу.
</Warning>

### Разрешение на подписание по квоте документов

Эта проверка подключена к адресам инициации подписи со стороны компании и к части публичных адресов клиентской ссылки. Она не подключена к созданию документа и не подключена к первому шагу публичного подписания по SMS-ссылке. По замыслу проверка должна пропускать запросы без исчерпания квоты, при исчерпании — смотреть на резервный тарифный лимит, а при его отсутствии — отклонять запрос.

<Warning>
В текущей реализации весь этот сценарий отключён, и разрешение всегда сразу пропускает запрос. При этом здесь нет даже базовой «технической» защиты за счёт наследования — родительский механизм сам по себе не содержит проверки доступа. Дополнительно: резервный лимит «подписание документов» не входит в перечень типов лимитов подписки, заведённых в системе на сегодня — то есть даже при включении этой проверки резервная ветка никогда не нашла бы такой лимит.
</Warning>

Аналогично, в сценариях SMS и ЕГОВ/ЭЦП есть общая проверка квоты перед сохранением подписи, но её тело отключено. В сценарии ручного подписания такой проверки нет вовсе — ни рабочей, ни отключённой.

### Что видит компания через API пакетов

- **Список пакетов документов** — полный список компании одним ответом, без пагинации, отсортированный от самого старого к новому; для каждого пакета отдаётся краткое описание тарифа, лимит, использовано, вычисленные остаток и активность. Все поля только на чтение.
- **Остаток подписей компании** — отдельный адрес с одним числом: суммарный остаток по всем активным пакетам.

Оба адреса доступны только пользователям с соответствующим правом доступа (staff-права), обычным клиентам компании не открыты.

## Особенности поведения

- Проверка квоты подключена не ко всем сценариям: она отсутствует у создания документа и у первого шага публичного подписания по SMS-ссылке (отправка кода клиенту). Сценарий ручного подписания не содержит проверки квоты вовсе.
- Списание одной единицы из пакета происходит по факту перехода каждой отдельной подписи в статус «Подписан» (для каждого подписанта отдельно), а не единовременно, когда документ становится полностью подписан.
- Если у документа несколько подписантов и самый старый доступный пакет исчерпывается ровно между их подписаниями, документ может списать квоту из двух разных пакетов вместо одного.
- Пакет создаётся автоматически только для позиций счёта с тарифом типа «количество»; проверка на повторное создание идёт по позиции счёта, поэтому один счёт с несколькими такими позициями создаёт несколько независимых пакетов.
- «Тариф» и «Счёт» у пакета могут быть пустыми — это не мешает вычислению остатка/активности, так как они зависят только от «Всего» и «Использовано».
