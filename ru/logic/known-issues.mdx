Здесь собраны все находки из разбора бизнес-логики системы: технический долг, потенциальные баги, неочевидные ограничения и расхождения источников истины. Раздел сгруппирован по страницам «Логики системы» — каждый заголовок ведёт на соответствующий модуль.

<Note>
Приоритет указан в начале каждого пункта: **высокий** — влияет на суммы, деньги или безопасность и требует внимания; **средний** — техдолг или логическая несогласованность с ограниченным эффектом; **низкий** — наблюдение, опечатка или мёртвый код без явного влияния. Краткая сводка по приоритетам — в начале этой страницы.
</Note>

| Кэш резолвинга компании живёт 24 часа и кэширует «не найдено» | Ключи компании (по идентификатору, по имени схемы, по каждому домену) гасятся при любом изменении компании и домена, включая массовое обновление; отрицательный ответ живёт 60 с, добавление домена гасит его сразу; срок жизни ключа стал одинаковым во всех местах, где он писался | [#1364](https://github.com/yume-cloud/backend/issues/1364) |
| Добор компании по токену может выставить контекст компании на «пустую» компанию | Нерезолвящийся идентификатор компании даёт `403 tenant_required` вместо внутренней ошибки; пустое значение больше не кэшируется | [#1366](https://github.com/yume-cloud/backend/issues/1366) |
| Кэш ролей в компании живёт вечно и не сбрасывается при смене роли | Ролевые ключи и ключ участия гасятся при любом изменении членства — сохранение, удаление, массовое обновление; срок жизни задан явно (5 минут) | [#1395](https://github.com/yume-cloud/backend/issues/1395) |
| Кэш прав группы живёт сутки и не сбрасывается при изменении прав | Сброс переехал на изменение состава прав группы, поэтому работает независимо от того, где права меняли — редактор роли в CRM, админка или код | [#1397](https://github.com/yume-cloud/backend/issues/1397) |
| Кэш подключённой интеграции не сбрасывается при массовом обновлении | Массовое обновление подключений гасит ключ затронутых записей; в частности сессия Kaspi Pay, которая пишется в обход сохранения, больше не расходится с базой | [#1414](https://github.com/yume-cloud/backend/pull/1414) |
| Признак активности проверяется по закэшированной копии аккаунта | Копия аккаунта гасится при любом отзыве доступа, а не только при сохранении карточки: массовое обновление и удаление аккаунта закрывают доступ сразу. Признак по-прежнему читается из кэша, поэтому обычный запрос не платит лишним чтением базы | [#1393](https://github.com/yume-cloud/backend/issues/1393) |

## Исправлено в релизе 4–5 августа 2026

Ниже — находки этой страницы, закрытые в релизе. Они убраны из сводки по приоритетам и из разделов; список оставлен, чтобы к нему можно было вернуться при разборе старых расхождений в данных.

| Находка | Что стало |
| --- | --- |
| Права на скидку «из справочника» и «ручную» объявлены, но нигде не проверяются | Проверяются на всех операциях, включая снятие скидки; нужное право определяется по ссылке на справочник, а не по типу из запроса |
| Логика скидок смешивает два разных перечня значений | Каждая сторона сравнения называет своё перечисление; суммы не изменились |
| Автор скидки связан отношением «один к одному» | Обычная связь «один ко многим» (исправлено ещё в июле, уникальное ограничение снято миграцией) |
| Дублирование формулы стоимости услуги | Осталась одна формула — центральный пересчёт; он же теперь запускается при создании и изменении услуги |
| Два разных порога перехода аренды в «Завершена» | Одно правило на все три пути. **Сама формулировка была неверна:** порог всегда был один, штрафы в расчёт статуса не входят нигде — расходились условия по позициям (строки-замены, непереданная продажа) |
| Автоматический штраф пишут два источника с разной логикой | Единственный владелец — центральный пересчёт; сохранение и удаление ручного штрафа больше не затирает автоматическую сумму |
| Возврат залога не создаёт компенсирующую операцию | Создаётся встречная расходная операция по сальдо, с того же счёта; действие идемпотентно |
| Доля оплаты может превышать 100% | Ограничена единицей сверху — дневная прибыль не выходит за плановую сумму |
| Расчёт окупаемости агрегирует прибыль без единого фильтра | Применяется общий фильтр зачётных строк; после обновления стоит один раз пересчитать окупаемость |
| Амортизация ограничена 12 месяцами | Считается по фактическому сроку службы; изношенная позиция даёт остаток 0, позиция без даты покупки — полный остаток |
| Присвоение рейтинга клиента сравнивает число аренд с денежным порогом | Порог «по обороту» сравнивается с суммой завершённых аренд; оба пути назначения метки согласованы |
| Максимальная сумма бонусов не проверяется на положительность | Ограничена нулём снизу; списание больше не увеличивает баланс клиента |
| В ядре вычисления статуса инвентаря захардкожен идентификатор одной компании | Заменено признаком этапа мастерской «занимает единицу», которым владеет сама компания |
| Триггеры воронки и алертов молча теряют ошибки | Вынесены в фоновую задачу после фиксации изменений, сбои видны. Осталось: начисление бонуса |
| Модульные метрики закрыты лишь проверкой авторизации | Закрыты набором прав раздела. Осталось: набор пропускает по любому праву, а не по соответствующему отчёту |

## Инвентарь

[Открыть страницу модуля →](/ru/logic/inventory)

Критичных багов, ломающих аренду, не найдено, но есть заметный техдолг и несколько потенциальных проблем.

<AccordionGroup>
<Accordion title="высокий — утечка внутренних данных в ответ при ошибке импорта">
При ошибке импорта экземпляров запрос завершается общей ошибкой с текстом. При этом в поле ошибки конкретной строки складываются значения внутренних переменных, участвовавших в обработке. Это потенциальная утечка внутренних данных в ответ клиенту.
</Accordion>
<Accordion title="средний — расхождение источника истины по субаренде">
Есть отдельная сущность «Периоды субаренды» с периодами и процентом, доступная в админке, но фактические расчёты дохода и фильтры используют поля владельца субаренды и процента субаренды прямо на единице инвентаря. Сущность с периодами в разделении выручки не участвует — двойной источник истины, который легко рассинхронизировать.
</Accordion>
<Accordion title="средний — при импорте товаров закупочная цена и дата считаются, но не сохраняются">
При импорте товаров с генерацией экземпляров закупочная цена и дата закупки используются во втором проходе (при создании экземпляров), но в первом проходе те же значения вычисляются и никак не применяются — мёртвый код, сбивающий с толку при чтении.
</Accordion>
<Accordion title="низкий — опечатка в списке разрешённых расширений файлов импорта">
В списке разрешённых расширений файлов импорта одно из значений записано с опечаткой (перепутан порядок букв в «xlsx»). Список, впрочем, нигде не используется, так что эффекта нет, но он вводит в заблуждение.
</Accordion>
<Accordion title="низкий — перенос между точками не проверяет принадлежность компании">
Массовый перенос экземпляров между точками проката отбирает записи по переданным идентификаторам без проверки, что все они существуют и принадлежат текущей компании. Несуществующие идентификаторы молча игнорируются, ответ всегда «успех». Аналогично массовое переназначение товара не проверяет, что целевой товар существует.
</Accordion>
<Accordion title="низкий — историческая опечатка в названии статуса «В аренде»">
Значение «В аренде» в перечне статусов единицы инвентаря исторически записано с опечаткой в коде, тогда как для статуса аренды то же состояние записано без опечатки. Опечатка закреплена в интерфейсе; переименование сломало бы клиентов, поэтому оставлено как есть.
</Accordion>
<Accordion title="низкий — выбор текущего клиента по самой поздней дате создания аренды">
Текущий клиент экземпляра выбирается как «последняя» активная аренда — по самой поздней дате создания аренды. Для экземпляра с несколькими одновременными активными арендами (что не должно случаться) выбор становится неоднозначным по бизнес-смыслу, хотя технически стабильным.
</Accordion>
</AccordionGroup>

## Товары (группы единиц)

[Открыть страницу модуля →](/ru/logic/inventory/inventory-groups)

<AccordionGroup>
<Accordion title="средний — генерация единиц товара уязвима к дубликатам артикула">
При массовом создании единиц товара их артикулы формируются как «артикул товара + порядковый номер» с выравниванием номера по трём знакам. При количестве больше 999 единиц выравнивание перестаёт работать, а артикул единицы не имеет уникального ограничения. Теоретически при повторной генерации (особенно если артикул товара менялся) новые номера могут столкнуться со старыми, и такие дубликаты не отлавливаются автоматически.
</Accordion>

<Accordion title="низкий — резерв товара не уменьшает счётчик, а создаёт бронь">
Добавление товара в аренду не меняет никакого «остатка» на товаре. Уменьшение числа свободных единиц — это следствие появления брони и пересчёта показателя при следующем запросе. Синхронизация расписания с заявкой выполняется фоновой задачей при сохранении заявки и при массовых операциях с инвентарём заявки. Прямого поля-счётчика доступности у товара нет.
</Accordion>

</AccordionGroup>

## Комплекты

[Открыть страницу модуля →](/ru/logic/inventory/inventory-sets)

<AccordionGroup>
<Accordion title="низкий — доступность позиции и доступность комплекта считаются разными способами">
Свободность отдельной позиции комплекта и свободность комплекта в целом рассчитываются двумя близкими, но не идентичными методами. Наборы исключаемых единиц слегка различаются (например, по-разному учитываются статусы ремонта и склада). Из-за этого числа доступности в списке позиций и в карточке комплекта могут немного расходиться.
</Accordion>

<Accordion title="низкий — альтернативные позиции не учитываются в сводке доступности">
При фактической выдаче комплекта единицы ищутся в объединении основного товара позиции и его альтернатив, и проверка достаточности выполняется по этому объединению. Однако сводная «доступность комплектов» считает доступность только по основному товару позиции, без учёта альтернатив. Поэтому сводка может занижать реальную возможность собрать комплект за счёт альтернативных товаров.
</Accordion>

<Accordion title="низкий — округление при перераспределении цены жёсткого комплекта зависит от порядка">
Копейка округления при перераспределении цены добавляется к последней строке выборки. Итоговая сумма экземпляра комплекта сохраняется корректно, но конкретная строка, куда попадает остаток округления, определяется порядком выборки. В отчётности по отдельным позициям это может выглядеть непоследовательно, хотя суммарно всё верно.
</Accordion>
</AccordionGroup>

## Аренда: жизненный цикл

[Открыть страницу модуля →](/ru/logic/rent/lifecycle)

<AccordionGroup>
<Accordion title="решено — Просрочка стала отдельным статусом «Просрочена»">
**Исправлено.** Раньше отдельного статуса «просрочено» не было: просрочка моделировалась флагом «Просрочено» при статусе «В аренде» и виртуальным «цветовым» ярлыком, из-за чего интерфейс и аналитика, ожидавшие отдельный статус, фильтровали неверно. Теперь «Просрочена» — полноценное значение статуса аренды: флаг «Просрочено» и «цветовой» ярлык убраны, статус выставляет и снимает пересчёт итогов, а все фильтры и счётчики проверяют «В аренде» и «Просрочена» вместе. Настройка объединения статусов в счётчиках списка (`order_merge_inrent_exceed`) сохранена. Подробнее — на странице [Аренда: жизненный цикл](/ru/logic/rent/lifecycle).
</Accordion>
<Accordion title="низкий — Внутренние названия механизмов вводят в заблуждение">
Механизм «пересчёта итогов» не создаёт дочерних заказов — это полный пересчёт той же аренды. Отдельная «ссылка на аренду» — это ссылка на оплату, а не связь между заявками. Новичок будет искать несуществующую модель «родитель — потомок».
</Accordion>
<Accordion title="низкий — Опечатка в названии поля длительности (техдолг именования)">
Поле длительности внутри системы названо с опечаткой (от английского «duration»). Оно везде используется консистентно и на поведение не влияет, но остаётся техдолгом именования.
</Accordion>
<Accordion title="низкий — Ошибка начисления бонуса молча проглатывается">
Триггеры воронки и уведомлений вынесены в отдельную фоновую задачу после фиксации изменений, поэтому их сбои теперь видны как упавшая задача. А вот начисление бонуса при сохранении аренды по-прежнему обёрнуто в перехват любых ошибок без записи в журнал — сбой начисления в мониторинге не появится.
</Accordion>
<Accordion title="низкий — Ограничение на объём автоматических штрафов за проход">
Задача автоматических штрафов обрабатывает максимум 100 штрафов за проход (раз в минуту). При большем числе просроченных аренд лишние обрабатываются в следующие циклы; в логах пишется предупреждение. Для крупных компаний возможна задержка начисления.
</Accordion>
</AccordionGroup>

## Пересчёт сумм и цен

[Открыть страницу модуля →](/ru/logic/rent/pricing)

<AccordionGroup>
<Accordion title="низкий · Деление на квант округления штрафа не защищено">
Штраф домножается и делится на квант округления. При нестандартном значении кванта (например, 0 — теоретически) деление на ноль не защищено. По умолчанию квант равен 1, так что на практике это безопасно, но проверки нижней границы этой настройки нет.
</Accordion>
<Accordion title="низкий · Нулевая длительность тарифа означает разовую тарификацию">
Тариф с нулевым периодом ведёт себя как разовый платёж: стоимость равна цене тарифа независимо от срока аренды. Это неявный «режим», не отражённый в полях тарифа в интерфейсе, — его стоит держать в виду при настройке тарифов.
</Accordion>
<Accordion title="низкий · «Итоговая сумма к оплате» — контринтуитивное название">
Поле «Итоговая сумма к оплате» содержит финальную сумму к оплате клиентом (со штрафом, налогом и доставкой), а не размер скидки. Долг рассчитывается как «итоговая сумма к оплате минус оплачено», что подтверждает этот смысл. Здесь легко ошибиться и принять это поле за размер скидки.
</Accordion>
<Accordion title="низкий · Предпросмотр периода не сохраняет данные">
Предпросмотр смены периода возвращает список тарифов, но ничего не записывает. Это, по сути, калькулятор «только для чтения», несмотря на то что вызывается операцией, обычно предназначенной для создания записей. Поведение корректное, но способ вызова может вводить в заблуждение.
</Accordion>
</AccordionGroup>

## Скидки

[Открыть страницу модуля →](/ru/logic/rent/pricing)

<Warning>
Ниже — находки по итогам разбора логики. Несколько пунктов высокого приоритета связаны с несогласованностью значений в ветвях расчёта.
</Warning>


- **высокий** — Поля справочника скидок не проверяются при применении. Срок действия («Действует с» / «Действует до»), лимит использований, признак активности и промокод нигде не контролируются перед созданием применённой скидки. Просроченную, неактивную или исчерпавшую лимит скидку можно применить без ограничений — нет ни счётчика использований, ни проверки периода.


- **средний** — Текстовое представление скидки в справочнике не покрывает способы расчёта за пределами «Процента» и «Фиксированной суммы» и возвращает пустое значение, если способ расчёта окажется вне двух известных. Некритично, но пустое текстовое представление приведёт к ошибке в админке или логах.

- **средний** — Ветка расчёта при выключенном «Суммировать скидки» помечена как устаревшая, но всё ещё исполняется, если у аренды этот признак выключен. По умолчанию признак включён, так что старый путь срабатывает лишь у явно переключённых заказов. Это устаревший путь расчёта, дублирующий логику. Стоит либо удалить, либо задокументировать как поддерживаемый.

- **средний** — Двойное определение дополнительной скидки. Значение считается и при сохранении применённой скидки, и повторно в общей процедуре пересчёта аренды. На текущий момент правила отбора дословно совпадают, так что результат идентичен. Это дублирование логики без единого источника истины: при правке одного места и забытом другом суммы разъедутся.

- **низкий** — Форма редактирования справочной скидки не позволяет менять промокод и признак удаления, тогда как чтение отдаёт все поля. Ассиметрия чтения и записи ожидаема, но стоит помнить при интеграции.

- **низкий** — В сводке по скидкам строки группируются по справочной скидке и суммируют размер скидки, а колонка суммы заказов берёт исходную сумму без скидок. Поскольку группировка идёт по строкам применённых скидок, при нескольких скидках одной группы на один заказ сумма заказа просуммируется несколько раз — возможно завышение колонки суммы в отчёте. Итоговый агрегат при этом свободен от проблемы: он суммирует итоговую сумму по уникальным арендам. Стоит перепроверить при аудите отчётов.

## Депозиты, штрафы, транзакции

[Открыть страницу модуля →](/ru/logic/rent/deposits-penalties)

<AccordionGroup>
<Accordion title="средний — избыточная защита нуля при пересчёте баланса счёта">
В формуле пересчёта баланса счёта есть подстраховка «иначе ноль», которая из-за особенности вычисления относится ко всей сумме «начальный остаток + операции», а не только к сумме операций. Сумма операций и так никогда не бывает пустой, поэтому подстраховка почти никогда не срабатывает; но если «начальный остаток + операции» окажется равным нулю, баланс явно выставится в ноль (безопасно, хотя и избыточно). Конструкция рабочая, но неочевидная — подстраховку стоит убрать для читаемости.
</Accordion>
<Accordion title="средний — расхождение определения долга и лимита оплаты">
Долг по списку аренд считается как «Итоговая сумма к оплате − Оплачено», а лимит переплаты при добавлении оплаты — как «Итоговая сумма к оплате + Сумма штрафов − Оплачено». Поскольку сумма штрафов уже входит в «Итоговую сумму к оплате», лимит фактически прибавляет штраф дважды и позволяет оплатить чуть больше «долга». Требует проверки бизнес-намерения.
</Accordion>
<Accordion title="средний — неполная проверка «не всё сразу» при привязке операции">
Проверка «нельзя привязать операцию к нескольким объектам» срабатывает только когда заданы **все четыре** объекта (аренда, продажа, мастерская, ТО) одновременно. Практический запрет «более одного объекта» держится на том, что для продажи и мастерской остальные привязки принудительно обнуляются, но сама проверка неполна (например, аренда вместе с ТО пройдут без ошибки).
</Accordion>
<Accordion title="низкий — статус залога «Принят» не выставляется автоматически">
Статус залога «Принят» объявлен, но нигде не проставляется системой — задать его можно только вручную при редактировании залога. Возврат переводит залог в статус «Возвращён» из любого состояния.
</Accordion>
<Accordion title="низкий — пачка автоштрафов ограничена 100 за цикл">
Периодическая задача обрабатывает не более 100 планировщиков штрафов за минуту. При большем числе созревших штрафов остаток переносится на следующие циклы (в журнал пишется предупреждение). При крупных инсталляциях это может создавать отставание в начислениях.
</Accordion>
<Accordion title="низкий — уведомление о создании операции игнорирует залоговые и неположительные суммы">
Уведомление о создании операции не отправляется, если сумма меньше или равна нулю, а также если операция привязана к залогу. Это осознанное поведение (залоги и возвраты не шумят), но стоит помнить при отладке отсутствующих уведомлений.
</Accordion>
</AccordionGroup>

## Метрики и аналитика

[Открыть страницу модуля →](/ru/logic/metrics)

<AccordionGroup>
<Accordion title="средний — Движение денег: остатки всегда нулевые">
При сопоставлении остатков с периодами используются несовпадающие ключи: остатки размечены по году и месяцу, а поиск ведётся по другим именам полей. В результате карта остатков схлопывается в единственный «мусорный» ключ и не находится по реальным году и месяцу. Из-за этого начальный и конечный остатки в разделе движения денег почти всегда отдают значение по умолчанию — нули.
</Accordion>

<Accordion title="средний — Показатель удержания всегда 0, отток одинаков в обоих периодах">
Показатель удержания клиентов возвращает захардкоженные нули, а показатель оттока кладёт одно и то же значение в текущий и предыдущий периоды. Значит, поля удержания и «прогресс» по оттоку в обзоре клиентов не несут смысла.
</Accordion>

<Accordion title="низкий — Пожизненная ценность: сомнительная эвристика с делением на «× 3»">
Пожизненная ценность считается как «средний платёж × клиенты с повторами / (число заявок × 3)». Множитель «3» и структура формулы не документированы и выглядят как подгонка; результат сильно зависит от объёма заявок за окно в 90 дней. Стоит перепроверить бизнес-смысл.
</Accordion>

<Accordion title="низкий — «График оттока» — это не отток, а рост базы">
График оттока считает «100 × (текущее количество − предыдущее количество) / текущее количество» по числу *созданных* клиентов накопительно — это темп прироста клиентской базы, а не отток. Название вводит в заблуждение.
</Accordion>

<Accordion title="низкий — Дублирование при подсчёте количества клиентов">
При построении графика количества клиентов один и тот же набор точек формируется дважды: первый проход лишь наполняет данные как побочный эффект, после чего строится второй, идентичный набор для вывода. Первый блок — фактически мёртвый код (дублирование).
</Accordion>

<Accordion title="низкий — Обслуживание не входит в общий фильтр прибыли, но считается в некоторых разделах">
Общий фильтр прибыли намеренно не содержит обслуживание (ТО). Однако общая дневная сводка отдельно показывает количество и сумму по обслуживанию, а плановый заработок и фактическая прибыль в той же выборке считаются уже по общему фильтру (без обслуживания). Это легко перепутать при чтении дашборда: строка «обслуживание» есть, но в итоговый плановый заработок она не включена.
</Accordion>

<Accordion title="низкий — Границы периода: несогласованность (+1 день против диапазона)">
Разные разделы по-разному трактуют длину периода: эффективность считает «всего дней = (конец − начало) + 1», а механизм заполнения пропусков для шага «день» строит диапазон без «+1», из-за чего последний день диапазона может не попасть на график. Плюс дефолтный «конец» — начало следующего месяца, что нужно учитывать при сравнении с условием «дата не позже конца периода».
</Accordion>

<Accordion title="средний — Тонкие права по разделам аналитики не работают">
Все разделы аналитики закрыты набором прав раздела, но проверка пропускает по **любому** из прав набора, а не по тому, которое соответствует конкретному отчёту. Поэтому сотрудник с одним-единственным правом аналитики читает и аналитику магазина, и мастерской, и доставок. Разделение по разделам требует новых кодов прав (для мастерской, доставок и воронки их нет вовсе) и правки ролей в каждой компании.
</Accordion>

<Accordion title="низкий — Есть неподключённая альтернативная реализация зарплатных бонусов">
Существует альтернативная реализация расчёта бонусов сотрудников с той же логикой, но она не подключена к маршрутам — используется только основная. Это потенциальный техдолг/дубль логики: при правках формул бонусов нужно менять оба места или удалить неиспользуемый вариант.
</Accordion>

<Accordion title="низкий — Исторические опечатки в названиях полей и адресах">
По всему модулю в названиях полей и адресах разделов закрепились опечатки (например, в слове «эффективность» и в «исходной длительности» при расчёте зарплат). Это уже часть публичного контракта, менять рискованно, но стоит помнить при чтении.
</Accordion>
</AccordionGroup>

  </Accordion>

  </Accordion>

  </Accordion>

## Фоновые процессы

[Открыть страницу модуля →](/ru/logic/background-tasks)

<AccordionGroup>
<Accordion title="средний — Пересчёт остаётся синхронным осознанно, но доступность считается лишним числом раз">
Центральный пересчёт аренды, пересчёт оплаты, пересчёт продажи и построение расписания платежей — обычный синхронный
код внутри обработки запроса, а не фоновые задачи. Для пересчёта аренды это осознанно: он **возвращает те суммы,
которые уходят в ответ**, и вынос в фон означал бы, что клиент видит устаревшие цены и долг, пока фон не догонит.
Пересчёт доступности инвентаря тоже оставлен синхронным намеренно — устаревшая доступность грозит двойной бронью.
Настоящий запас здесь другой: доступность пересчитывается 2–3 раза за одно изменение аренды, тогда как достаточно
одного раза. Побочные эффекты перехода статуса (уведомления и лиды воронки) из запроса уже вынесены.
</Accordion>
<Accordion title="средний — Начисление автоштрафов может копить отставание при лимите партии">
Задача обрабатывает максимум 100 штрафов за минуту. При превышении пишется предупреждение в лог, но остаток
переносится на следующие циклы. При большом числе одновременно просроченных аренд начисление штрафов будет отставать.
Ограничение осознанное, но потолок жёстко зашит и не настраивается.
</Accordion>
<Accordion title="средний — Алерт «скоро просрочка» падает, если не переданы нужные параметры">
В обработчике алерта «скоро просрочка» идентификатор аренды и идентификатор триггера присваиваются только при наличии
соответствующих ключей во входных данных. Если ключи отсутствуют, дальнейшее использование идентификатора аренды
приведёт к ошибке вместо аккуратного выхода. На практике их всегда передаёт посев штрафов, но защиты от отсутствия
параметров нет.
</Accordion>
<Accordion title="средний — Тихое проглатывание ошибок в цикле пересчёта">
В синхронизации автоматических штрафов каждый шаг (удаление / пакетное обновление / пакетное создание) обёрнут в
обработку ошибок с записью в лог, но без повторной попытки и без пометки задачи как неуспешной. Частичный сбой
приведёт к рассинхрону автоматических штрафов, который заметят только при следующем полном пересчёте (массовый
пересчёт прибыли).
</Accordion>
<Accordion title="средний — Посев штрафов: удаление лишних записей внутри цикла">
Удаление «хвоста» лишних записей штрафов происходит **внутри** цикла, а не после него. Логически это удаление
достаточно выполнить один раз; повторные вызовы безвредны, но избыточны, и общая структура запутана.
</Accordion>
<Accordion title="низкий — Двойной пересчёт поля «Оплачено»">
Поле «Оплачено» аренды считается одним и тем же выражением и в центральном пересчёте аренды, и в пересчёте оплаты
аренды. Дублирование логики: при изменении правила «какие платежи считаются» нужно править оба места.
</Accordion>
<Accordion title="низкий — Массовый пересчёт прибыли без расписания и с суточным лимитом времени">
Массовый пересчёт прибыли не входит в расписание — это ручная ремонтная задача с лимитом времени в одни сутки.
Перебирает все компании последовательно; на большом числе компаний один прогон может быть очень долгим. Запускать
точечно по конкретной компании или конкретной аренде.
</Accordion>
<Accordion title="низкий — Наполнение аренды Yume Plus вызывается и синхронно, и асинхронно">
Наполнение аренды по корзине Yume Plus — настоящая асинхронная задача, но в одном месте (из заказа) вызывается
синхронно, а в другом (из счёта) — асинхронно. Смешение режимов затрудняет рассуждение о том, в какой схеме и когда
выполняется наполнение аренды.
</Accordion>
</AccordionGroup>

## Клиенты, бонусы, рефералы

[Открыть страницу модуля →](/ru/logic/clients-loyalty)

<AccordionGroup>
  <Accordion title="средний — начисление бонусов зависит от аккаунта пользователя, которого у офлайн-клиентов нет" icon="user-slash">
    Процент кэшбэка берётся из уровня лояльности, привязанного к аккаунту пользователя, но у большинства клиентов, заведённых менеджером вручную или импортом, аккаунт пользователя не заполнен. В итоге программа лояльности де-факто не действует для них, и всегда применяется процент кэшбэка по умолчанию из настроек компании. Уровень лояльности логичнее было бы хранить на самом клиенте, а не на аккаунте пользователя.
  </Accordion>
  <Accordion title="средний — начисление блокируется любым списанием бонусов по аренде" icon="ban">
    Начисление за аренду пропускается, если по этой аренде есть хоть одно списание бонусов. То есть если клиент оплатил часть завершённой аренды бонусами, он **не получит** кэшбэк за неё вовсе (а не только за оставшуюся оплаченную деньгами часть). Поведение может быть намеренным, но не очевидно.
  </Accordion>
  <Accordion title="средний — молчаливое подавление ошибок при начислении" icon="bug">
    Создание операции начисления обёрнуто в подавление любых исключений. Это гасит нарушение ограничения «только одно начисление на аренду», но заодно скроет любую другую ошибку начисления без записи в журнал.
  </Accordion>
  <Accordion title="низкий — дублированная логика стартового начисления" icon="copy">
    Приветственное стартовое начисление создаётся в двух местах: при создании клиента и при первом списании бонусов. На практике не дублируется благодаря проверке, был ли счёт создан впервые, но одну и ту же бизнес-логику стоит держать в одном месте.
  </Accordion>
  <Accordion title="низкий — валидатор ИИН допускает 12–14 символов" icon="id-card">
    ИИН в документе физлица проверяется как 12–14 символов, тогда как казахстанский ИИН всегда 12 цифр. При импорте значение обрезается до 14. Верхняя граница выглядит избыточной.
  </Accordion>
  <Accordion title="низкий — удаление пользователя не затрагивает связанного клиента" icon="link-slash">
    Ссылка клиента на аккаунт пользователя (в общей части системы) настроена так, что удаление пользователя не меняет клиента и может оставить «висячую» ссылку на уровне базы данных. Целостность полагается на то, что пользователей в общей части системы фактически не удаляют.
  </Accordion>
  <Accordion title="низкий — мягкое удаление клиента гасит все ошибки" icon="trash">
    Мягкое удаление клиента обёрнуто в подавление всех ошибок и на любой сбой возвращает конфликт (409) без деталей. Диагностика причины конфликта затруднена.
  </Accordion>
</AccordionGroup>

Критичных с точки зрения безопасности замечаний в модуле не выявлено: доступ к клиентам/бонусам защищён проверкой прав на соответствующие модели, а к уровням лояльности — правом «только суперпользователь может изменять». Основной риск — понятийный: уровень лояльности привязан к аккаунту пользователя, а не к самому клиенту, поэтому у клиентов, заведённых менеджером вручную или импортом, программа лояльности де-факто не действует.
