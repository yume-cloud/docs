Эта страница собирает в одном месте **проблемы, баги и логические ошибки** раздела: где поведение расходится с ожидаемым и к чему это приводит. Пункты сгруппированы по странице, на которой описано соответствующее штатное поведение.

<Note>
Остальные страницы раздела намеренно описывают только штатное поведение — все отклонения вынесены сюда.
</Note>

## Подводные камни со страниц раздела

### [Бонусы сотрудников](/ru/logic/metrics/bonuses)

<Warning>
- Показатель «Общая сумма транзакций» в сводке по бонусам не ограничивается выбранным периодом и суммирует вообще все транзакции компании за всё время, тогда как «Начислено» и «Списано» в том же отчёте считаются только за период — это несогласованность, которую легко принять за ошибку выбора периода.
- Тот же показатель «Общая сумма транзакций» — это простая сумма всех транзакций с учётом знака (начисления положительные, списания отрицательные), а не сумма масштаба операций без учёта направления: крупная программа с равными начислениями и списаниями даст маленькое или нулевое значение этого показателя.
- Баланс бонусного счёта нельзя задать напрямую: при каждом сохранении счёта его сумма принудительно перезаписывается пересчитанной суммой всех связанных транзакций, поэтому любое прямое редактирование баланса в обход транзакций теряется.
- На одну заявку аренды допускается не более одной транзакции начисления — это гарантируется ограничением на уровне базы данных; при попытке создать вторую такую транзакцию для той же заявки операция будет отклонена. Для списаний такого ограничения нет.
</Warning>

### [Депозиты](/ru/logic/metrics/deposits)

<Warning>
- **Названия счётчиков в сводке залогов вводят в заблуждение.** Все три показателя количества (общий, по полученным, по возвращённым) на самом деле считают записи с типом «Описание/предмет», а не денежные залоги — и все три реально возвращаются в ответе.
</Warning>

### [Амортизация и окупаемость инвентаря](/ru/logic/metrics/depreciation-payback)

<Warning>
- Показатели окупаемости (срок, эффективность, накопленный доход) в отчётах по группам, по единицам и в общей сводке всегда отражают всю историю единицы инвентаря, а не выбранный период дат — только доход, расход и количество начислений реально ограничены периодом.
- Накопленные ожидаемый и фактический доход в записи окупаемости включают историческое значение дохода единицы инвентаря, зафиксированное до подключения к учёту метрик, — то есть цифры окупаемости не начинаются с нуля для старого инвентаря.
- Запись окупаемости обновляется, если изменились округлённые до целого значения накопленного ожидаемого или фактического дохода, либо изменились дата или срок окупаемости. Небольшие изменения дохода (менее одной единицы валюты), которые при этом не сдвигают дату окупаемости, к обновлению записи не приводят.
- Дата окупаемости считается по тем же дневным начислениям, что и накопленный фактический доход, — то есть без фильтра по статусу зачётных строк. Если для единицы уже была историческая доходность (доход до подключения к учёту метрик), покрывающая цену покупки, датой окупаемости станет самый ранний день с начислением в учёте метрик.
</Warning>

### [Скидки](/ru/logic/metrics/discounts)

<Warning>
- **Суммарная «дополнительная скидка» на аренде не равна сумме всех скидок аренды.** В неё попадают только скидки, введённые вручную, или скидки из справочника с фиксированной суммой, не привязанные к конкретному инвентарю или услуге. Процентные скидки на всю аренду и скидки на конкретный инвентарь/услугу туда не включаются — полную картину показывает только сам отчёт.
</Warning>

### [Эффективность инвентаря](/ru/logic/metrics/efficiency)

<Warning>
- **Техническое обслуживание не входит** в число «валидных» источников дохода для этих отчётов, хотя в системе для него предусмотрено отдельное поле начисления прибыли — правило валидных источников фактически учитывает только заявки аренды, услуги, доставки, штрафы, заказ-наряды мастерской и продажи.
- В отчёте «Эффективность единицы инвентаря» (по прибыли) выручка и дни в аренде берутся из первой агрегированной строки на единицу инвентаря; поскольку группировка идёт строго по единице, это сейчас безопасно, но при изменении логики группировки в будущем есть риск случайно потерять часть данных.
- Формула упущенной выручки основана на обратном пересчёте через уже округлённую загрузку, а не через точное значение — из-за этого итоговая упущенная выручка может слегка отличаться от «идеального» значения, особенно при малой загрузке.
</Warning>

### [Финансы: список, PnL, движение денег](/ru/logic/metrics/finances)

<Warning>
- «Сальдо» в отчёте о прибылях и убытках считается как начисленная прибыль по всем источникам минус расходы месяца, а не как разница между выручкой по операциям и расходами — это может ввести в заблуждение, если ожидать симметрии с кэшфлоу.
- Выключенная статья доходов/расходов исключает операции из отчёта о прибылях и убытках полностью (и из общих сумм, и из разбивки по статьям), но не исключает их из кэшфлоу — там суммы и разбивка по статьям считаются без проверки этого признака.
- В расчёте кэшфлоу баланс на начало и на конец месяца не привязывается к нужному месяцу из-за внутренней ошибки сопоставления — в ответе API оба значения всегда равны нулю, независимо от реальных операций. Для фактического остатка нужно смотреть баланс самого счёта/кассы.
- Читать все три финансовых отчёта может не любой аутентифицированный пользователь, а только пользователь с ролью штатного сотрудника компании либо партнёра по субаренде.
- PnL группирует операции по месяцу через дату ведомости (а при её отсутствии — через дату создания), тогда как кэшфлоу всегда использует только дату создания операции, включая разбивку по статьям — перенос операции в ведомость на другую дату влияет на PnL, но не на кэшфлоу.
- Разбивка по статьям и в PnL, и в кэшфлоу строится только по операциям, у которых есть ведомость — операции без ведомости попадают в общие суммы месяца, но не попадают в разбивку по статьям ни в одном из двух отчётов.
</Warning>

### [Модули: доставки, мастерская, воронки, склад, инвентаризации](/ru/logic/metrics/modules)

<Warning>
- Отчёт по ресурсам мастерской фактически построен на перечне задач мастерской, а не на перечне записей о списании ресурсов: поля с товарной группой и количеством списанных единиц отсутствуют в ответе, а показанные стоимость и единица инвентаря относятся к задаче, а не к конкретному ресурсу. Постатейной разбивки по ресурсам, которую от него ожидаешь по названию, он сейчас не даёт.
- В отчёте по доставкам «дата последней доставки» и средняя длительность доставки считаются только для доставок с заполненной датой фактической выдачи исполнителю — если это поле пустое, доставка не участвует в расчёте, даже если у неё есть дата фактического завершения.
- В отчёте по продажам общие итоги не фильтруют по статусу продажи (учитываются черновики и отменённые продажи, если у них есть количество или ненулевая сумма), а разбивка по товарным группам учитывает только завершённые продажи — это разное поведение внутри одного отчёта.
- Рентабельность товара и рентабельность продаж по товарной группе выводятся как пустое значение (а не 0 или отрицательное число), если прибыль группы не положительна или выручка группы не положительна соответственно.
</Warning>

### [Обзор и общая сводка](/ru/logic/metrics/overview)

<Warning>
- Раздел «Метрики и аналитика» (включая эту страницу) проверяет не одно конкретное право доступа, а требует у сотрудника **сразу весь** набор прав аналитики. Если не хватает хотя бы одного пункта из списка, доступ к обзору и ко всем отчётам этого раздела закрывается целиком — выдать права аналитики выборочно не получится.
- Итоговые суммы дневной сводки считаются отдельным запросом по всей отфильтрованной выборке, а не по текущей странице — они одинаковы на любой странице одного и того же набора фильтров.
- Сумма «Оплачено клиентом» в построчной детализации считается по клиенту и дню в целом, а не по конкретной аренде, продаже или задаче. При нескольких начислениях одного клиента за один день это поле показывает одну и ту же общую сумму на каждой строке — визуально это выглядит как задвоение оплаты.
- В фильтре типа источника прибыли значение «аренда» присутствует в списке, но ничего не фильтрует — отчёт вернёт данные без сужения по типу. Рабочее значение для отбора аренд инвентаря — «инвентарь».
</Warning>

### [Штрафы](/ru/logic/metrics/penalties)

<Warning>
- **Отчёт не использует хранимое поле «оплаченная сумма».** Оплата всегда пересчитывается заново по фактическим проводкам прибыли, поэтому расхождение между полем на самом штрафе и тем, что видно в отчёте, — не ошибка.
</Warning>

### [Рефералы и клиенты](/ru/logic/metrics/referrals-clients)

<Warning>
- Показатель оттока клиентов в обзоре («текущее»/«предыдущее») на самом деле дважды содержит одно и то же вычисленное значение — реального сравнения с предыдущим периодом для этого показателя нет, хотя по форме блок выглядит как парный.
- Если для списка клиентов не переданы оба параметра периода одновременно, показатели «прогноз за период», «долг за период» и «задолженность по оплате» приводят к ошибке запроса, а не к расчёту без ограничения по датам — оба параметра нужно передавать либо вместе, либо не передавать вовсе (тогда отработает только сумма транзакций).
- Поле «показатель роста повторных обращений» в обзоре клиентской аналитики всегда возвращает ноль в обоих значениях — расчёт для него ещё не реализован.
- В графике оттока клиентов процентное изменение считается от более позднего (текущего) значения окна, а не от более раннего, как можно было бы предположить по названию показателя.
</Warning>

### [Зарплаты и субаренда сотрудников](/ru/logic/metrics/salaries-sublease)

<Warning>
- В отчёт по субаренде попадают не администраторы компании, а любые пользователи, у которых в записи о членстве в текущей компании включён признак «сотрудник-субарендатор» — отдельной проверки на роль администратора нет.
- Признак, определяющий доступность субаренды, — это персональный признак конкретного сотрудника в конкретной компании, а не общая настройка компании: отдельного общего выключателя субаренды на уровне всей компании не существует.
- При использовании фильтра по точке аренды в отчёте по сотрудникам-субарендаторам он ограничивает не только количество и стоимость инвентаря, но и все суммы дохода (факт/прогноз, доля сотрудника и доля компании) — они считаются только по инвентарю выбранной точки, а не по всему инвентарю сотрудника.
- Индивидуальные проценты вознаграждения заявки нигде не редактируются после её создания — они выставляются один раз автоматически и с тех пор действуют без изменений, даже если общие настройки компании позже меняются.
</Warning>

### [Услуги](/ru/logic/metrics/services)

<Warning>
- **Отменённые заявки без оплаты полностью выпадают из отчётов.** Если заявка отменена и по ней не внесено ни одной оплаты, все её услуги исключаются из всех четырёх представлений раздела — даже если услуги формально были назначены или фактически оказаны.
- **Один и тот же фильтр пригодности заявки действует везде одинаково.** Общая сводка, список услуг, обзор по исполнителям и история начислений применяют совершенно одинаковое условие отбора заявок, ещё до пользовательских фильтров по дате, услуге или исполнителю.
</Warning>

### [Транзакции](/ru/logic/metrics/transactions)

<Warning>
- Операции, которые являются строкой ведомости учёта (сверка с контрагентами, приход/расход по инвентарю), полностью исключаются из всех трёх отчётов раздела — это легко упустить при сверке итоговых сумм с другими источниками.
- В отчётах учитываются только операции со статусом «Успешно»; операции в статусах «Ожидает оплаты», «Ошибка» и «Истёк срок» никогда не появятся ни в списке, ни в сводках, даже если задать по ним фильтр по статусу — исходные данные уже отфильтрованы по успешному статусу до применения любых остальных фильтров.
</Warning>

### [Смены сотрудников](/ru/logic/metrics/workshifts)

<Warning>
- Фильтр по дате окончания смены («от» и «до») всегда пропускает смены без даты окончания, независимо от заданного диапазона — незакрытые смены нельзя отфильтровать по этому полю, они попадают в выдачу при любом значении фильтра.
- Открытие детализации смены каждый раз пересчитывает и перезаписывает сохранённые итоги смены в базе, даже если смена давно закрыта и ничего не изменилось — это операция записи, а не просто чтение.
- Расчёт оплат и возвратов для детализации смены не учитывает точку проката смены — берутся все успешные оплаты сотрудника за период смены независимо от точки проката связанной аренды.
- Аренда попадает в итоги смены либо по признаку «создана сотрудником на этой точке в период смены», либо по признаку «сотрудник совершил любое действие над арендой в период смены» — во втором случае точка проката аренды не проверяется, и аренда другой точки может попасть в чужую смену. Такое же правило (с тем же исключением по точке проката) действует и при отборе оказанных услуг для детализации смены, а не только для аренд.
</Warning>
