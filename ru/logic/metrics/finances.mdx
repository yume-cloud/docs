## Обзор

Эта страница описывает три финансовых отчёта, которые компания использует для контроля денег: **список операций** (реестр всех поступлений и списаний), **отчёт о прибылях и убытках (PnL)** и **кэшфлоу** (движение денег по счетам). Все три отчёта построены на одних и тех же финансовых операциях, но группируют и трактуют их по-разному:

- **Список операций** — построчный реестр с фильтрами и поиском, для повседневной сверки и разбора конкретных платежей.
- **PnL** — помесячная выручка (по методу начисления, «когда услуга оказана») в сравнении с расходами.
- **Кэшфлоу** — помесячное движение живых денег (по факту поступления/списания) с разбивкой по источникам.

<Info>
Во всех трёх отчётах из базовой выборки исключаются операции с нулевой суммой и операции, являющиеся «принимающей» стороной автоматического обмена (см. раздел «Обмен между операциями» ниже). Читать эти отчёты может пользователь, прошедший аутентификацию и имеющий роль сотрудника компании (штатного сотрудника или партнёра по субаренде) — не любой аутентифицированный пользователь. Изменение самих отчётов не предполагается (это `read-only` витрины) — управлять можно только исходными операциями.
</Info>

## Модель данных

### Финансовая операция

Центральная сущность — **финансовая операция**. Каждая запись — это одно движение денег: оплата аренды, продажи, работы мастерской, депозита, штрафа, обслуживания инвентаря или произвольная операция по счёту (не привязанная ни к чему).

| Поле | Тип | Назначение |
|---|---|---|
| Направление операции | поступление / списание | Определяет знак суммы: для списания сумма всегда становится отрицательной, для поступления — положительной, это происходит автоматически при сохранении независимо от того, как значение было введено. |
| Вид оплаты | связь со справочником | Наличные, карта, перевод и т.п. |
| Статус операции | ожидает / успешно / ошибка / истёк срок | Новая операция по умолчанию создаётся сразу успешной, если явно не указано иное; статус доступен как один из фильтров списка операций, но сами отчёты не ограничивают выборку каким-то одним статусом автоматически. |
| Статья | связь со справочником статей доходов/расходов | Группировка в PnL и кэшфлоу по категориям; статья может быть выключена из отчётов. |
| Счёт | связь со справочником счетов/касс | Отдельный фильтр в списке операций; при сохранении операции счёт может автоматически подставиться из вида оплаты, если для этого вида оплаты найден подходящий счёт в справочнике. |
| Сумма | число, 2 знака после запятой | Итоговая величина движения денег с учётом знака. |
| Дата и время создания | дата/время | Используется как дата операции, если для неё нет отдельной ведомости. |
| Продажа / Аренда / Задача мастерской / Обслуживание / Депозит / Штраф | связи | К какой сущности относится операция; операция может быть не привязана ни к одной из них (тогда это свободная операция по счёту). |
| Возврат | связь 1:1 | Если операция была возвращена клиенту — здесь фиксируется причина. |
| Ведомость (кассовый ордер) | связь 1:1 | Дополнительная детализация: инвентарь, контрагент и «дата ведомости», которая может отличаться от даты создания операции. |

### Обмен между операциями

Операция может ссылаться на другую операцию как на свою «пару обмена» — например, перевод денег с одного счёта на другой оформляется как две связанные операции. Операция, которая является «принимающей» стороной такого обмена (на неё есть обратная ссылка от операции-источника), исключается из базовой выборки списка операций и из верхнеуровневых сумм PnL и кэшфлоу. Операция-«источник» (та, что сама ссылается на пару) дополнительно исключается из верхнеуровневых сумм поступлений/расходов в PnL и кэшфлоу, но не исключена отдельно из разбивки по статьям — там применяется только базовое правило «принимающая сторона убирается». В списке операций у обменных операций есть отдельный третий вид фильтра — «обмен», в дополнение к «поступление» и «списание»; этот фильтр смотрит на то, ссылается ли сама операция на пару (то есть проверяет её со стороны источника).

### Ведомость (кассовый ордер)

Ведомость — необязательное расширение операции. Если она есть, у операции появляется:

- привязка к конкретной единице инвентаря и/или контрагенту (для более точной аналитики: например, расходы на топливо по конкретному автомобилю);
- собственная **дата ведомости**, которая может не совпадать с датой создания операции. Эта дата — тот момент, к которому операция фактически должна быть отнесена (например, расход был проведён в системе в начале следующего месяца, но фактически относится к прошлому).

<Note>
В отчёте о прибылях и убытках при разбивке по месяцам используется дата ведомости, если она есть, и только при её отсутствии — дата создания операции. В кэшфлоу дата ведомости не учитывается вообще — там всегда берётся дата создания операции. Это ключевое различие в поведении двух отчётов.
</Note>

### Статья доходов/расходов и её отключение

Статья — классификатор операции («Аренда», «Зарплата», «Топливо» и т.д.), с возможной иерархией (статья может иметь родительскую статью) и признаком «Учитывается в отчётах». Важно: разбивка по статьям в обоих отчётах (PnL и кэшфлоу) строится только по операциям, у которых есть ведомость — операция без ведомости, даже если у неё есть статья, попадает в общие суммы месяца, но не попадает в разбивку по статьям ни в одном из отчётов.

Если статья выключена:

- в отчёте о прибылях и убытках операции с такой статьёй **полностью выпадают** — и из общей суммы выручки/расходов по месяцу, и из разбивки по статьям;
- в кэшфлоу выключенные статьи **по-прежнему участвуют** в общей сумме поступлений/расходов месяца и в разбивке по статьям (среди операций с ведомостью) — признак «Учитывается в отчётах» там не проверяется.

<Warning>
Это асимметричное поведение: одна и та же операция может присутствовать в кэшфлоу, но отсутствовать в PnL за тот же месяц, если её статья выключена. При расхождении цифр между двумя отчётами в первую очередь стоит проверять именно этот флаг у статьи.
</Warning>

## Список операций

Это постраничный, фильтруемый и сортируемый реестр всех финансовых операций. К каждой строке подмешивается дополнительная информация, которой нет в самой операции:

- данные о клиенте (идентификатор, имя, телефон, аватар) — берутся из аренды, если она есть, иначе из продажи, иначе из задачи мастерской (первое найденное значение по этому приоритету);
- статус связанной аренды (если операция относится к аренде);
- точка проката — либо через ведомость с привязкой к инвентарю (берётся точка проката инвентаря), либо через саму аренду;
- при наличии ведомости — данные об инвентаре, контрагенте, дате ведомости, ресурсах обслуживания, комментариях и вложенных изображениях;
- при наличии обмена — сведения о парной операции;
- при наличии возврата — причина возврата.

### Фильтры

| Фильтр | Что делает |
|---|---|
| Направление операции («поступление» / «списание» / «обмен») | «Поступление» и «списание» дополнительно исключают операции, которые сами ссылаются на пару обмена; «обмен» — наоборот, показывает только их. |
| Точка проката | Ищет совпадение по точке проката через инвентарь ведомости, через аренду, через продажу или через задачу мастерской — операция попадает в выборку, если совпадает хотя бы один из этих путей. |
| Период по дате создания (с/по) | Фильтрует по дате и времени создания операции, с начала и до конца соответствующих суток. |
| Период по дате ведомости (с/по) | Сравнивает год и месяц: используется дата ведомости, а если её нет — дата создания операции; сравнение идёт по году и месяцу, а не по точной дате. |
| Счёт | Можно указать конкретный счёт по идентификатору либо специальное значение «без счёта», чтобы найти операции, не привязанные ни к одному счёту. |
| Метки, статус, статья, вид оплаты, направление, автор, статус/точка проката/клиент аренды, инвентарь и контрагент ведомости, наличие продажи/аренды/мастерской/обслуживания/ведомости | Стандартные фильтры точного совпадения или вхождения в список значений. |

### Поиск

Свободный поиск ищет совпадения по сумме, имени клиента, названию инвентаря и контрагента (из ведомости) и названию счёта; если в компании включён учёт автомобилей, дополнительно ищет по государственному номеру и техпаспорту привязанного автомобиля.

### Сортировка

Доступна сортировка по виду оплаты, сумме, автору, дате создания, ведомости, инвентарю и контрагенту ведомости, дате ведомости — с учётом того, что записи без значения сортируемого поля всегда показываются последними, независимо от направления сортировки.

## Отчёт о прибылях и убытках (PnL)

Этот отчёт показывает помесячную картину: сколько компания заработала и потратила, а также насколько «бумажная» выручка (начисленная по датам оказания услуги) отличается от реально полученных денег.

### Из чего складывается отчёт

Отчёт строится из трёх независимых источников, которые затем объединяются по ключу «год + месяц»:

1. **Помесячные суммы расходов и выручки по операциям.** Для каждого месяца берётся сумма всех списаний (расходы) и сумма всех поступлений (выручка) — учитываются только операции с включённой статьёй, без учёта обменных операций (ни принимающей, ни исходящей стороны). Месяц операции определяется по дате ведомости, а при её отсутствии — по дате создания.
2. **Начисленная прибыль по методу «сколько заработано, а не сколько получено деньгами»** — из отдельного набора записей о прибыли, который ведётся системой независимо от факта оплаты (подробнее — в отчётах по инвентарю и окупаемости). Сюда попадают только записи, прошедшие «фильтр учитываемой прибыли» (см. ниже), и они группируются не только по году и месяцу, но и по **типу источника**: аренда (инвентарь), услуга, доставка, штраф, мастерская, обслуживание, продажа.
3. **Разбивка по статьям** — операции с ведомостью и включённой статьёй, сгруппированные по статье, чтобы показать, из чего именно складываются расходы и выручка месяца. В отличие от пункта 1, здесь учитываются только операции, у которых есть ведомость; отдельного исключения обменных операций тут нет, но базовое правило (исключение принимающей стороны обмена) действует и здесь, как для любой выборки операций.

### Фильтр учитываемой прибыли

При расчёте начисленной прибыли (пункт 2 выше) в отчёт попадает только то, что можно считать «настоящей», подтверждённой выручкой:

- по аренде (инвентарь, услуга, доставка, штраф) — аренда не должна быть удалена, и либо она находится в статусе «в аренде», «завершена» или «должник», либо она отменена, но по ней уже есть фактически оплаченная сумма больше нуля;
- по мастерской — задача должна быть в статусе «завершена» или «в работе»;
- по обслуживанию — достаточно самого факта наличия записи;
- по продаже — продажа должна быть в статусе «продано».

Это общее правило используется не только в PnL, но и в ряде других денежных и аналитических отчётов, где фигурирует начисленная прибыль.

### Поля итоговой строки месяца

| Поле | Что показывает |
|---|---|
| Расходы | Сумма списаний за месяц по операциям с включённой статьёй, без учёта обменов. |
| Выручка по операциям | Сумма поступлений за месяц по операциям с включённой статьёй, без учёта обменов (не то же самое, что «начисленная прибыль» ниже). |
| Начисленная прибыль (по всем источникам) | Сумма начисленной прибыли по всем типам источника за месяц (аренда, услуга, доставка, штраф, продажа, мастерская, обслуживание). |
| Начисленная прибыль по аренде / по услуге / по доставке / по штрафу / по продаже / по мастерской / по обслуживанию | То же самое, но по каждому типу источника отдельно. |
| Разбивка по статьям | Список статей месяца (только по операциям с ведомостью) с суммой расходов и выручки по каждой. |
| Сальдо | Начисленная прибыль (по всем источникам) минус расходы месяца — то есть операционный финансовый результат месяца по методу начисления. |

<Warning>
Обратите внимание: «Сальдо» в этом отчёте считается не как «Выручка по операциям минус Расходы», а как «Начисленная прибыль минус Расходы». Это два разных числа — «Выручка по операциям» показывает реальные денежные поступления месяца, а «Начисленная прибыль» показывает, сколько выручки признано в этом месяце по датам фактического оказания услуги (метод начисления). Использовать оба поля как взаимозаменяемые нельзя.
</Warning>

### Применимые фильтры

По периоду (дате создания и/или дате ведомости), точке проката, направлению/статусу/статье/виду оплаты/автору операции, а также — отдельно для начисленной части отчёта, своим набором фильтров — по аренде, продаже, мастерской, обслуживанию, категории, инвентарю, группе/набору инвентаря и услуге. Отчёт не разбивается на страницы — он всегда возвращает весь период целиком.

## Кэшфлоу

Этот отчёт показывает помесячное движение реальных денег: сколько поступило, сколько списано и из каких источников.

### Из чего складывается отчёт

1. **Помесячные суммы поступлений и списаний**, всегда по дате создания операции (дата ведомости здесь не используется, в отличие от PnL). Обменные операции (обе стороны) не учитываются. Дополнительно вычисляется разбивка поступлений по источнику: по аренде, по продаже, по задаче мастерской, по обслуживанию, по депозиту, по бонусной операции.
2. **Разбивка по статьям** — операции с ведомостью, сгруппированные по статье; признак «Учитывается в отчётах» здесь не проверяется — то есть выключенные статьи всё равно показываются.
3. Отдельно система пытается рассчитать **помесячный баланс** нарастающим итогом по всем операциям. В текущей реализации этот расчёт не работает как задумано (см. примечание ниже) — начальный и конечный баланс месяца в выдаче отчёта фактически всегда равны нулю.

### Начальный и конечный баланс месяца

По замыслу для каждого месяца должны рассчитываться два значения баланса — баланс, накопленный на начало месяца (равный балансу на конец предыдущего), и баланс на конец месяца (с учётом операций текущего месяца).

<Warning>
На практике из-за расхождения между тем, как считаются агрегаты баланса, и тем, как их потом сопоставляют с месяцами отчёта, значения начального и конечного баланса не привязываются к нужному месяцу и в ответе API всегда возвращаются нулевыми — независимо от реального движения денег. Если нужен фактический остаток по счетам, следует ориентироваться на баланс, хранящийся у самого счёта/кассы (он пересчитывается независимо при каждой операции), а не на эти поля отчёта.
</Warning>

### Поля итоговой строки месяца

| Поле | Что показывает |
|---|---|
| Поступления (всего) | Сумма всех поступлений месяца без учёта обменов. |
| Поступления по аренде / по продаже / по мастерской / по обслуживанию / по депозиту / по бонусу | То же самое, но по каждому источнику отдельно. |
| Расходы | Сумма всех списаний месяца без учёта обменов. |
| Сальдо | Поступления плюс расходы (расходы уже хранятся как отрицательное число, поэтому фактически это «поступления минус расходы»). |
| Разбивка по статьям | Список статей месяца (только по операциям с ведомостью) с суммой расходов и поступлений по каждой, без фильтра по признаку «Учитывается в отчётах». |
| Баланс на начало месяца / Баланс на конец месяца | В текущей реализации всегда возвращаются нулевыми — см. предупреждение выше. |

### Применимые фильтры

Те же фильтры, что и в списке операций (период, точка проката, счёт, статус, статья, вид оплаты, автор, метки и т.д.), применяются к суммам движения денег и к разбивке по статьям. Отчёт также не разбивается на страницы.

## Как это используется

- **Список операций** — рабочий инструмент бухгалтера/администратора для повседневной сверки: найти конкретный платёж, отфильтровать по счёту или контрагенту, проверить, был ли возврат.
- **PnL** — управленческий отчёт для оценки прибыльности по месяцам с разбивкой по источникам дохода (что именно приносит прибыль: аренда, продажи, мастерская) и по статьям расходов.
- **Кэшфлоу** — контроль поступлений и списаний по месяцам и по источникам; для фактического остатка денег на счетах на определённую дату отчёт в его нынешнем виде использовать нельзя (см. предупреждение выше) — для этого стоит смотреть баланс самих счетов/касс.

<Tip>
Если нужно понять, почему PnL и кэшфлоу за один и тот же месяц показывают разные суммы выручки — это ожидаемо и почти всегда объясняется одной из причин: (1) в PnL используется дата ведомости, а в кэшфлоу — дата создания операции; (2) в PnL выручка — это начисленная прибыль по датам фактического оказания услуги, а в кэшфлоу — фактически полученные деньги; (3) в PnL операции с выключенной статьёй не учитываются вовсе, а в кэшфлоу — учитываются; (4) разбивка по статьям в обоих отчётах учитывает только операции с ведомостью, а верхнеуровневые суммы — нет.
</Tip>

## Подводные камни

<Warning>
- «Сальдо» в отчёте о прибылях и убытках считается как начисленная прибыль по всем источникам минус расходы месяца, а не как разница между выручкой по операциям и расходами — это может ввести в заблуждение, если ожидать симметрии с кэшфлоу.
- Выключенная статья доходов/расходов исключает операции из отчёта о прибылях и убытках полностью (и из общих сумм, и из разбивки по статьям), но не исключает их из кэшфлоу — там суммы и разбивка по статьям считаются без проверки этого признака.
- В расчёте кэшфлоу баланс на начало и на конец месяца не привязывается к нужному месяцу из-за внутренней ошибки сопоставления — в ответе API оба значения всегда равны нулю, независимо от реальных операций. Для фактического остатка нужно смотреть баланс самого счёта/кассы.
- Читать все три финансовых отчёта может не любой аутентифицированный пользователь, а только пользователь с ролью штатного сотрудника компании либо партнёра по субаренде.
- PnL группирует операции по месяцу через дату ведомости (а при её отсутствии — через дату создания), тогда как кэшфлоу всегда использует только дату создания операции, включая разбивку по статьям — перенос операции в ведомость на другую дату влияет на PnL, но не на кэшфлоу.
- Разбивка по статьям и в PnL, и в кэшфлоу строится только по операциям, у которых есть ведомость — операции без ведомости попадают в общие суммы месяца, но не попадают в разбивку по статьям ни в одном из двух отчётов.
</Warning>

- Статус операции используется только как один из пользовательских фильтров списка операций, а не как автоматическое условие, встроенное в выборку любого из трёх отчётов.
- Автоматическая подстановка счёта при сохранении операции берёт первый подходящий счёт для вида оплаты — если таких счетов несколько, выбор непредсказуем.
- Начисленная прибыль в PnL берётся не напрямую из операций, а из отдельного набора записей о прибыли, отфильтрованных по признаку «настоящей» выручки; например, отменённая аренда без фактической оплаты полностью выпадает из начисленной прибыли.
- Данные о клиенте, статусе аренды и точке проката в списке операций собираются по цепочке «аренда → продажа → мастерская» (берётся первое найденное значение), поэтому в нетипичных случаях в выдаче может отобразиться клиент не той сущности, которую ожидает пользователь.
- «Принимающая» и «исходящая» стороны обмена — это разные стороны одной связи; фильтр «обмен» и исключение из верхнеуровневых сумм проверяют разные признаки, а в разбивке по статьям исходящая сторона отдельно не исключается.
- Фильтр по периоду ведомости сравнивает год и месяц, а не точную дату — границы «с»/«по» действуют как «с начала месяца» и «по конец месяца».
- Направление операции и знак суммы всегда выставляются автоматически при сохранении, независимо от того, как сумма была введена изначально.
