## Платёжная безопасность

<Tip>
**Исправлено: вебхук результата оплаты теперь проверяет подпись.** Раньше публичный адрес приёма результата помечал счёт оплаченным по данным из тела запроса без проверки подписи — кто угодно мог выдать себе подписку. Сейчас входящая подпись сверяется по секрету мерчанта до любых изменений, предварительная проверка платежа сверяет сумму с суммой счёта и отклоняет уже оплаченный заказ, а повторные колбэки идемпотентны. (`tenant/views/billing/invoice.py`, `tenant/freedompay/client.py`)
</Tip>

<Warning>
**Колбэк привязки карты проверяет подпись с неверным именем операции — карты не сохраняются.** Адрес приёма результата привязки карты заканчивается слешем, а FreedomPay для таких адресов подставляет в подпись **пустое имя операции**. Обработчик же жёстко задаёт имя `create`, поэтому ожидаемая подпись никогда не совпадает с присланной.

- **Последствие:** каждый легитимный колбэк привязки отклоняется с кодом 400, платёжная карта не создаётся. Без сохранённой карты не работает рекуррентное автопродление — подписки перестают продлеваться автоматически. Обработчик результата платежа эту тонкость учитывает (перебирает варианты имени), а обработчик карты — нет.
- **Где:** `tenant/views/billing/card.py` (жёсткое имя операции при проверке подписи); корректный перебор — `tenant/views/billing/invoice.py`; адрес регистрации — `tenant/serializers/billing/card.py`, `tenant/urls/billing.py`.
- **Как чинить:** использовать тот же перебор имён, что в обработчике результата платежа (пустое имя, последний сегмент пути, затем явное имя).
</Warning>

<Warning>
**Дата окончания демо доступна на запись через API — бесплатная подписка без ограничения срока.** Сериализатор подключения интеграции отдаёт все поля модели, а в список «только для чтения» новое поле даты окончания демо не добавлено. Дата начала и дата окончания подключения защищены, но при сохранении модель подтягивает дату окончания подключения до даты окончания демо — то есть запись в незащищённое поле обходит защиту основного срока.

- **Последствие:** сотрудник компании-клиента может передать дату окончания демо на много лет вперёд (без флага демо, поэтому проверка платного подключения не срабатывает) и получить интеграцию бессрочно бесплатно. Снятие признака демо происходит только при оплате, которой не будет.
- **Где:** `integrations/serializers.py` (список полей только для чтения); подтягивание срока — `integrations/models/integration.py` (сохранение подключения); доступ к endpoint — `crm/permissions.py` (права сотрудника компании).
- **Как чинить:** добавить дату окончания демо в поля «только для чтения»; единственный допустимый способ включить демо — входной флаг демо.
</Warning>

<Warning>
**Повторное включение демо на действующем подключении продлевает пробный период без ограничений.** Проверка «интеграция уже подключена» срабатывает только если найденное подключение **неактивно**. Если оно активно и пришёл флаг демо, дата окончания демо безусловно переставляется на «сейчас + длительность демо», а модель подтягивает под неё дату окончания подключения.

- **Последствие:** повторяя запрос на подключение с флагом демо чаще, чем истекает пробный период, компания получает бесконечное бесплатное продление; проверка «подключается после оплаты» при флаге демо не применяется. Тот же запрос по **оплаченному** подключению помечает его демо-подключением.
- **Где:** `integrations/serializers.py` (ветка обновления при флаге демо); прежний код даты окончания на обновлении не трогал — дефект новый.
- **Как чинить:** запрещать демо, если у подключения уже есть дата окончания демо (в том числе истёкшая) или если подключение оплачено.
</Warning>

<Warning>
**Хранимый XSS в карточке счёта в админке.** Блок «Детали оплаты» собирает HTML из данных платежа и отдаёт его как доверенную разметку без экранирования. Данные платежа заполняются из колбэка шлюза дословно — включая имя держателя карты, которое вводит плательщик, а также бренд и способ оплаты, которые при неизвестном значении подставляются «как есть». Комментарий оператора при ручной регистрации оплаты тоже попадает в разметку без экранирования.

- **Последствие:** плательщик вводит в имя держателя карты разметку со скриптом; когда сотрудник Yume открывает этот счёт в админке, скрипт исполняется в его сессии — с доступом к админке, включая страницу регистрации оплаты.
- **Где:** `tenant/admin.py` (сборка деталей оплаты как доверенной разметки); источник данных — `tenant/views/billing/invoice.py` (запись данных карты из колбэка), `tenant/services/payment_info.py`.
- **Как чинить:** экранировать все подставляемые значения (или собирать разметку через средства форматирования с автоэкранированием).
</Warning>

## Расчёт стоимости

<Warning>
**Режим продления до даты не берёт плату за прирост лимита внутри текущего срока.** В этом режиме все платные единицы тарифицируются только за дни **от текущей даты окончания лимита до целевой даты**. Интервал «сейчас → текущая дата окончания» не оплачивается вообще, хотя при подтверждении счёта лимит поднимается до нового значения немедленно. Пропорциональная доплата за середину срока, которая есть в обычном режиме, здесь не применяется.

- **Последствие:** если срок лимита выровнен по подписке на аренду и уходит на месяцы вперёд (а выравнивание это делает штатно), то докупка мест до конца этого срока стоит около нуля. При целевой дате, равной текущей дате окончания или раньше неё, оплачиваемых дней получается ноль — прирост бесплатен полностью.
- **Где:** `tenant/services/billing.py` (ветка целевой даты в расчёте лимитной позиции); применение нового значения — `tenant/models/subscription/payment.py`.
- **Как чинить:** тарифицировать прирост от «сейчас», а не от текущей даты окончания: доплата за остаток текущего срока плюс полная цена за продление.
</Warning>

<Warning>
**Целевая дата раньше текущего срока укорачивает оплаченный период.** Отрицательное число дней приводится к нулю (плата не берётся), но дата окончания позиции всё равно ставится равной целевой дате. При подтверждении счёта дата окончания подписки и лимита перезаписывается значением из позиции без сравнения с текущей — то есть срок сдвигается **назад**.

- **Последствие:** оператор (или клиент через API) указывает дату раньше текущей даты окончания — оплаченные месяцы исчезают без возврата, предупреждения и строки в расчёте. У поля выбора даты нет и минимального значения.
- **Где:** `tenant/services/billing.py` (дата окончания = целевая дата в обеих ветках); перезапись — `tenant/models/subscription/payment.py`; разбор даты — `tenant/serializers/billing/invoice.py`, `tenant/views/admin/register_payment.py`.
- **Как чинить:** отклонять целевую дату в прошлом; при применении брать максимум из текущей и новой даты окончания.
</Warning>

<Warning>
**Пропорциональная доплата опирается на срок, который никто не проверяет.** Проверка лимитов сравнивает только «разрешено» и «использовано» — дату окончания лимита она не смотрит, и никакая задача не понижает лимит по истечении срока. При этом доплата за прирост считается пропорционально остатку срока и в последние сутки окна обнуляется (остаток дней округляется вниз до нуля).

- **Последствие:** купив прирост лимита в последний день срока за ноль тенге, компания получает повышенный лимит бессрочно.
- **Где:** `tenant/services/billing.py` (пропорция по остатку дней); проверка без учёта срока — `crm/permissions.py`; продление в автосписании только модулей и интеграций — `tenant/tasks/recurring_invoice.py`.
- **Как чинить:** либо применять срок лимита при проверке (по истечении опускать до бесплатного объёма), либо не продавать доплату дешевле некоторого минимума.
</Warning>

Прочие нюансы расчёта:

- **Автоподбор тарифа не учитывает валюту.** Поиск тарифа нужной длительности фильтрует по интеграции, типу, дням и вариации, но не по валюте, хотя у одной интеграции могут быть тарифы в разных валютах. Счёт всегда в тенге, поэтому цена из тарифа в долларах будет списана как тенге; при нескольких валютах выбор недетерминирован. То же касается сравнения цен в защите от подорожания. (`tenant/services/billing.py`)
- **Увеличение лимита в обычном режиме подорожает, если срок лимита разошёлся с тарифом аренды.** Раньше прирост всегда считался по месячной цене, умноженной на долю остатка, поэтому при сроке лимита в 180–365 дней доля превышала 6–12 месяцев и обычный режим стоил дороже режима продления до даты. Теперь цикл лимита равен длительности тарифа аренды, и с той же подпиской доля не превышает единицы. Остаточный риск — рассинхрон: если срок лимита выходит за пределы цикла (см. раздел о выравнивании сроков), доля снова становится больше единицы. (`tenant/services/billing.py`)
- **Две одинаковые позиции в одной корзине тарифицируются независимо.** Расчёт не сводит дубликаты по типу и интеграции: две лимитные позиции одного типа обе посчитаются от одного и того же исходного лимита, а провижининг применит последнюю. Клиент заплатит дважды за один прирост. Страница регистрации оплаты дубликаты снимает, а API — нет. (`tenant/serializers/billing/invoice.py`, `tenant/services/billing.py`)
- **Остаток дней округляется вниз.** Пропорция за середину срока считается по целым сутками с округлением вниз, тогда как в режиме целевой даты дни считаются по календарным датам. Одна и та же длительность в двух режимах может дать разное число оплачиваемых дней. (`tenant/services/billing.py`)
- **Позиции фискального чека не сходятся с итогом счёта.** В чеке для лимитной позиции указывается количество, равное итоговому лимиту, и цена, равная **сумме всей строки**, поэтому произведение «количество × цена» не совпадает с суммой, переданной шлюзу. (`tenant/tasks/recurring_invoice.py`)

## Сроки лимитов и подписка на аренду

<Warning>
**Выравнивание сроков лимитов по подписке на аренду перезаписывает уже оплаченные окна.** При каждом сохранении подключения интеграции «аренда» (оплата, продление, подключение демо, правка в админке) сроки **всех** лимитов компании принудительно приравниваются к дате окончания этого подключения. Никакого сравнения с текущим сроком лимита нет, поэтому срок меняется в обе стороны. При этом срок лимита — опора расчёта доплаты.

- **Последствие, укорачивание:** компания оплатила места на год, через месяц продлевается аренда на 30 дней — оплаченное окно мест схлопывается до 30 дней; следующая покупка «до даты» посчитает уже оплаченный интервал заново, то есть клиент заплатит за него дважды. **Обратное направление:** аренда оплачена на год, места — на месяц; любое сохранение подключения аренды бесплатно растягивает окно мест до года.
- **Где:** `integrations/models/integration.py` (сигнал выравнивания сроков лимитов); второй владелец того же поля — `tenant/models/subscription/payment.py` (провижининг по позициям счёта); использование срока в расчёте — `tenant/services/billing.py`.
- **Как чинить:** определить единственного владельца срока лимита. Если выравнивание нужно — только вверх (максимум из текущего и нового срока) и только для лимитов, входивших в оплату.
</Warning>

<Warning>
**Подключение аренды без даты окончания обнуляет сроки всех лимитов.** Отсутствующая дата окончания — легитимное состояние «бессрочно активна» (так же трактует её проверка доступа, и такую дату ставит оплата количественного тарифа). Но выравнивание ищет только подключения **с датой** и, не найдя ни одного, ставит всем лимитам срок «сейчас».

- **Последствие:** у компании с бессрочной арендой любое сохранение этого подключения делает все лимиты истёкшими: страница регистрации оплаты показывает их просроченными, а расчёт начинает брать полный месяц вместо пропорции.
- **Где:** `integrations/models/integration.py` (запасное значение «сейчас» при отсутствии датированного подключения); источник пустой даты — `tenant/models/subscription/payment.py` (количественный тариф).
- **Как чинить:** трактовать отсутствие даты как «бессрочно» и не трогать сроки лимитов вовсе.
</Warning>

Прочие нюансы сроков:

- **Обязательный срок лимита создаёт «фиктивно действующий» период.** Дата окончания лимита теперь обязательна и по умолчанию равна «сейчас + 30 дней». Автоматически созданный лимит поэтому выглядит как действующий период, и первая покупка идёт по пропорции за остаток этого периода, а не за полный месяц. (`tenant/models/tenant_limit.py`)
- **Выравнивание сроков идёт массовым обновлением.** Сроки лимитов обновляются в обход сохранения записи, поэтому история изменений лимита эти правки не фиксирует. (`integrations/models/integration.py`)

## Логические ошибки

<Warning>
**Возврат оплаты не откатывает выданные ресурсы.** Провижининг по счёту срабатывает только при статусе «подтверждён»; когда счёт позже переводится в «возвращён», ранее выданные лимиты, интеграции и SMS-баланс **не отзываются**.

- **Последствие:** после возврата средств компания сохраняет оплаченные места/интеграции/баланс.
- **Где:** `tenant/models/subscription/payment.py` (обработчик действует только на статус «подтверждён», отката для «возвращён» нет).
</Warning>

<Warning>
**Оплата инвойса не продлевает срок доступа компании.** Подтверждение оплаченного счёта выдаёт лимиты, интеграции и SMS-баланс, но не сдвигает окно доступа самой компании (начало/окончание периода): поля срока есть только у счёта и его позиций, у компании они не обновляются.

- **Последствие:** компания может оставаться «просроченной» по своему окну доступа несмотря на успешную оплату; автоматическое продление в коде не просматривается.
- **Где:** `tenant/models/subscription/payment.py` (обработчик подтверждения не трогает срок компании); окно доступа компании — `tenant/models/tenant.py`. Требует проверки, где именно должен продлеваться срок.
</Warning>

<Warning>
**Регистрация оплаты не защищена от повторной отправки.** Страница регистрации оплаты не имеет ни блокировки кнопки, ни признака идемпотентности: повторная отправка формы (двойной клик, обновление страницы, кнопка «назад») создаёт второй подтверждённый счёт с тем же составом.

- **Последствие:** двойной учёт выручки в отчётах и повторный провижининг — сроки подписки уезжают вперёд на два периода вместо одного, а лимиты выставляются дважды.
- **Где:** `tenant/views/admin/register_payment.py` (обработчик отправки формы).
- **Как чинить:** одноразовый токен формы либо проверка недавнего идентичного счёта перед созданием.
</Warning>

Прочие логические нюансы:

- **Оплата количественного тарифа снимает срок у уже оплаченного периодного подключения.** Провижининг переиспользует существующее подключение интеграции и для количественного тарифа ставит дату окончания пустой. Если по этой же интеграции был оплачен период, его срок превращается в «бессрочно активна». (`tenant/models/subscription/payment.py`)
- **Уменьшение лимита до нуля записывается как единица.** При переносе позиции в счёт нулевое количество заменяется на единицу, поэтому попытка обнулить лимит через регистрацию оплаты оставит компании одну платную единицу. (`tenant/services/billing.py`)
- **Пересчёт лимита без указания типа считает неверно.** Если тип не передан, последовательно выполняются все ветки подсчёта, каждая переписывает счётчик, и в итоге сохраняется только значение последней ветки (мотоциклы) в единственную запись лимита без типа. (`tenant/tasks/update_limit.py`)
- **Провижининг компании уведомляет администратора внутри транзакции.** Оповещение о регистрации компании отправляется до фиксации транзакции — при откате администратор всё равно уже уведомлён. (`tenant/tasks/generate_tenant.py`)

## Проверка лимитов (enforcement)

<Warning>
**Лимиты инвентаря не проверяются при создании.** Enforcement подключён только к созданию сотрудников и точек проката. Для автомобилей, самокатов и мотоциклов проверки лимита при создании нет, хотя эти лимиты тарифицируются и оплачиваются в счёте.

- **Последствие:** за лимиты по технике берут деньги, но создание сверх лимита ничем не блокируется.
- **Где:** миксины лимитов — `crm/mixins/subscription.py`; применены только в `crm/views/users.py` (сотрудники) и `crm/views/common/rental_points.py` (точки проката); для инвентаря аналога нет.
</Warning>

Прочие нюансы enforcement:

- **Срок действия лимита не проверяется.** Проверка сравнивает только разрешённое и использованное количество, а кэш хранит лишь эти два значения. Истёкший срок лимита ни на что не влияет — оплаченное однажды повышение действует бессрочно. Именно это делает возможными дефекты дешёвого прироста, описанные выше. (`crm/permissions.py`)
- **Проверка опирается на кэшированный счётчик использования**, который пересчитывает фоновая задача (у неё есть дефект подсчёта без указания типа — см. выше). Счётчик может отставать от реальности, поэтому при быстром создании нескольких объектов лимит можно кратковременно превысить. (`crm/permissions.py`, `tenant/tasks/update_limit.py`)
- **Демо-режим интеграции аренды снимает все лимиты.** При активном пробном периоде проверка сразу разрешает действие независимо от лимитов — вероятно, намеренно для демо, но полностью отключает enforcement. Вместе с дефектом бесконечного продления демо это даёт компании безлимитный доступ. (`crm/permissions.py`)

## Пролонгация и смена лимитов/интеграций в середине срока

<Tip>
**Исправлено: срок больше не «протекает» между позициями одного счёта.** Раньше длительность периода вычислялась как максимум по позициям интеграций в корзине, поэтому годовая интеграция, попавшая в тот же счёт, датировала места на год. Сейчас цикл лимитов не зависит от состава корзины: он берётся из тарифа подписки «аренда» этой компании — то есть из её плана, а не из случайного соседа по счёту. (`tenant/services/billing.py`)
</Tip>

<Tip>
**Исправлено: доплата за середину срока считается пропорционально.** Раньше докупка мест бралась по полному периоду без пропорции, а окно дельты стакалось на будущую дату окончания. Сейчас прирост в середине действующего срока считается пропорционально остатку, а окно лимита не сдвигается. Оставшиеся вопросы — в разделе [«Расчёт стоимости»](#расчёт-стоимости) выше: срок, к которому привязана пропорция, никто не проверяет, а режим целевой даты пропорцию не применяет.
</Tip>

<Tip>
**Исправлено: выбор даты окончания при нескольких подключениях одной интеграции.** Раньше карта «интеграция → дата окончания» строилась без сортировки, и при нескольких подключениях бралось произвольное. Сейчас берётся максимальная дата окончания, а поиск подключения предпочитает боевое, подключённое и более новое. (`tenant/services/billing.py`, `integrations/cache.py`)
</Tip>

<Tip>
**Исправлено: «оплачено, но неактивно» после досрочного продления и переподключения.** У подключения интеграции была дата начала, которую провижининг заполнял из позиции счёта — а при продлении она равна **концу текущего периода, то есть будущей дате**. Проверка активности требовала «дата начала не позже сейчас», поэтому досрочное продление (и переподключение сразу после отключения) выключало оплаченную интеграцию до наступления старой даты окончания. Дата начала у подключения **удалена**: активность теперь определяется только признаком «подключено» и датой окончания. Купленный период по-прежнему фиксируется в позиции счёта. (`integrations/models/integration.py`, `integrations/cache.py`, `tenant/models/subscription/payment.py`; миграция `integrations/0092`)
</Tip>

<Warning>
**Разные лимиты в первом и втором месяце не выставляются на продлении.** Рекуррентная задача берёт в счёт только позиции модулей и интеграций — лимиты (сотрудники, точки, техника) в неё не попадают. Вместе с тем проверка лимитов не смотрит на дату окончания, поэтому повышенный лимит оплачивается один раз и держится бессрочно.

- **Последствие:** «другой лимит на второй месяц» через автосписание выставить нельзя; изменение лимита возможно только счётом из кабинета или регистрацией оплаты, а однажды оплаченный лимит на продлении не перевыставляется.
- **Где:** `tenant/tasks/recurring_invoice.py` (в счёт идут только модули/интеграции); проверка без учёта срока — `crm/permissions.py`.
</Warning>

## Развёртывание и окружение

<Warning>
**Пакет crispy-forms подключён в настройках, но отсутствует в зависимостях.** В список приложений добавлен `crispy_forms` и настроен шаблонный пакет из состава Unfold, однако `django-crispy-forms` не добавлен в `requirements.txt`. Локально пакет установлен в виртуальном окружении, поэтому проблема не видна в разработке.

- **Последствие:** сборка Docker-образа устанавливает зависимости только из `requirements.txt`, а затем выполняет сбор статики, который импортирует все приложения — сборка падает с ошибкой отсутствующего модуля, деплой на stage и production блокируется.
- **Где:** `rental_tenant_back/settings.py` (список приложений и настройки шаблонного пакета); `requirements.txt`; `Dockerfile` (установка зависимостей и сбор статики).
- **Как чинить:** добавить `django-crispy-forms` в зависимости (для Django 5.1 — версия 2.4) либо убрать приложение из настроек, пока шаблонные теги не используются.
</Warning>

Прочие нюансы окружения:

- **При внутренней ошибке колбэк отвечает кодом 500 с текстом исключения.** Это заставляет шлюз повторить доставку (что желательно), но передаёт наружу внутренние детали ошибки. (`tenant/views/billing/invoice.py`)
- **Набор тестов расчёта не подключён к обычному запуску.** Тесты биллинга требуют отдельного запуска с указанием собственного тест-раннера; обычный запуск тестов проекта на них не рассчитан, в CI они не выполняются. (`rental_tenant_back/test_runner.py`, `tenant/tests/`)

## Кэширование компании

Прочие нюансы кэширования:

- **Кэш компании не сбрасывается при массовом обновлении.** Компания кэшируется целиком на 24 часа (по домену и по идентификатору), а сброс висит на сигнале сохранения записи. Массовое обновление компании в обход сохранения кэш не инвалидирует — устаревшие поля (например, окно доступа) держатся до истечения срока жизни кэша. (`middlewares/tenant.py`; сигнал сброса — `tenant/models/tenant.py`)
- **Кэш ролей в компании живёт без срока и не сбрасывается при смене роли** — то же, что описано в разделе проблем модуля пользователей; смена членства/роли эти ключи не инвалидирует. (`user/models.py`)
- **Подключения интеграций кэшируются целиком.** В кэш попадает объект подключения, а признак демо вычисляется из даты окончания демо при обращении — поэтому просроченный кэш может показывать демо активным до истечения срока жизни записи. (`integrations/cache.py`)

## Прочее

- **Захардкоженные адреса возврата на localhost в автосписании.** Адреса успеха/ошибки платежа указывают на `http://rent.localhost:3000/...` — локальные адреса разработки в задаче списания. (`tenant/tasks/recurring_invoice.py`)
- **Захардкоженный множитель цены SMS (×27).** Сумма SMS-баланса считается умножением на константу 27 прямо в коде. (`tenant/models/subscription/payment.py`)
