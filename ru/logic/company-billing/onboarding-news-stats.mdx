## Что покрывает эта страница

Здесь собраны вспомогательные части модуля компаний и биллинга, которые не относятся напрямую к жизненному циклу подписки и платежей, но работают в тех же общих таблицах платформы и обслуживают все компании сразу:

- отметки о пройденных шагах онбординга — общие для компании или личные для одного менеджера;
- системные новости с форматированным содержимым и вложенными изображениями;
- снимки статистики по каждой компании (метрики бизнеса и размер базы данных);
- планировщик пени по заявкам на аренду (записи-таймеры просрочки и напоминаний до неё);
- две фоновые задачи-помощника: архивация просроченных броней и отправка писем.

<Info>
Эти записи — учёт платформы, а не рабочие данные компании. Новость ни к какой компании не относится. Отметка онбординга, снимок статистики и запись планировщика пени несут ссылку на компанию, но их менеджеры по активной компании не фильтруют: там, где с ними работает код, компания указывается явно. Заявки, инвентарь и продажи устроены иначе: каждая их строка несёт ссылку на компанию, и менеджеры этих моделей сами ограничивают выборки активной компанией.
</Info>

## Онбординг компании

### Модель данных

Шаг онбординга — это простая отметка «такая-то компания (или менеджер в ней) прошла такой-то шаг».

| Поле | Тип | Назначение |
|------|-----|------------|
| Идентификатор | число | Первичный ключ |
| Компания | связь | Компания, к которой относится отметка |
| Пользователь | связь | Необязательное. Пусто — отметка общая для компании; заполнено — отметка записана только для этого менеджера. При удалении пользователя его личные отметки удаляются |
| Шаг | текст | Код пройденного шага (произвольная строка) |
| Дата прохождения | дата/время | Проставляется автоматически в момент создания записи |

Уникальны тройка «компания + пользователь + шаг» и, отдельно, пара «компания + шаг» среди общих отметок (у них пользователя нет): один и тот же шаг нельзя отметить дважды ни для компании, ни для одного менеджера. Записи упорядочены по порядку добавления.

**Какие шаги личные.** Общие шаги компании — прогресс первоначальной настройки (коды вида `first_…`: первый клиент, первая единица инвентаря и т. п.). Личные — подсказки функций и быстрый старт по задачам (коды `todo_…`, в том числе пропуск знакомства): прогресс по задачам считается по задачам самого менеджера, поэтому у каждого он свой. Шаги `todo_…` всегда записываются как личные, даже если признак личной отметки не передан: так работают старые сборки десктопного приложения.

### Как это используется

Онбординг доступен через личный кабинет компании и требует авторизации.

- **Получение списка** возвращает общие шаги текущей компании и личные шаги вызывающего менеджера; чужие личные отметки не видны (компания определяется по контексту запроса, а не передаётся клиентом). Постраничная разбивка отключена — отдаётся весь список сразу.
- **Отметка шага** создаёт запись; компания подставляется автоматически из контекста запроса, клиент передаёт код шага и, при необходимости, признак «личная» (только запись, по умолчанию выключен): с ним отметка привязывается к менеджеру, который её отправил. В ответе возвращаются код шага и дата прохождения.

<Note>
Набор кодов шагов не зафиксирован в модели — это свободный текст. Смысл конкретных кодов задаёт фронтенд, который и решает, какие шаги считать пройденными и как показывать прогресс.
</Note>

<Check>
Повторная отправка уже отмеченного шага безопасна: вместо ошибки уникальности возвращается уже существующая запись — так же и при одновременной отправке из двух вкладок. Раньше такой повтор заканчивался серверной ошибкой. Дубли клиент по-прежнему не создаёт, но и обрабатывать отказ ему не нужно.
</Check>

<Note>
При выпуске личных отметок удалены общие записи `todo_…`, которые успели появиться с момента переезда быстрого старта на этот адрес: прогресс каждого менеджера восстанавливается заново по его задачам при ближайшей проверке. Пропуск знакомства с задачами, отмеченный раньше только в браузере, теперь хранится на сервере и переезжает с менеджером на другое устройство.
</Note>

## Новости

### Модель данных

Новость — это системный анонс с форматированным содержимым и прикреплёнными изображениями.

| Поле | Тип | Назначение |
|------|-----|------------|
| Заголовок | текст | Заголовок новости |
| Содержимое | форматированный текст | HTML-контент; редактируется визуальным редактором в админке |
| Изображения | связь (список) | Прикреплённые изображения (обобщённая связь с общим хранилищем изображений) |
| Дата создания | дата/время | Момент создания (индексируется) |
| Дата обновления | дата/время | Момент последнего изменения |

Дата создания и дата обновления наследуются из базовой модели: первая проставляется один раз при создании, вторая обновляется при каждом сохранении.

### Как это используется

Новости отдаются через публичный API под префиксом новостей и, в отличие от онбординга, не требуют авторизации.

- **Список новостей** возвращает все новости, отсортированные от свежих к старым, с заранее подгруженными изображениями.
- **Детали новости** возвращают одну новость по её идентификатору, также с подгруженными изображениями.

В обоих случаях в ответ попадают идентификатор, заголовок, содержимое, список изображений и дата создания. Изображения доступны только для чтения — через этот API их нельзя добавить или изменить; наполнение новостей выполняется в админке.

<Tip>
Изображения подгружаются заранее одним дополнительным запросом (а не по одному на каждую новость), поэтому список новостей с картинками не порождает лавину запросов к базе. Выбираются изображения из административного набора хранилища.
</Tip>

## Снимок статистики компании

### Модель данных

Снимок статистики компании — это срез ключевых показателей одной компании на конкретный момент времени. Каждая запись — самостоятельный «фотоснимок»: новые данные не перезаписывают старые, а добавляются новой строкой, поэтому по накопленным записям можно смотреть динамику.

Поля сгруппированы по смыслу:

| Группа | Показатели |
|--------|------------|
| Пользователи | Число сотрудников, число пользователей |
| Тариф | Тип тарифа, период тарифа, категория компании |
| Заявки | Дата последней заявки, всего заявок, в аренде, забронированных, завершённых, отменённых, просроченных |
| Продажи | Число продаж |
| Справочники | Число клиентов, услуг, точек проката, скидок, типов оплаты, категорий, каналов привлечения |
| Инвентарь | Единиц инвентаря, наборов инвентаря, групп инвентаря |
| Деньги | Число платежей, сумма платежей |
| Служебные | Дата снимка, размер базы данных |

Особенности отдельных полей:

- **Дата снимка** индексируется и задаётся вручную при создании записи (а не автоматически) — это позволяет привязывать снимок к нужному расчётному моменту.
- **Тип тарифа, период тарифа, категория и дата последней заявки** могут отсутствовать (например, у компании без активного тарифа или без единой заявки).
- **Сумма платежей и размер базы данных** хранятся с точностью до двух знаков и по умолчанию равны нулю.

<Info>
Снимок — строка со ссылкой на компанию: его показатели описывают строки заявок, инвентаря, продаж и справочников этой компании. Кода, который создаёт снимки, в бэкенде нет: модель объявлена, но ни задача, ни представление в неё не пишут. Поэтому как должен считаться «размер базы данных» одной компании, по коду не установить.
</Info>

<Note>
Снимок — это сводка «сколько всего на момент X», а не журнал операций. Чтобы понять, что изменилось между двумя датами, нужно сравнить два снимка; сама запись изменения не хранит.
</Note>

## Планировщик пени по заявке

Планировщик пени по заявке — это запись-таймер в общих таблицах. По ней ежеминутная задача начисляет пеню по просроченной заявке на аренду или отправляет напоминание до просрочки.

| Поле | Тип | Назначение |
|------|-----|------------|
| Компания | связь | Компания, к которой относится запись (может быть незаданной) |
| Вид | выбор | «Просрочка» (по умолчанию) или «Напоминание до просрочки» |
| Индекс | число | У просрочки — порядковый номер группы позиций заявки с общим сроком возврата; у напоминания — 0 |
| ID заявки | число | «Сырой» идентификатор заявки компании |
| ID триггера | число | Только у напоминания: триггер сообщения, по которому оно уходит |
| Время начисления | дата/время | Момент срабатывания: у просрочки — срок возврата группы позиций, у напоминания — окончание аренды минус упреждение триггера |
| Последний запуск | дата/время | Когда запись сработала в последний раз |
| Интервал | интервал | Период повтора. У просрочки — шаг начисления пени из заявки (значение по умолчанию в модели — один час); у напоминания пусто, и оно срабатывает один раз |
| Включено | флаг | Активна ли запись (по умолчанию выключено) |

Уникальность зависит от вида: просрочка уникальна по тройке «компания + ID заявки + индекс», напоминание — по тройке «компания + ID заявки + триггер». У одной заявки может быть несколько записей просрочки, различаемых по индексу, и по одному напоминанию на каждый триггер.

<Note>
Идентификатор заявки хранится обычным числом, а не связью с таблицей заявок: база не проверяет, что такая заявка есть, и не удаляет запись вместе с заявкой. Заявку по этому номеру ищет ежеминутная задача — после того как установит контекст компании из записи, поэтому номер имеет смысл только в связке с компанией. Если заявка удалена или уже не в аренде и не просрочена, задача сама удаляет её записи.
</Note>

Механика начисления пени (когда создаются записи, как срабатывает периодический запуск, как выполняется автоначисление и центральный пересчёт) подробно описана в отдельной странице.

Подробнее: [«Депозиты и штрафы»](/ru/logic/rent/deposits-penalties).

## Задача архивации просроченных броней

Задумка задачи: бронь, до старта которой осталось меньше буферного времени и которая так и не перешла в аренду, автоматически убирается из активных, чтобы не занимать инвентарь. Для этого задача помечает удалёнными забронированные заявки, у которых начало аренды уже близко.

Как задача написана сейчас:

1. Перебирает только компании, у которых служебное имя (`schema_name`) не совпадает ни с общим значением по умолчанию, ни с `base`, — то есть старые компании. Компании, созданные в общих таблицах, в перебор не попадают вовсе.
2. Для каждой устанавливает контекст по служебному имени, а не по самой компании: активной компании с идентификатором в этом контексте нет.
3. Читает настройки автоархивации и буфера. Настройки хранятся строками со ссылкой на компанию, и без активной компании хранилище настроек их не находит — возвращаются значения по умолчанию: автоархивация выключена, буфер 3 часа.
4. Если автоархивация выключена или буфер — не интервал времени, задача завершается целиком, не переходя к следующим компаниям.
5. Иначе все ещё не удалённые заявки в статусе «забронирована», у которых начало аренды раньше, чем «текущий момент плюс буфер», помечаются удалёнными; перед этим у них удаляются строки [расписания занятости инвентаря](/ru/logic/inventory/availability), чтобы единицы освободились сразу, а не при ближайшей сверке расписания.

<Warning>
В текущем коде задача ничего не архивирует. Компании в общих таблицах она не перебирает, а на первой же старой компании получает «автоархивация выключена» — настройка читается без активной компании — и завершается. В расписании `CELERY_BEAT_SCHEDULE` задачи нет, и из кода её никто не ставит; есть ли для неё запись планировщика в базе, по коду не установить.
</Warning>

## Задача отправки письма

Фоновая задача, через которую уходят все транзакционные письма платформы: приветствие, создание компании, счёт и оплата, напоминание об окончании подписки, код и смена пароля, приглашение сотрудника. Принимает тему, текст письма, список адресатов и необязательный HTML-вариант. Собирает письмо из текстовой части и HTML-альтернативы и отправляет его от общего отправителя (по умолчанию «Yume») с заголовком автоматического письма. Работает в очереди «default».

Задача не подавляет ошибки: если почтовый сервер недоступен или отказал, она завершается с ошибкой, и сбой виден в мониторинге фоновых задач. Автоматического повтора у задачи нет — упавшее письмо само не переотправится.

<Tip>
**Исправлено: задача есть в реестре воркера.** Раньше её не было в пакете задач модуля компаний, и свежий воркер отбрасывал поставленные в очередь письма как незарегистрированные.
</Tip>

Как письма собираются из шаблонов, какие события их запускают и кому они уходят — на странице [«Транзакционные письма»](/ru/logic/notifications/emails).
