## Что делает эта часть модуля

Когда заказ аренды меняется, у клиента в Apple Wallet должна автоматически обновиться его карта заказа: новый статус, новые даты, актуальная сумма к оплате. Эта часть модуля отвечает за то, чтобы система вовремя «заметила» значимое изменение заказа, отметила соответствующие пропуска как обновлённые и разослала телефонам клиентов сигнал «пора скачать свежую версию карты».

<Note>
Автоматическая связка «отметка обновления + push» в этой части работает только для карт Apple Wallet. Карты Google Wallet в модуле тоже поддерживаются, но обновляются по другому пути и этим механизмом не затрагиваются.
</Note>

Механизм состоит из трёх звеньев:

1. **Перехват изменений заказа** — автоматический обработчик, который срабатывает при каждом сохранении заказа.
2. **Пометка пропуска обновлённым** — общая процедура, которая находит нужные карты, поднимает у них отметку времени изменения и ставит фоновые задачи на отправку push.
3. **Регистрация обработчика при старте** — подключение перехватчика к событиям заказа в момент запуска приложения.

<Info>
Отметка времени изменения на пропуске (поле «Обновлён») — это тот самый признак, по которому устройство Apple понимает, что карта устарела и её нужно перекачать. Push лишь «будит» телефон, а решение об обновлении устройство принимает, сверяя эту отметку. Поэтому поднять отметку времени так же важно, как и отправить push.
</Info>

## Отслеживание изменений заказа

При каждом сохранении заказа аренды автоматически вызывается обработчик изменения заказа. Он решает, нужно ли беспокоить карты клиента, по двум правилам:

- **Создание заказа игнорируется.** Если заказ только что создан, обработчик сразу завершает работу. Пропуск для нового заказа выпускается в другом месте (при выдаче карты клиенту), а не по факту создания заказа.
- **Фильтр по значимым полям.** Если сохранение указывает конкретный список изменённых полей, обработчик реагирует только тогда, когда этот список пересекается с набором «значимых полей заказа». Изменение любого другого поля (например, служебной пометки) карту не трогает.

### Значимые поля заказа

Обновление карты запускают изменения именно тех полей, которые видны клиенту на лицевой стороне пропуска:

| Что изменилось | Почему это важно для карты |
|---|---|
| Статус заказа | Клиент видит текущее состояние аренды |
| Статус оплаты | Отражает, оплачен ли заказ |
| Плановая дата начала аренды | Даты проката на карте |
| Плановая дата окончания аренды | Даты проката на карте |
| Фактическая дата начала аренды | Фактические сроки |
| Фактическая дата окончания аренды | Фактические сроки |
| Точка выдачи | Где забрать технику |
| Точка возврата | Куда вернуть технику |
| Скидка по цене | Влияет на итоговую сумму |
| Оплаченная сумма | Остаток к оплате на карте |

Если изменилось хотя бы одно из этих полей — карта считается устаревшей и запускается процедура пометки пропуска обновлённым для типа «Заказ».

<Warning>
Фильтр по значимым полям работает только тогда, когда сохранение заказа явно перечисляет изменённые поля. Если поля не перечислены (обычное полное сохранение заказа), фильтр пропускается и процедура пометки запускается при **любом** сохранении заказа. Лишний холостой прогон не вреден — если реальных изменений в картах нет, процедура тихо завершится, — но это значит, что нагрузка на этот механизм привязана к частоте сохранений заказов в целом, а не только к «значимым» правкам.
</Warning>

## Пометка пропуска обновлённым

Это общая процедура, к которой обращается обработчик заказа (а также, при необходимости, другие места модуля). Она получает на вход тип пропуска (здесь — «Заказ») и идентификатор связанного объекта (здесь — идентификатор заказа) и выполняет следующие шаги.

### Шаг 1. Проверка контекста компании

Процедура сначала убеждается, что известна текущая компания. Пропуска хранятся в общих (глобальных) таблицах, но привязаны к конкретной компании, поэтому без установленного контекста компании выбрать «свои» карты невозможно. Если контекст компании не определён — процедура молча завершается, ничего не делая.

<Note>
Обработчик заказа всегда работает уже внутри контекста конкретной компании (заказы принадлежат компании), поэтому в штатном потоке этот контекст присутствует. Проверка защищает от вызовов вне обычного веб-запроса.
</Note>

### Шаг 2. Выбор непогашенных пропусков

Процедура находит все пропуска, у которых одновременно совпадают:

- **компания** — активная компания;
- **тип пропуска** — «Заказ»;
- **идентификатор связанного объекта** — идентификатор изменившегося заказа;
- **признак аннулирования** — пропуск не аннулирован.

Аннулированные карты в выборку не попадают: их обновлять бессмысленно. Из выборки берётся список серийных номеров найденных пропусков.

<Tip>
На один объект (заказ) заводится ровно один пропуск, поэтому обычно в списке один серийный номер. Тем не менее логика рассчитана на несколько карт и рассылает push каждой найденной.
</Tip>

Если для заказа не нашлось ни одного действующего пропуска (карту клиенту вообще не выпускали) — процедура завершается, не производя записи в базу и не создавая фоновых задач.

### Шаг 3. Подъём отметки времени изменения

Для всех найденных пропусков одним групповым обновлением проставляется текущий момент времени в поле «Обновлён». Именно эта отметка сигнализирует устройству клиента, что его версия карты устарела.

### Шаг 4. Отложенная рассылка push

Рассылка push-задач ставится не сразу, а «после успешного сохранения изменений в базу». Только когда изменения гарантированно зафиксированы, на каждый серийный номер ставится отдельная фоновая задача push-обновления пропуска.

<Warning>
Push-задачи ставятся строго после фиксации изменений. Если операция сохранения по какой-то причине откатится, отметка времени не сохранится и push-и не уйдут — карты не окажутся в рассинхроне с базой. Это осознанная защита от «преждевременных» уведомлений.
</Warning>

## Фоновая доставка уведомления

Отправка каждого push вынесена в отдельную фоновую задачу — по одной на серийный номер. Задача является обёрткой над низкоуровневой отправкой push через сервис Apple (APNs) и при сбое автоматически повторяется: до трёх повторов с паузой около 10 секунд между попытками. Возвращаемое значение — количество фактически отправленных уведомлений (у одного пропуска может быть зарегистрировано несколько устройств; для каждого из них отправляется свой push).

## Подключение обработчика при старте

Перехватчик изменений заказа не подключается сам по себе — он регистрируется в момент готовности приложения Wallet. При запуске конфигурация модуля подгружает описание обработчиков, что и «включает» реакцию на сохранение заказов. Без этого шага изменения заказов проходили бы мимо карт.

## Как это связано с остальным модулем

Эта часть — «нервная система» модуля: она не выпускает карты и не собирает их содержимое, а лишь следит за изменениями заказа и запускает цепочку обновления уже выпущенных карт. Само содержимое обновлённой карты собирается позднее, когда устройство клиента, получив push, обращается за свежей версией пропуска к веб-сервису PassKit.
