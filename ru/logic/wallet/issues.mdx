Эта страница собирает в одном месте все известные **проблемы, риски и ограничения** модуля кошельков: где поведение расходится с ожидаемым, к чему это приводит и где искать причину в коде. Модуль в целом аккуратный — большинство пунктов относятся к доступу и к покрытию обновлений, а не к явным поломкам.

<Note>
Ссылки на файлы и строки даны для разработчиков как ориентир и относятся к состоянию кода на момент составления страницы. Остальные страницы раздела намеренно описывают только штатное поведение — все отклонения вынесены сюда.
</Note>

## Безопасность и доступ

<Warning>
**Брендированная выдача карт не требует входа в систему.** Четыре адреса выдачи карт (файл карты Apple и ссылка сохранения Google для бонусной карты клиента и для заказа) не задают класс доступа, поэтому действует общий для проекта режим «разрешено всем». Любой, кто может обратиться к адресу компании, способен запросить карту по числовому идентификатору бонуса или заказа.

- **Последствие:** перебором идентификаторов можно получить карту с персональными данными клиента (имя, баланс бонусов, детали заказа, QR со ссылкой на клиента) без какой-либо авторизации.
- **Где:** `wallet/views.py:57-108` (четыре представления без `permission_classes`; в проекте класс доступа по умолчанию — «разрешено всем»).
- **Уточнение:** если это задумано как публичные диплинки для добавления карты, риск ниже, но идентификаторы последовательны и легко перебираемы — стоит хотя бы подписывать/усложнять их либо требовать привязки к клиенту.
</Warning>

## Покрытие обновлений

<Warning>
**Бонусные карты в кошельке не обновляются автоматически.** Оповещение об изменении карты подключено только к изменениям заказа аренды. Ни одно место не вызывает пересчёт/рассылку при изменении баланса бонусов, поэтому уже добавленная в Apple Wallet бонусная карта не получает push-обновление при изменении баланса.

- **Последствие:** баланс на бонусной карте в телефоне «застывает» на момент добавления и расходится с реальным до тех пор, пока карту не перевыпустят/переоткроют вручную.
- **Где:** сигнал изменения — `wallet/signals.py:28-36` (только заказ аренды); рассылка — `wallet/services.py:15-31`.
- **Как чинить:** добавить оповещение об изменении карты при изменении баланса бонусов (по аналогии с заказом).
</Warning>

<Info>
**Серверные обновления карт есть только для Apple.** Рассылка обновлений идёт через фоновые уведомления Apple (push-сервис Apple); для Google Wallet серверного механизма обновления нет — сохранённая карта Google обновляется только когда клиент повторно открывает ссылку сохранения. То есть даже для заказов (где сигнал есть) push доходит лишь до карт Apple. (`wallet/services.py`, `wallet/push.py`, `wallet/google.py`)
</Info>

## Крайние случаи

- **Ключ поиска карты шире, чем ограничение уникальности.** Поиск-или-создание карты сопоставляет по набору «компания + вид + объект + идентификатор типа пропуска», тогда как уникальность в базе — по «компания + вид + объект». Если идентификатор типа пропуска когда-нибудь изменится, поиск не найдёт существующую строку, а вставка упрётся в ограничение уникальности и завершится ошибкой. (`wallet/views.py:46-53`, модель — `wallet/models.py:30-31`)
- **Список обновлённых карт для устройства не проверяет токен карты.** Endpoint, возвращающий серийные номера обновлённых карт для устройства, не выполняет проверку токена авторизации карты (фильтрует только по идентификатору устройства и типу пропуска). Это соответствует протоколу Apple служба обновления карт (данный запрос не подписывается токеном карты), но стоит иметь в виду при аудите. (`wallet/views.py:160-183`)
