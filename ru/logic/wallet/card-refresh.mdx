Полный перечень полей — в [глоссарии](/ru/logic/wallet/passkit-glossary).

## Что это за раздел

Когда клиент добавляет брендированную карту в приложение Apple Wallet, дальше карта общается с нашим сервером не через обычный кабинет, а через отдельный служебный интерфейс, описанный компанией Apple: приложение Wallet само регистрирует устройство для получения обновлений, спрашивает, какие карты изменились, скачивает свежую версию карты и присылает диагностические сообщения. Этот раздел описывает именно такой служебный интерфейс — набор эндпоинтов, к которым обращается **само приложение Apple Wallet на устройстве клиента**, а не сотрудник и не мобильное приложение компании.

<Info>
Все эндпоинты этого раздела вызываются устройством клиента автоматически. Человек их не открывает: их «пользователь» — приложение Apple Wallet, которое ходит на сервер по расписанию и в ответ на push-уведомления.
</Info>

## Общие правила для всех эндпоинтов

### Отключённая стандартная авторизация

Обычные эндпоинты системы требуют вход по токену сотрудника. Здесь это невозможно: у приложения Wallet нет учётной записи в системе. Поэтому у всех служебных эндпоинтов PassKit стандартная проверка входа и права доступа **полностью отключены** — доступ формально открыт для всех. Вместо этого для запросов, адресованных конкретной карте, используется собственная проверка секретного токена этой карты (см. ниже).

### Проверка токена карты

Каждый чувствительный запрос устройство сопровождает заголовком авторизации в формате `ApplePass <секрет карты>`, где секрет — это индивидуальный **токен авторизации**, сгенерированный при выпуске карты. Сервер:

1. Находит карту по паре «идентификатор типа пропуска + серийный номер».
2. Составляет ожидаемое значение заголовка из хранимого токена этой карты.
3. Сравнивает присланный заголовок с ожидаемым.

<Warning>
Сравнение выполняется защищённым от тайминг-атак способом (сравнение с постоянным временем), а не обычным равенством строк. Это осознанная мера безопасности: обычное сравнение по времени ответа могло бы подсказать злоумышленнику, насколько угаданный токен близок к настоящему.
</Warning>

### Единый порядок поиска карты и коды ответов

Для запросов, которые адресованы конкретной карте, действует общий алгоритм поиска:

| Ситуация | Ответ |
| --- | --- |
| Карта с такими типом и серийным номером не найдена | 404 (не найдено) |
| Карта найдена, но токен в заголовке не совпал | 401 (не авторизован) |
| Карта найдена и токен верный | запрос обрабатывается дальше |

При поиске карты сразу подтягивается связанная **компания** — она понадобится позже, чтобы установить RLS-контекст нужной компании.

## Регистрация и отмена регистрации устройства

Это эндпоинт, через который приложение Wallet подписывает устройство на push-обновления конкретной карты и отписывает его.

### Подписка устройства (создание регистрации)

Устройство присылает свой push-токен в теле запроса. Обработка:

1. Проверяется токен карты (иначе 404/401 по общим правилам).
2. Тело запроса разбирается как JSON. Если это не корректный JSON — ответ 400 (некорректный запрос).
3. Из тела берётся push-токен. Если он отсутствует или пустой — ответ 400.
4. Создаётся или обновляется **регистрация устройства** по паре «карта + идентификатор устройства»; в неё записывается свежий push-токен.

Результат зависит от того, была ли это новая привязка:

| Результат | Код ответа |
| --- | --- |
| Устройство привязано к карте впервые (создана новая регистрация) | 201 (создано) |
| Устройство уже было привязано, обновлён только push-токен | 200 (успех) |

<Note>
На одну карту одно устройство регистрируется только один раз: повторный запрос не плодит дубли, а обновляет ранее сохранённый push-токен. Именно этот токен потом используется фоновой отправкой push-обновлений.
</Note>

### Отписка устройства (удаление регистрации)

Запрос на удаление тоже сначала проходит проверку токена карты. Затем удаляется привязка «это устройство ↔ эта карта», и сервер отвечает 200. Ответ 200 возвращается независимо от того, существовала ли такая регистрация — повторное удаление безопасно.

## Список обновлённых карт

Периодически приложение Wallet спрашивает: «какие из моих карт на этом устройстве изменились с такого-то момента?». Эндпоинт отвечает списком серийных номеров.

### Как формируется ответ

1. Берутся все регистрации данного устройства, относящиеся к запрошенному типу пропуска.
2. Если в запросе передана отметка времени «обновлены после» (в виде числа — секунд Unix-времени), список сужается до карт, чьё время обновления **строго позже** этой отметки. Если отметку не удалось разобрать как число, она просто игнорируется, и возвращаются все карты устройства.
3. Из отобранных регистраций собираются серийные номера карт и время их последнего обновления.

<Note>
Этот эндпоинт не требует заголовка авторизации по конкретной карте — он работает на уровне устройства и типа пропуска, а не отдельной карты. Проверка секрета карты происходит уже на шаге скачивания самой карты.
</Note>

### Коды и содержимое ответа

| Ситуация | Ответ |
| --- | --- |
| Ни одной подходящей (обновлённой) карты нет | 204 (нет содержимого) |
| Есть обновлённые карты | JSON с меткой последнего обновления и списком серийных номеров |

В ответе метка «последнее обновление» — это самое позднее время изменения среди возвращённых карт (в виде секунд Unix-времени). Приложение сохранит эту метку и в следующий раз пришлёт её как «обновлены после», чтобы не запрашивать одно и то же повторно. Список серийных номеров возвращается без повторов.

## Скачивание карты

После того как приложение узнало, какие карты изменились, оно скачивает свежую версию каждой. Это самый содержательный эндпоинт: он собирает актуальный файл карты «на лету».

### Проверка «не изменилось ли с прошлого раза»

Устройство может прислать заголовок «если изменено после» с датой предыдущей загруженной версии. Сервер:

1. Разбирает эту дату. Если у неё нет часового пояса, она считается временем по Гринвичу.
2. Сравнивает её со временем последнего обновления карты. Если карта **не новее** присланной даты — возвращается 304 (не изменялось), и файл не пересобирается.
3. Если дату не удалось разобрать — она просто игнорируется, и карта отдаётся целиком.

<Tip>
Эта оптимизация экономит и трафик, и работу сервера: пересборка файла карты со всеми картинками и подписью запускается только тогда, когда карта действительно изменилась.
</Tip>

### Загрузка исходного объекта в RLS-контексте компании

Служебный интерфейс PassKit и сами карты живут в общих (глобальных) таблицах, а бонусные карты клиентов и заказы аренды принадлежат конкретной компании и разграничены RLS-политикой. Поэтому, чтобы собрать актуальную карту, сервер временно устанавливает RLS-контекст той компании, которой принадлежит карта, и уже в этом контексте загружает исходный объект:

- для карты типа **бонусная карта** — соответствующую бонусную карту клиента;
- для карты типа **заказ** — соответствующий заказ аренды.

<Warning>
Если исходный объект компании больше не существует (например, заказ или бонусная карта удалены), сервер возвращает 410 (ресурс исчез навсегда). Это сигнал приложению Wallet, что карту можно удалить с устройства.
</Warning>

Если объект найден, в RLS-контексте компании собирается свежий файл карты, и он отдаётся устройству с проставленным временем последнего изменения (чтобы в следующий раз сработала проверка «если изменено после»).

## Приём диагностических логов

Приложение Wallet может присылать на сервер собственные диагностические сообщения (например, если не смогло обновить карту). Этот эндпоинт:

1. Разбирает тело запроса как JSON. Если это не корректный JSON — вместо ошибки тело сохраняется как есть в текстовом виде.
2. Каждую строку из присланного списка сообщений записывает в журнал сервера как предупреждение.
3. Всегда отвечает 200 — приём логов не должен приводить к ошибкам на стороне устройства.

<Note>
Эти сообщения — служебная диагностика от Apple, а не бизнес-данные. Они попадают в общий журнал сервера и полезны при разборе проблем с обновлением карт.
</Note>

## Как это используется

Полный цикл жизни карты в Apple Wallet выглядит так:

1. Клиент добавляет карту в Wallet (карта выпускается в другом разделе модуля).
2. Устройство **регистрируется** для получения обновлений этой карты, присылая свой push-токен.
3. При изменении заказа или бонусной карты сервер помечает карту обновлённой и рассылает push (это происходит в фоновом разделе модуля).
4. Получив push, устройство **спрашивает список обновлённых карт**.
5. По каждой изменившейся карте устройство **скачивает свежую версию** (с учётом проверки «изменилось ли»).
6. При удалении карты пользователем устройство **отменяет регистрацию**.
7. При сбоях устройство может прислать **диагностические логи**.
