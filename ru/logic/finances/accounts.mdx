Полный перечень полей — в [глоссарии счетов](/ru/logic/finances/accounts-glossary).

## Модель данных

Три справочника, вокруг которых строятся все операции.

| Поле | Тип | Назначение |
| --- | --- | --- |
| **Денежный счёт** | | |
| Название | строка | Наименование кассы или расчётного счёта |
| Счёт по умолчанию | флаг | Отметка основного счёта |
| Начальный остаток | число (2 знака) | Стартовая сумма, от которой ведётся расчёт баланса |
| Текущий баланс | число (2 знака) | Начальный остаток плюс успешные операции по счёту, дата которых наступила; считается системой, вручную не задаётся |
| Привязанные виды оплаты | список | Виды оплаты, которые зачисляются на этот счёт; по ним подбирается счёт для оплаты |
| **Вид оплаты** | | |
| Название | строка | Наименование способа оплаты |
| **Статья** | | |
| Название | строка | Наименование категории |
| Родительская категория | связь на себя | Вышестоящая статья; пусто у верхнего уровня |
| Направление | выбор (приход/расход) | Приход или расход для этой статьи |
| Активна | флаг | Признак того, что статью можно выбирать |

Все три справочника поддерживают ручную сортировку и «мягкую» архивацию вместо физического удаления.

<Note>
В списке счетов (`GET /v1/finances/accounts/`) помимо реальных счетов всегда присутствует виртуальная строка **«Без счёта»**
без идентификатора — её остаток равен сумме успешных операций без счёта, дата которых уже наступила. Сюда же попадают оплаты
бонусами: вида оплаты у них нет, а значит, нет и счёта (см. [«Оплата бонусами»](/ru/logic/finances/payments#оплата-бонусами)).
</Note>

<Check>
Строка «Без счёта» теперь считает только состоявшиеся деньги — по тому же правилу, что и остатки реальных счетов. Раньше в неё шли все операции без счёта в любом статусе и с любой датой: ошибочные, ожидающие оплаты, с истёкшим сроком и датированные будущим раздували её остаток наравне с настоящими деньгами.
</Check>

## Логика и побочные эффекты

### Пересчёт баланса счёта

- При создании нового счёта текущий баланс приравнивается к начальному остатку.
- При изменении начального остатка существующего счёта баланс **сдвигается ровно на разницу** между новым и старым значением —
  накопленные операции при этом не теряются.
- Остаток счёта — это **«начальный остаток + сумма успешных операций по этому счёту, дата которых уже наступила»**. Расходы
  уменьшают его, приходы увеличивают; операции «ожидает оплаты», «ошибка» и «истёк срок» не участвуют. Как именно оплата
  попадает на счёт — см. [«Оплата: модель, знак и проверки»](/ru/logic/finances/payments).
- **Операция, датированная будущим, ждёт своей даты.** Берётся дата самой операции, дата назначения платежа на остаток не
  влияет. До наступления даты операция видна в списках, но остаток не двигает.
- Список и карточка счёта (`GET /v1/finances/accounts/`, `GET /v1/finances/accounts/<id>/`) считают остаток **в момент
  запроса**, поэтому операция на будущее начинает учитываться в свою дату без всякого пересчёта. Хранимое значение баланса
  пересобирается по той же формуле при каждом сохранении или удалении оплаты по счёту; в поле `balance` ответа на создание и
  правку счёта отдаётся именно оно.

<Check>
Проводка на будущее больше не двигает остаток заранее. Раньше в баланс шла любая успешная операция по счёту, в том числе датированная будущим: оплата, внесённая заранее с будущей датой, сразу меняла остаток кассы, хотя денег ещё не было.

Список и карточка теперь считают остаток по самим операциям. Раньше в выдачу шло хранимое поле, а его пересобирала только запись оплаты — по тому счёту, на котором оплата оказалась: когда оплату уводили на другой счёт, прежний счёт показывал устаревший остаток до следующей записи по нему.
</Check>

<Warning>
Нельзя менять начальный остаток, ожидая, что текущий баланс останется прежним — он автоматически сдвинется на разницу.
Текущий баланс задать вручную нельзя: поле `balance` в API только для чтения, остаток всегда вычисляется системой.
</Warning>

### Привязка вида оплаты к счёту

Каждое сохранение счёта через API — создание (`POST /v1/finances/accounts/`) или правка
(`PATCH`/`PUT /v1/finances/accounts/<id>/`) — забирает на него оплаты, пришедшие без счёта:

- берутся оплаты этой же компании **без счёта** с видом оплаты из привязанных к счёту, в любом статусе (в остаток из них
  попадут только успешные с наступившей датой);
- только сделанные **с момента открытия счёта** — дата операции не раньше даты создания счёта. Более ранние деньги не
  переносятся: считается, что они уже учтены в начальном остатке. У только что созданного счёта под это правило попадают
  разве что оплаты, датированные будущим;
- только по тем видам оплаты, для которых этот счёт — тот самый, на который подбор отправил бы новую оплату (первый по
  порядку живой счёт компании с этим видом). Если вид привязан и к счёту выше по списку, его оплаты сюда не переносятся;
- оплаты, уже лежащие на другом счёте, не трогаются; отвязка вида оплаты ничего не переносит обратно.

Если что-то перенеслось, остаток счёта сразу пересобирается, и ответ на запрос показывает его уже после переноса. Перенос
меняет у оплат только счёт — массовым обновлением, без побочных эффектов сохранения оплаты.

<Check>
Раньше привязка вида оплаты действовала только вперёд: оплаты этого вида, пришедшие, пока он не был привязан ни к одному счёту, оставались в «Без счёта», пока их не пересохранят. Теперь привязка забирает их на счёт — начиная с даты его открытия.
</Check>

### Мягкое удаление справочников

Удаление вида оплаты, счёта или статьи через интерфейс — не физическое: создаётся отметка об архивации (с причиной и
автором), а сама запись перестаёт показываться в списках выбора, но остаётся связанной с прошлыми операциями. Удалённый счёт
пропадает из списка и карточки счетов и выпадает из подбора счёта: новые оплаты на него больше не попадают. Контрагент
(см. [«Распределение, назначение платежа и контрагенты»](/ru/logic/finances/distribution)) удаляется как переключатель архивации:
первое удаление архивирует, повторное — восстанавливает.
