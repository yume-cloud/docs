## Модель данных

Оплата — центральная сущность финансового модуля. Одна запись всегда относится ровно к одному объекту бизнеса.

| Поле | Тип | Назначение |
| --- | --- | --- |
| Направление | выбор (приход/расход) | Задаёт знак суммы; при сохранении приход делается положительным, расход — отрицательным |
| Сумма | число (2 знака) | Итоговая величина со знаком; знак принудительно выставляется по направлению |
| Статус | выбор | Ожидает оплаты, успешно, ошибка, истёк срок; по умолчанию «успешно» |
| Вид оплаты | связь | Способ оплаты; по нему автоматически подбирается счёт |
| Счёт | связь | Счёт, на балансе которого отражается сумма; подставляется автоматически по виду оплаты среди живых счетов компании |
| Статья | связь | Статья прихода/расхода для аналитики |
| Кто создал | связь | Сотрудник, оформивший оплату |
| Аренда / Продажа / Мастерская / Тех.обслуживание | связь | Объект, к которому относится оплата (только один) |
| Депозит / Штраф | связь | Привязка к залогу или начисленному штрафу по аренде |
| Бонусная операция | связь | Заполнена у оплаты бонусами — аренды, оплаченной баллами клиента, а не деньгами (см. [ниже](#оплата-бонусами)) |
| Дата операции | дата и время | Можно передать при создании и изменить позже; операция с будущей датой двигает остаток счёта только с наступлением этой даты |
| Парная оплата (обмен) | связь на себя | Встречная оплата при переводе между счетами и при зачёте залога |
| Метки | множественная связь | Произвольные метки для группировки и фильтрации |
| Служебные данные | структура | Технические пометки; влияют на синхронизацию с Kaspi, на запрет удаления и помечают ноги зачёта залога |
| Комментарий | текст | Произвольное примечание |

<Info>
Оплата не может одновременно относиться к аренде, продаже, мастерской и тех.обслуживанию — при указании одного объекта
остальные обнуляются. Хотя бы один объект указать обязательно (это проверяется ещё до основной валидации).
</Info>

## Логика и побочные эффекты

### Знак суммы и подбор счёта

- **Знак задаёт направление, а не пользователь.** При каждом сохранении оплаты сумма нормализуется: расход всегда становится
  отрицательным, приход — положительным. Вручную заданный знак игнорируется.
- **Счёт подставляется по виду оплаты.** Если у оплаты указан вид оплаты, система ищет его в перечне привязанных видов
  **живых (не удалённых) счетов компании самой оплаты** и подставляет первый такой счёт по порядку в списке счетов —
  перезаписывая явно выбранный счёт. Если такого счёта нет, у оплаты остаётся счёт, переданный явно, а без него она
  попадает в строку «Без счёта».

<Check>
Подбор счёта смотрит только на живые счета своей компании. Раньше поиск шёл по всем счетам, в перечне которых встречался нужный вид оплаты: оплата могла уйти на удалённый счёт, и её сумма не попадала ни в один видимый остаток — удалённые счета в списке не показываются. Перечень привязанных видов — массив идентификаторов без внешнего ключа, поэтому в нём могли совпасть и идентификаторы видов оплаты других компаний; теперь подбор фильтрует счета по компании самой оплаты.
</Check>

<Warning>
Если один вид оплаты привязан к нескольким живым счетам компании, все оплаты этого вида получает **первый из них по порядку
в списке счетов**; остальные такие оплаты не получают никогда — ни при создании, ни при переносе после привязки (см.
[«Привязка вида оплаты к счёту»](/ru/logic/finances/accounts#привязка-вида-оплаты-к-счёту)). У переводов между счетами вид
оплаты не задаётся, поэтому там счета остаются заданными явно (откуда/куда) — подробнее в разделе
[«Переводы между счетами и возвраты»](/ru/logic/finances/transfers-refunds).
</Warning>

### Проверки суммы при создании

- **Продажа**: сумма не может превышать остаток к оплате по продаже; дополнительно проверяется наличие продаваемого
  инвентаря на складе.
- **Аренда**: сумма не может превысить остаток по аренде (цена со скидкой + штрафы − уже оплачено), а при оплате депозита —
  остаток к внесению по депозиту. При включённой настройке переплаты проверка по аренде пропускается, **а потолок депозита —
  нет**: залог нельзя внести сверх номинала ни при каких настройках.
- **Депозит** должен принадлежать той же аренде, что и оплата. Операцию, уже привязанную к депозиту, **редактировать нельзя** —
  её можно только вернуть или зачесть.
- **Оплата за выбранные дни графика** (только для аренды): сумму считает система — не больше остатка выбранных дней и
  остатка по аренде, а переданная сумма служит потолком (см. [«Оплата за выбранные дни»](/ru/logic/finances/schedule#оплата-за-выбранные-дни)).
- **Мастерская**: сумма не может превышать остаток по задаче.
- **Распределение**: если оно передано по аренде и непусто, сумма всех частей обязана точно совпадать с суммой оплаты (см.
  [«Распределение, назначение платежа и контрагенты»](/ru/logic/finances/distribution)).

<Note>
Проверка достаточности инвентаря на складе выполняется **только для оплат по продаже**, но не по аренде. Проверка равенства
распределения сумме оплаты срабатывает только для оплат по аренде.
</Note>

### Пересчёт оплаченности заказа

После любого сохранения или удаления оплаты автоматически пересчитываются суммы по связанному объекту:

- по **аренде** — обновляется оплаченность заказа (сумма всех успешных платежей аренды, не привязанных к назначению платежа;
  оплата бонусами в неё тоже входит). Операции по залогам **на хранении** в неё **не входят** — они попадают в оплату только
  зачётом; операции по залогам без этого признака засчитываются как обычная оплата (см. [«Депозиты и штрафы»](/ru/logic/rent/deposits-penalties#два-режима-учёта-денежного-залога));
- по **продаже** — дочерние расчёты продажи;
- по **задаче мастерской** — расчёты задачи.

Следом отложенно (в фоне) запускается пересчёт дневной прибыли — об этом ниже.

### Зачёт залога — пара операций

Зачёт залога в счёт аренды пишется парой: расходная операция по залогу и приходная операция по аренде на ту же сумму и с тем
же видом оплаты, связанные как парная оплата и помеченные признаком зачёта в служебных данных. Касса и баланс счёта при этом
не меняются, а удаление любой из двух ног уносит и вторую. Механика и потолки описаны в разделе
[«Зачёт в счёт аренды»](/ru/logic/rent/deposits-penalties#зачёт-в-счёт-аренды).

<Note>
В журнале финансов и в карточке операции такая пара подписывается как **зачёт залога** и не показывает пару счетов, как это
делает обычный перевод между счетами. Только приходная нога зачёта зеркалится в баланс клиента Kaspi — это уже оплата аренды;
сами залоговые операции в режиме «деньги на хранении» туда не попадают.
</Note>

### Оплата бонусами

Оплата с заполненной бонусной операцией (поле `bonus`) — это аренда, оплаченная **бонусными баллами клиента, а не деньгами**.
Она создаётся автоматически на каждое списание бонусов (см. [«Бонусы»](/ru/logic/clients-loyalty/bonuses)): приход на списанную
сумму без вида оплаты — а значит, и без счёта; списание по аренде привязывает её к этой аренде.

- **Входит в оплаченную сумму аренды** наравне с деньгами и поэтому видна в списке оплат аренды
  (`GET /v1/finances/transactions/?request=<id>`) с заполненным `bonus` — идентификатором бонусной операции.
- **Не открывается, не правится и не удаляется через карточку оплаты**: `/v1/finances/transactions/<id>/` отвечает на неё
  «не найдено». Снимается она только вместе со своим списанием — отменой списания бонусов по аренде
  (`DELETE /v1/crm/requests/<id>/delete_bonus/`) или удалением операции из бонусной истории клиента
  (`DELETE /v1/crm/clients/<client_id>/bonuses/<bonus_id>/`): оплата удаляется следом, а бонусы возвращаются на баланс
  клиента. Удаление одной оплаты оставило бы бонусы списанными.
- **Отделяется фильтром `bonus__isnull`**: `true` оставляет только деньги, `false` — только оплаты бонусами. Фильтр есть у
  списка оплат, у сводки `/v1/finances/transactions/general/` и у финансовых отчётов (см.
  [«Финансы: список, PnL, движение денег»](/ru/logic/metrics/finances)).

<Check>
Оплата бонусами теперь видна в списке оплат аренды. Раньше список её прятал, хотя в оплаченную сумму аренды она входила, — «Оплачено» по аренде не сходилось с суммой видимых оплат. В оплатах заказа интерфейс показывает её отдельным блоком «Бонусы» с отменой списания, в журнале финансов — с пометкой «Бонусы» вместо счёта.
</Check>

### Уведомления

- **О поступлении** — при создании новой успешной оплаты с положительной суммой; текст зависит от объекта. Депозитные
  оплаты по аренде намеренно **не** порождают такое уведомление; обе ноги зачёта залога — тоже.
- **Об удалении** — при удалении оплаты, с текстом по соответствующему объекту.
- **О возврате** — сразу после оформления возврата, с указанием объекта и причины (причина подставляется вместо комментария;
  подробнее — в разделе [«Переводы между счетами и возвраты»](/ru/logic/finances/transfers-refunds)). Возвраты по залогам
  из этого правила исключены — как и приход залога и обе ноги зачёта, они уведомлений не порождают.

<Note>
Уведомление о поступлении не отправляется, если сумма не положительна, если это не новая запись или если статус не «успешно».
Поэтому для оплаты возврата (отрицательная сумма) обычное уведомление о поступлении не срабатывает.
</Note>

## Как оплаты превращаются в прибыль

Оплата **не пишет прибыль напрямую**. При её сохранении или удалении срабатывает граница «оплата → прибыль»:

<Steps>
  <Step title="Пересчёт оплаченной суммы">
    Система заново собирает оплаченную сумму по аренде (или продаже) как сумму успешных платежей, не привязанных к назначению
    платежа, округлённую до целого.
  </Step>
  <Step title="Фоновый пересчёт прибыли">
    Запускается отложенная задача: ей передаются период аренды, цены по группам (инвентарь, услуги, доставка, штрафы) и общая
    оплаченная сумма.
  </Step>
  <Step title="Раскладка по дням «по остатку»">
    Оплаченная сумма раскладывается по дням и позициям своим алгоритмом: заводится «остаток», равный оплаченной сумме, и
    последовательно расходуется на предметы проката → услуги → доставку → штрафы. По каждой позиции и дню берётся минимум из
    планового дневного значения и оставшегося остатка.
  </Step>
  <Step title="Обновление окупаемости">
    По каждой затронутой единице инвентаря пересчитывается накопленная окупаемость — прибыль относительно закупочной цены.
  </Step>
</Steps>

<Warning>
Строки **распределения оплаты** по позициям в этом расчёте не участвуют — прибыль игнорирует, как менеджер разметил платёж,
и раскладывает общую оплаченную сумму в фиксированном порядке (сначала инвентарь, затем услуги, доставка, штрафы).
Из-за этого сумма дневной прибыли не обязана совпадать ни с оплаченной суммой, ни с суммами частей распределения.
</Warning>

Подробности алгоритма раскладки, коэффициент оплаты и расчёт окупаемости описаны на странице
[«Прибыль и окупаемость»](/ru/logic/profit-payback).
