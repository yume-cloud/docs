Эта страница собирает в одном месте **ограничения и неочевидное поведение** журнала истории действий: где строки не
окажется, где она окажется неполной и какие вопросы по журналу ответа не имеют. Пункты сгруппированы по странице, на
которой описано соответствующее штатное поведение.

<Note>
Остальные страницы раздела намеренно описывают только штатное поведение — все отклонения вынесены сюда.
</Note>

## Подводные камни со страниц раздела

### [Как события попадают в журнал](/ru/logic/audit/recording)

<Warning>
- Сбой записи журнала полностью проглатывается: ошибка уходит в технический лог, строка теряется, а сама операция
  проходит успешно. Поэтому **отсутствие строки не доказывает, что действия не было** — доказательной силой обладает
  только наличие строки.
- Сбой при сохранении накопленного буфера теряет **все** события запроса сразу, а не одно: буфер сохраняется одной
  операцией и обнуляется перед ней.
- Хозяин для поглощения автоматического события ищется только по основному объекту, без учёта действия. Если в одном
  запросе над одним объектом произошло два разных смысловых события, сравнение полей достанется тому, которое записано
  первым, а второе останется без изменений вовсе.
- Повторные правки одного поля внутри одного запроса схлопываются в одну строку: сохраняются самое раннее «было» и самое
  позднее «стало», промежуточные значения теряются безвозвратно.
- На страницах, работающих без компании — сброс пароля, коды подтверждения, вход через Google, личный кабинет клиента, —
  событие записывается только если у пользователя **ровно одно** место работы. Если мест работы ноль или больше одного,
  компанию определить нечем и события не будет совсем.
</Warning>

### [Автоматическое отслеживание изменений](/ru/logic/audit/tracking)

<Warning>
- Массовые операции не проходят через наблюдение за записями и оставляют только сводную строку с количеством затронутых
  записей. Понять по журналу, что именно изменилось в конкретной записи, в этом случае нельзя — это касается массовой
  правки состава аренды, массового изменения инвентаря, тарифов, импорта клиентов и инвентаря, списания и восстановления.
- Изменения, сделанные прямыми запросами к базе, сигналов не вызывают и в журнал не попадают вообще.
- Дополнительные поля клиента, снятые компанией с формы, перестают отслеживаться: их прошлые правки в журнале остаются, а
  новые изменения этих значений не фиксируются, пока поле не вернут на форму.
- Если перед сохранением записи не удалось прочитать её текущее состояние из базы, сохранение трактуется как создание: в
  журнале появится «создана» со всеми непустыми значениями вместо «обновлена» с перечнем правок.
</Warning>

### [Каталог событий](/ru/logic/audit/actions)

<Warning>
- Шесть формулировок присутствуют в списке фильтра «Все действия», но не возникают ни при каком действии: «Лимит
  изменён», «Документы клиента изменены», «Пользовательское поле изменено», «Функция компании изменена», «Подписи
  изменены» и «Настройка таблицы изменена». Соответствующие правки фиксируются автоматическим отслеживанием под складными
  названиями, поэтому фильтр по любому из этих шести значений всегда возвращает пустой список.
- Складные названия в фильтр не попадают вовсе — их 97, и все они относятся к реально возникающим событиям. Выбрать такое
  событие из выпадающего списка нельзя, отобрать его можно только запросом напрямую.
- Два справочника настроек названы в журнале иначе, чем в остальном интерфейсе: наименования сущностей отображаются как
  «Метка», дополнительные поля — как «Кастомное поле». Роль доступа на плашке объекта выводится со строчной буквы.
</Warning>

### [Как записывается изменение](/ru/logic/audit/diff)

<Warning>
- Маскирование работает по имени поля, а не по содержимому. Чувствительное значение, введённое в поле с безобидным
  именем — комментарий, название, описание, — попадёт в журнал целиком.
- Файловые поля сравниваются только по имени файла. Перезапись файла новым содержимым под тем же именем изменением не
  считается и в журнал не попадает.
- Если любая из версий текста больше 20 КБ, построчное сравнение не строится совсем: остаются только размеры и
  контрольные суммы обеих версий. Что именно изменилось в тексте, по журналу восстановить нельзя.
- Название связанного объекта подставляется в момент записи события. Если объект к этому моменту уже удалён, подписи не
  будет и в изменении навсегда останется только номер.
</Warning>

### [Просмотр, фильтры и доступ](/ru/logic/audit/access)

<Warning>
- Поиск покрывает только подпись объекта и подпись инициатора. Найти событие по изменившемуся значению — например все
  события, где сумма стала равна конкретному числу, — нельзя.
- Плашки объектов построены для шести видов: аренда, клиент, единица инвентаря, группа инвентаря, документ и шаблон.
  Объекты остальных видов — платёж, счёт, роль доступа, подключение интеграции, настройки — в строке журнала **не
  отображаются вовсе**, хотя к событию привязаны и через выборку по объекту доступны.
- Ссылка на плашке строится по номеру объекта и не проверяет, существует ли он. Для удалённого объекта переход приведёт
  на отсутствующую страницу.
- Дополнительные данные события — количества, суммы, коды, причины отказа, статусы до и после перехода — в панели
  истории не показываются. Они сохранены и возвращаются в выдаче события, но увидеть их в интерфейсе нельзя.
</Warning>

### [Событие журнала](/ru/logic/audit/event)

<Warning>
- События старше срока хранения (по умолчанию 365 дней) удаляются физически, без архивирования и без выгрузки. Механизма
  экспорта журнала во внешнее хранилище в системе нет, поэтому по истечении срока данные теряются безвозвратно.
- Служебные названия самих таблиц журнала заданы по-русски и не переводятся, поэтому на англоязычном служебном экране
  платформы они выводятся по-русски.
</Warning>
